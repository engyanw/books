## 1. 核心设计哲学
设计哲学是整套架构的底层逻辑原点，回答「为什么这么设计」的根本问题。本架构的所有能力、组件、流程均衍生自三大核心设计哲学，而非零散功能的堆砌。

### 1.1 为什么采用九平面分层架构（Why Plane Architecture）
#### 传统架构模式的核心局限
企业安全架构的演进经历了三代模式，在 AI Agent 场景下均存在本质性局限：
1. **边界式架构**：以网络边界为核心，外部不可信、内部可信，通过防火墙、WAF 等边界设备防护。其核心问题是 AI 风险来自输入语义与内部决策逻辑，而非网络位置，边界设备无法识别语义级攻击，「内网即可信」的假设彻底失效。
2. **单体式架构**：将所有安全能力打包在单一网关或代理中，统一处理所有流量。其核心问题是 AI 安全涉及身份、运行时、数据、基建、运营等多个完全不同的技术域，单体架构耦合度高、扩展困难、迭代慢，无法适配 AI 技术的快速发展。
3. **零散式架构**：按需采购单点安全工具，彼此独立、数据不通、策略分散。其核心问题是防护有缺口、数据有孤岛、运营效率低，无法形成纵深防御体系。

#### 九平面架构的设计依据
九平面分层架构本质是**业务-能力-基建三级解耦**的架构思想在 AI 安全领域的落地，核心设计依据来自三个维度：
1. **职责解耦**：将业务接入、AI 能力、Agent 执行、安全管控、基础设施、运营治理按职责分层，每层专注单一领域，技术栈可独立选型、独立迭代，避免技术绑定。例如 AI 模型迭代不会影响基础设施安全，运行时规则更新不会中断业务。
2. **纵深防御**：每层均设置对应安全控制点，形成从外到内的多层防御屏障，单层被突破仍有其他层兜底。相比单点防护，分层架构的攻击穿透成本呈指数级上升。
3. **企业级复用**：对齐 TOGAF 企业架构分层方法论与 SABSA 安全架构分层体系，与企业现有 IT 架构、安全架构天然兼容，可直接融入企业整体架构体系，避免形成独立的安全孤岛。

#### 分层架构的核心优势
- **可替换性强**：任意平面的组件可独立替换，不影响整体架构，例如更换模型厂商无需改造运行时安全，更换基建厂商不影响上层业务。
- **扩展能力好**：新的安全能力可在对应平面快速扩展，无需重构整体架构，适配 AI 技术快速迭代的特性。
- **责任边界清晰**：不同团队负责对应平面，业务团队负责业务平面、AI 团队负责 Agent 与 AI 平面、安全团队负责安全与治理平面，权责清晰、协同高效。
- **弹性适配性强**：不同规模企业可按需裁剪，小企业可合并多个平面部署，大企业可分布式独立部署，均不破坏架构一致性。

### 1.2 为什么坚持运行时优先（Why Runtime First）
#### 传统安全范式的失效
传统 IT 安全遵循「边界防护 + 静态权限 + 事后审计」的范式，其底层假设是「系统行为是确定的、可枚举的」，通过预设的权限与规则即可管控风险。但 AI Agent 的核心特性是**自主决策、动态行为、黑盒执行**，彻底打破了这一假设：
- 行为不可枚举：Agent 会根据输入动态生成决策与工具调用，无法提前穷举所有可能的操作路径。
- 风险发生在运行时：提示注入、越狱、工具滥用、记忆投毒等核心风险，均在运行过程中动态发生，静态权限与边界防护无法感知。
- 事后审计损失已造成：传统事后审计模式下，风险发生后才能追溯，此时数据泄露、误操作等损失已经产生，无法挽回。

#### 运行时优先的核心内涵
运行时优先，是指将安全管控的主防线从「边界与静态权限」前移到「Agent 运行全流程」，在行为执行的过程中完成检测、校验、拦截，实现风险的实时管控。其核心内涵包括三层：
1. **全流程嵌入**：安全能力嵌入 Agent 执行的每一个环节——输入检测、思考链校验、工具调用鉴权、记忆写入审核、输出脱敏，全程动态管控，而非仅在入口做一次检测。
2. **动态决策**：安全策略基于实时上下文、风险等级、身份信任度动态判定，而非固定的角色权限。同一 Agent 在不同场景、不同风险等级下，拥有不同的操作权限。
3. **实时拦截**：风险在执行前或执行中被拦截，而非事后追溯，从根源上避免损失发生。

#### 运行时优先的定位
运行时安全是 AI 原生安全的核心标志，也是区别于传统安全的最核心特征。它不替代身份、数据、基建等其他层的安全能力，而是作为纵深防御体系中的核心主防线，承担绝大多数 AI 原生威胁的检测与拦截职责，其他层作为兜底与补充。

行业实践数据表明，以运行时为核心的多层防护体系，对 AI 原生威胁的综合拦截率比传统边界式防护高出 60% 以上，同时具备更强的对抗变种攻击的能力。

### 1.3 为什么践行 Agent 原生安全（Why Agent Native）
#### 身份复用的本质风险
很多企业落地 AI Agent 时，直接复用用户身份或服务身份作为 Agent 的权限依据，这一模式存在不可忽视的本质风险：
- **权限放大风险**：Agent 自主决策的特性，使其可能执行用户本身不会执行的操作，若完全继承用户权限，会导致权限被间接放大，出现「用户没权限做的事，Agent 替他做了」的风险。
- **责任主体模糊**：当 Agent 执行操作时，到底是用户的责任、Agent 的责任还是管理员的责任，身份复用模式下无法清晰界定，出现问题难以追溯问责。
- **行为不可管控**：用户身份的权限体系是为人设计的，无法适配 Agent 动态调用工具、批量执行操作的特性，要么权限过松造成风险，要么权限过紧丧失价值。

#### Agent 原生安全的核心逻辑
Agent 原生安全，核心是承认 Agent 作为一类全新的独立实体，拥有专属的身份、权限、管控体系，而非用户或服务的附属。其核心设计逻辑包括三点：
1. **独立身份体系**：为每个 Agent 实例分配独立的工作负载身份，构建「用户身份→Agent 身份→服务身份」三级身份穿透链。Agent 的权限不直接继承用户，而是基于自身角色、任务场景、信任等级动态授予，用户身份仅用于审计追溯与权限边界约束。
2. **原生特性管控**：针对 Agent 独有的记忆、思考链、工具调用、多 Agent 协作等原生特性，设计专属安全管控机制，例如记忆写入校验、思考链安全审计、Agent 间信任边界等，这些是传统安全体系完全覆盖不到的领域。
3. **全生命周期治理**：从 Agent 的创建、部署、运行、迭代到下线，建立全生命周期的安全治理流程，适配 Agent 快速迭代、数量众多的运营特性。

#### Agent 原生的价值
- **权限更精准**：Agent 权限与任务精准匹配，遵循最小权限原则，既不放大风险，也不限制价值。
- **责任可追溯**：三级身份穿透，操作可定位到具体 Agent、对应用户、所属业务，责任边界清晰。
- **防护更全面**：覆盖 Agent 所有原生特性的攻击面，不留防护死角。

## 2. 七步架构设计方法论
整套架构的设计与落地遵循标准化的七步方法论，从业务出发，经风险、身份、运行时、策略、证据到治理，形成完整的闭环逻辑。所有能力设计均严格遵循该推导路径，确保架构不是功能堆砌，而是业务与风险驱动的科学结果。

### 2.1 第一步：业务驱动（Business Driven）
#### 设计依据
安全是业务的支撑，而非独立存在。脱离业务场景的安全架构是无的放矢，只会产生过度建设或防护不足的问题。所有安全设计必须从业务场景出发，以支撑业务安全落地为最终目标。

#### 执行逻辑
1. **业务场景梳理**：全面盘点企业所有 AI Agent 应用场景，明确每个场景的业务价值、用户规模、调用量级、操作权限、数据接触范围。
2. **价值优先级排序**：按业务重要性、价值量级对场景排序，明确核心场景与长尾场景。
3. **业务约束识别**：明确每个场景的性能要求、体验要求、可用性要求、迭代节奏，作为安全设计的约束条件。

#### 落地方法
- 建立业务场景分级标准，按核心/重要/普通划分三级。
- 安全方案与业务场景一一匹配，不同等级场景对应不同安全强度，不搞一刀切。
- 安全团队深度嵌入业务项目，从需求阶段同步介入，而非事后卡点。

#### 验证标准
- 核心业务场景 100% 覆盖对应安全方案。
- 安全对核心业务的性能影响控制在预设阈值内。
- 新业务场景的安全接入周期满足业务上线节奏要求。

### 2.2 第二步：风险驱动（Risk Driven）
#### 设计依据
安全的本质是风险管理。有限的投入不可能消灭所有风险，必须基于风险等级分配资源，高风险高投入，低风险低投入，实现投入产出比最优。

#### 执行逻辑
1. **攻击面分析**：针对每个业务场景，全面梳理攻击面、入口点、信任边界。
2. **威胁建模**：识别所有可能的威胁类型、攻击路径、发生概率、影响程度。
3. **风险评级**：按「发生概率 × 影响程度」计算风险值，划分高、中、低三级风险。
4. **防护优先级排序**：高风险场景优先覆盖，高危威胁优先解决，80% 的投入用于解决 20% 的核心风险。

#### 落地方法
- 采用标准威胁建模流程，对齐 MITRE ATLAS、OWASP LLM Top 10 等威胁框架。
- 建立风险分级标准，统一全企业的风险评判口径。
- 定期重估风险，随业务变化与攻击手法演进动态调整优先级。

#### 验证标准
- 高危风险 100% 有对应防护措施。
- 威胁覆盖度与风险等级正相关，核心风险无遗漏。
- 安全投入与风险等级匹配，资源分配合理。

### 2.3 第三步：身份优先（Identity First）
#### 设计依据
零信任架构的核心原则是「永不信任，始终验证」，身份是新的信任边界。在网络边界失效的 AI 场景下，身份成为所有访问控制的唯一可信锚点，所有权限、管控、审计都必须基于身份展开。

#### 执行逻辑
1. **实体识别**：明确所有参与主体——用户、Agent、服务、数据，为每类实体定义独立的身份体系。
2. **信任链构建**：建立「用户→Agent→服务→数据」的完整信任传递链，明确每一层的身份映射关系与权限约束。
3. **权限基准设定**：基于身份与角色，设定最小权限基准，所有权限默认关闭，按需申请开通。

#### 落地方法
- 遵循 SPIFFE 等通用工作负载身份标准，为 Agent 分配独立可验证的身份。
- 身份体系复用企业现有 IAM 底座，扩展 Agent 身份域，避免账号孤岛。
- 所有资源访问必须经过身份校验，无身份的访问默认拒绝。

#### 验证标准
- 所有 Agent 实例拥有唯一可追溯的身份。
- 全链路身份可穿透，操作可追溯到具体 Agent 与对应用户。
- 权限遵循最小原则，无过度授权的身份。

### 2.4 第四步：运行时优先（Runtime First）
#### 设计依据
如 1.2 节所述，AI 原生风险绝大多数发生在运行时，静态权限与边界防护无法有效管控。运行时是纵深防御体系的核心主防线，必须优先建设、重点投入。

#### 执行逻辑
1. **执行节点拆解**：将 Agent 全执行流程拆解为输入、规划、工具调用、记忆读写、输出等关键节点。
2. **控制点布设**：在每个关键节点布设安全控制点，对应检测、校验、拦截能力。
3. **防护分层设计**：每个节点采用多层防护，规则、模型、语义校验组合兜底，避免单层被绕过。
4. **动态适配**：防护强度随实时风险等级动态调整，高风险场景强防护，低风险场景保体验。

#### 落地方法
- 采用 Sidecar 模式部署运行时安全组件，与 Agent 同生命周期，无侵入接入。
- 建立规则+模型+行为的三层检测体系，兼顾已知威胁与未知威胁。
- 所有拦截操作支持灰度发布与一键回滚，避免误拦截影响业务。

#### 验证标准
- 核心 AI 原生威胁在运行时拦截率≥95%。
- 运行时新增延迟控制在业务可接受范围内。
- 关键执行节点 100% 覆盖安全控制点。

### 2.5 第五步：策略驱动（Policy Driven）
#### 设计依据
安全规则散落在各个组件中，会导致策略不一致、更新不同步、管理成本高。必须将安全策略从业务逻辑、组件代码中解耦，统一管理、统一分发、统一审计，实现安全即代码。

#### 执行逻辑
1. **策略统一抽象**：将身份权限、运行时规则、数据安全、访问控制等各类安全策略，抽象为统一的策略模型。
2. **策略集中管理**：建立统一策略中台，所有策略的编写、审核、发布、回滚均在中台完成。
3. **策略分发执行**：策略通过控制平面同步分发到所有执行点，确保全链路策略一致。
4. **策略即代码**：策略全部代码化管理，纳入版本控制，随业务流水线同步发布。

#### 落地方法
- 采用 OPA 等通用策略引擎，构建统一策略中台。
- 建立策略分级审批机制，高危策略变更多人审核。
- 策略变更支持灰度发布、效果验证、一键回滚。

#### 验证标准
- 所有安全策略统一纳管，无分散的隐形策略。
- 策略变更分钟级同步到全链路执行点。
- 策略全生命周期可审计、可追溯、可回滚。

### 2.6 第六步：证据支撑（Evidence Based）
#### 设计依据
没有度量就没有优化。安全效果不能凭感觉，必须基于可观测的数据与可量化的证据，持续验证防护效果，驱动架构迭代。

#### 执行逻辑
1. **全链路可观测**：所有安全组件、执行节点全面埋点，指标、日志、链路全覆盖。
2. **核心指标定义**：定义安全效果、运营效率、业务影响三类核心度量指标。
3. **效果持续验证**：通过红蓝对抗、攻防演练、误报统计、事件复盘，持续验证防护效果。
4. **数据驱动优化**：基于观测数据与验证结果，针对性优化防护规则、策略、架构。

#### 落地方法
- 基于 OpenTelemetry 标准构建统一可观测底座，避免数据孤岛。
- 建立定期评估机制，月度轻评估、季度深评估、年度全面评估。
- 攻防演练常态化，用真实攻击验证防护效果，而非纸面评估。

#### 验证标准
- 全链路安全数据可观测、可查询、可关联。
- 安全效果有量化指标，可衡量、可对比、可追溯。
- 架构优化有数据依据，而非经验驱动。

### 2.7 第七步：持续治理（Continuous Governance）
#### 设计依据
安全不是一次性项目，而是持续过程。AI 技术在快速发展，攻击手法在快速迭代，监管要求在持续更新，安全体系必须建立持续治理机制，动态进化、与时俱进。

#### 执行逻辑
1. **运营闭环**：建立「检测-分析-响应-复盘-优化」的完整运营闭环，每个安全事件都驱动防护能力升级。
2. **合规治理**：持续跟踪监管要求变化，动态更新合规管控措施，确保持续满足合规要求。
3. **生命周期治理**：覆盖 Agent 从创建、上线、运行、迭代到下线的全生命周期安全管控。
4. **组织与流程治理**：持续优化跨部门协同机制、责任体系、考核机制，保障安全体系有效运行。

#### 落地方法
- 建立常态化安全运营团队，7×24 小时值守核心场景。
- 定期开展安全审计、风险评估、攻防演练。
- 建立架构年度评审机制，同步技术与业务发展，持续迭代升级。

#### 验证标准
- 安全事件 100% 闭环，事件驱动规则迭代。
- 监管要求更新后可在规定周期内完成适配。
- 架构每年至少一次全面评审升级，保持先进性。

## 4. 核心设计原则体系
在三大设计哲学与七步方法论之下，架构落地遵循 13 项核心设计原则，分为四大类，统一指导所有组件与能力的设计。

### 4.1 安全本质类原则
1. **纵深防御原则**：多层防护、错位互补，避免单点防御，单层失效不导致整体失守。
2. **最小权限原则**：所有身份、组件、服务仅授予完成任务必需的最小权限，默认零权限。
3. **默认拒绝原则**：所有访问、操作、调用默认拒绝，仅白名单内的行为允许执行。
4. **零信任原则**：不基于网络位置赋予信任，所有访问必须经过身份验证与授权校验，持续验证信任度。

### 4.2 AI 原生类原则
5. **运行时优先原则**：安全管控重心放在运行时动态行为，优先建设运行时防护能力。
6. **Agent 原生原则**：为 Agent 建立独立的身份、权限、管控体系，适配 Agent 原生特性。
7. **安全左移原则**：安全能力向开发、测试、上线阶段前移，越早发现风险，修复成本越低。

### 4.3 工程落地类原则
8. **解耦可替换原则**：各层组件解耦，接口标准化，可独立替换，避免厂商锁定与技术绑定。
9. **标准开放原则**：优先采用开放标准与通用协议，兼容主流生态，降低集成与迁移成本。
10. **可观测可度量原则**：所有组件全量埋点，安全效果可量化、可验证、可追溯。
11. **故障友好原则**：安全组件故障时优先降级保障业务可用，事后补审，绝不因安全故障导致业务中断。

### 4.4 运营治理类原则
12. **数据驱动原则**：所有策略调整、架构优化基于数据证据，而非经验与主观判断。
13. **持续迭代原则**：安全体系持续进化，跟随攻击手法、业务发展、监管要求动态升级。

## 5. 架构评审与迭代机制
### 5.1 架构评审体系
#### 评审层级
1. **决策级评审**：由治理委员会执行，评审架构整体规划、重大调整、年度路线图，每年度一次。
2. **方案级评审**：由架构委员会执行，评审重大架构变更、核心组件选型、跨域方案设计，每季度一次。
3. **执行级评审**：由安全与技术团队执行，评审常规策略更新、规则优化、组件升级，按需开展。

#### 评审维度
所有架构评审统一围绕六个维度展开：
- 安全性：防护能力是否满足风险要求
- 性能：对业务性能的影响是否在阈值内
- 可用性：高可用与故障降级能力是否达标
- 可扩展性：是否支撑业务规模增长与能力扩展
- 合规性：是否满足监管与行业合规要求
- 成本：投入产出比是否合理

### 5.2 持续迭代机制
1. **事件驱动迭代**：每起安全事件、攻防演练发现的问题，72 小时内启动防护优化，形成事件驱动的快速迭代。
2. **周期驱动迭代**：每季度开展架构优化评估，每年完成一次全架构评审升级，保持架构先进性。
3. **监管驱动迭代**：监管新规发布后，第一时间开展差距分析，在要求时限内完成合规适配。
4. **技术驱动迭代**：跟踪前沿技术发展，定期开展技术预研，成熟后逐步引入架构升级。
