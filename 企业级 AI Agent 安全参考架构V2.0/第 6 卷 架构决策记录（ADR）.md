## 1. ADR 总述
### 1.1 定位与价值
架构决策记录（Architecture Decision Record, ADR）是整套架构的核心决策资产库，用于沉淀所有核心技术选型与架构设计的背景、依据、权衡过程与影响范围。其核心价值在于：
- **可追溯**：所有重要架构决策均有书面记录，避免“当时为什么这么设计”的历史疑问
- **可复用**：新团队、新成员可通过 ADR 快速理解架构设计逻辑，避免重复踩坑
- **可评审**：架构评审可基于 ADR 开展系统性复盘，确保决策逻辑严谨、权衡充分
- **可维护**：架构迭代时可基于历史决策评估变更影响，避免盲目调整破坏架构一致性

本卷所有决策均严格遵循第 2 卷的设计哲学与方法论推导得出，与整体架构体系保持完全一致。

### 1.2 标准记录格式
每份 ADR 均采用统一标准化格式，确保信息完整、逻辑清晰：
| 字段 | 说明 |
|------|------|
| 编号 | 全局唯一标识，格式为 ADR-XXX |
| 标题 | 决策主题的精准概括 |
| 状态 | 生效中 / 已废弃 / 待评审 |
| 背景 | 决策的触发场景、面临的问题与约束条件 |
| 决策 | 最终选定的架构方案 |
| 备选方案 | 曾考虑过的其他可选方案 |
| 利弊分析 | 各方案的优势、劣势、风险与成本对比 |
| 影响范围 | 受该决策影响的架构平面、组件与业务场景 |
| 关联引用 | 关联的架构卷册、能力项与外部标准 |

## 2. 身份与访问类决策
### ADR-001 身份联邦架构
**状态**：生效中

#### 背景
企业普遍已建设成熟的 IAM 身份体系与员工账号管理流程，若为 AI Agent 新建独立身份体系，会形成账号孤岛，增加管理成本、同步风险与安全漏洞；同时，Agent 权限与用户权限边界模糊，直接复用用户权限会导致权限放大风险。

#### 决策
采用**身份联邦 + Agent 独立身份域**的架构：
1. 复用企业现有 IAM 作为用户身份源，通过 OIDC/SAML 协议实现身份联邦对接，用户身份统一由企业 IAM 认证
2. 新增 Agent 工作负载身份域，为每个 Agent 实例分配独立身份，不直接继承用户权限
3. 用户身份与 Agent 身份建立映射绑定关系，仅用于审计追溯与权限边界约束，不做权限传递

#### 备选方案
1. **新建独立 AI 身份体系**：单独建设 AI 专属账号系统，独立管理用户与 Agent 身份
2. **完全复用用户身份**：Agent 直接继承操作用户的全部权限，无独立身份
3. **身份联邦扩展架构**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 新建独立身份体系 | 灵活性高，可完全适配 AI 场景 | 形成账号孤岛，同步成本高，管理复杂度翻倍，存在一致性风险 |
| 完全复用用户身份 | 实现简单，无额外开发成本 | 权限放大风险极高，责任主体模糊，无法实现 Agent 级细粒度管控 |
| 身份联邦扩展架构 | 复用现有身份投资，管理成本低；Agent 身份独立，权限可控；符合零信任最佳实践 | 需要一定的集成开发工作量，初期对接成本略高 |

#### 影响范围
- 零信任安全平面全量组件
- 所有跨平面访问鉴权逻辑
- 全链路身份追溯与审计体系

#### 关联引用
- Vol.2 架构方法论 · 身份优先原则
- Vol.3 零信任安全平面
- Vol.5 身份与访问安全域

### ADR-002 Agent 工作负载身份标准
**状态**：生效中

#### 背景
Agent 作为独立运行的智能实体，需要可验证、可追溯的身份标识。若采用自定义身份格式，会存在兼容性差、安全强度不足、跨系统互认困难等问题，需选择行业通用的标准化工作负载身份方案。

#### 决策
遵循 **SPIFFE 标准**构建 Agent 工作负载身份体系，使用 SPIRE 作为身份颁发与校验组件，为每个 Agent 实例颁发全局唯一、可加密验证的身份凭证（SVID）。
- 身份标识格式：`spiffe://企业域/agent/业务线/角色/实例ID`
- 凭证自动轮换，无长期静态密钥
- 支持跨集群、跨云的身份互认

#### 备选方案
1. **基于 API Key 的静态身份**：为每个 Agent 分配固定 API Key
2. **基于云厂商原生身份**：绑定云厂商服务角色，仅适配单一云环境
3. **SPIFFE 标准工作负载身份**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 静态 API Key | 实现简单，开发成本低 | 静态密钥泄露风险高，轮换困难，粒度粗，无法适配动态实例 |
| 云厂商原生身份 | 原生集成，安全强度高 | 厂商锁定严重，多云/混合云场景无法统一，不支持私有化部署 |
| SPIFFE 标准身份 | 开放标准、厂商中立、安全强度高、支持动态轮换、多云兼容 | 部署与运维有一定学习成本，初期建设工作量略大 |

#### 影响范围
- Agent 编排平面身份体系
- 工具网关、数据服务的访问鉴权
- 跨系统、跨域 Agent 协作信任

#### 关联引用
- Vol.2 架构方法论 · Agent 原生原则
- Vol.3 零信任安全平面
- SPIFFE/SPIRE 行业标准

### ADR-003 A2A 多智能体信任模型
**状态**：生效中

#### 背景
多 Agent 协作场景下，任务在多个 Agent 间流转，若权限随任务传递随意放大，会出现“低权限父 Agent 调用高权限子 Agent”的权限溢出风险；若每个 Agent 独立授权，又会导致协作链路断裂、效率低下。

#### 决策
采用**权限单向收敛的信任链模型**：
1. 任务从父 Agent 传递给子 Agent 时，子 Agent 的有效权限只能小于等于父 Agent，不得超出父 Agent 的权限边界
2. 协作链路全程携带身份上下文，每一跳都做权限校验与审计
3. 跨信任域的 Agent 协作必须经过信任网关校验，禁止直接点对点调用

#### 备选方案
1. **统一大权限模型**：所有 Agent 共享统一高权限，靠业务逻辑约束
2. **点对点独立授权**：每个 Agent 间单独授权，无信任传递
3. **单向收敛信任链模型**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 统一大权限 | 实现简单，协作顺畅 | 风险极高，单点突破全链路失守，无最小权限可言 |
| 点对点独立授权 | 权限最严格，安全强度最高 | 配置复杂度极高，协作效率低，无法支撑大规模多 Agent 场景 |
| 单向收敛信任链 | 兼顾安全与效率，符合最小权限原则，权限传递可追溯 | 设计复杂度较高，需要 Agent Mesh 层统一管控 |

#### 影响范围
- 多 Agent 协作架构
- Agent Mesh 信任管控
- 权限授权与校验逻辑

#### 关联引用
- Vol.3 Agent 编排平面
- Vol.4 多 Agent 视图
- Vol.5 身份与访问安全域

### ADR-004 动态授权引擎选型
**状态**：生效中

#### 背景
Agent 行为动态多变，传统基于角色的静态授权（RBAC）无法适配“同个 Agent 不同场景权限不同”的需求，需要支持基于上下文、属性、风险的动态授权能力，同时需保证策略与业务代码解耦。

#### 决策
采用 **OPA（Open Policy Agent）作为统一策略引擎**，构建 ABAC（属性基访问控制）动态授权体系：
1. 策略与业务代码完全解耦，统一在策略中台管理
2. 支持多维度属性输入：身份属性、场景属性、风险等级、数据敏感度、时间环境等
3. 策略即代码，纳入版本控制，支持灰度发布与一键回滚

#### 备选方案
1. **RBAC 角色授权**：基于角色分配固定权限
2. **业务代码硬编码权限**：权限逻辑写在业务代码中
3. **OPA + ABAC 动态授权**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| RBAC 角色授权 | 简单直观，易于理解 | 粒度粗，无法适配动态场景，容易出现权限过度，角色爆炸问题 |
| 代码硬编码 | 灵活性最高，可定制性强 | 策略与代码耦合，修改需要发版，无法统一管理，审计困难 |
| OPA + ABAC | 动态细粒度授权，策略统一管理，解耦业务，支持复杂场景 | 有一定学习成本，策略编写需要专业能力，性能略低于硬编码 |

#### 影响范围
- 零信任平面授权引擎
- 工具网关权限校验
- 数据访问权限管控

#### 关联引用
- Vol.2 架构方法论 · 策略驱动原则
- Vol.3 零信任安全平面
- Vol.5 身份与访问安全域

## 3. 运行时安全类决策
### ADR-005 运行时护栏部署模式
**状态**：生效中

#### 背景
运行时安全是 AI 原生安全的核心，需要嵌入 Agent 执行全流程。部署模式直接决定了侵入性、性能、可维护性与扩展能力，需要在业务无侵入与防护深度之间做权衡。

#### 决策
采用 **Sidecar 旁挂 + 集中网关**的双层部署模式：
1. 核心 Agent 实例旁挂安全 Sidecar，实现进程级细粒度管控，覆盖输入、思考、工具调用、记忆、输出全节点
2. 接入层部署集中式运行时网关，做前置流量清洗与基础检测，降低 Sidecar 压力
3. 所有检测规则统一由控制平面分发，Sidecar 与网关执行策略一致

#### 备选方案
1. **纯集中式网关**：所有流量经过统一网关检测，Agent 侧无防护
2. **代码 SDK 嵌入**：将安全能力以 SDK 形式嵌入 Agent 业务代码
3. **Sidecar + 集中网关双层模式**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 纯集中式网关 | 部署简单，无业务侵入，统一管理 | 只能检测入口出口，无法管控内部工具调用、记忆读写等中间节点，防护深度不足 |
| SDK 代码嵌入 | 防护深度最高，可管控全执行节点 | 业务侵入性极强，多语言适配成本高，版本升级困难 |
| Sidecar + 网关双层 | 防护覆盖全节点，业务无侵入，统一管理，兼顾深度与效率 | 部署复杂度略高，Sidecar 有少量资源开销 |

#### 影响范围
- 运行时安全平面全量组件
- Agent 部署架构
- 检测规则与策略分发体系

#### 关联引用
- Vol.2 架构方法论 · 运行时优先原则
- Vol.3 运行时安全平面
- Vol.5 运行时安全防护域

### ADR-006 提示注入检测三层架构
**状态**：生效中

#### 背景
提示注入与越狱攻击变种极快，单一检测机制很容易被绕过。纯规则检测灵活度不足，纯大模型检测性能差、成本高，需要多层组合的检测体系平衡检出率、误报率与性能成本。

#### 决策
采用**规则引擎 + 专用检测小模型 + 语义校验**三层检测架构：
1. **第一层：规则引擎**：基于正则、关键词、特征匹配拦截已知典型攻击，毫秒级响应，拦截 70% 以上已知攻击
2. **第二层：专用检测小模型**：针对变种注入与越狱攻击做深度学习检测，百毫秒级响应，拦截大部分未知攻击
3. **第三层：语义逻辑校验**：对高风险请求做深度语义分析与意图判断，秒级响应，精准判定复杂攻击

低风险场景只跑前两层，高风险场景跑全三层；所有层检测结果综合判定，多层兜底防绕过。

#### 备选方案
1. **纯规则检测**：仅依靠规则与关键词匹配
2. **纯大模型检测**：全部请求调用大模型做安全判定
3. **三层组合检测架构**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 纯规则检测 | 性能好、成本低、可解释性强 | 只能拦截已知攻击，变种攻击极易绕过，检出率低 |
| 纯大模型检测 | 泛化能力强，对未知攻击检出率高 | 延迟高、成本高、可解释性差，存在自身被注入的风险 |
| 三层组合架构 | 兼顾检出率、性能与成本，多层兜底防绕过，适配不同风险等级场景 | 架构复杂度高，需要持续迭代优化各层阈值 |

#### 影响范围
- 输入检测引擎
- 检测规则迭代体系
- 运行时性能与成本控制

#### 关联引用
- Vol.7 威胁建模体系 · 提示注入类威胁
- Vol.3 运行时安全平面

### ADR-007 上下文隔离机制
**状态**：生效中

#### 背景
多租户、多会话场景下，Agent 上下文与记忆数据如果共享存储，容易出现跨会话、跨租户的数据串扰与越权读取风险；如果全量物理隔离，资源成本又会大幅上升。

#### 决策
采用**会话+租户双维度逻辑隔离 + 高敏场景物理隔离**的分级方案：
1. 普通场景下，上下文与记忆按「租户 ID + 会话 ID」双维度做逻辑隔离，存储层统一，访问层强制校验权限
2. 高敏感租户与核心场景，采用独立存储实例物理隔离，与普通场景完全不互通
3. 所有跨上下文访问必须经过权限校验，禁止直接跨会话读取数据

#### 备选方案
1. **全量物理隔离**：每个租户/会话独立存储实例
2. **共享存储+标签标记**：统一存储，仅靠标签区分，无强制访问校验
3. **分级隔离方案**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 全量物理隔离 | 隔离强度最高，无串扰风险 | 资源成本极高，管理复杂度大，无法支撑大规模租户 |
| 共享存储+标签 | 成本最低，实现最简单 | 隔离强度弱，一旦出现权限漏洞直接导致数据泄露，风险极高 |
| 分级隔离方案 | 兼顾安全与成本，不同风险等级匹配对应隔离强度，整体性价比最优 | 分级规则设计复杂，需要精准的场景风险评级 |

#### 影响范围
- 记忆管理模块
- 上下文存储架构
- 多租户数据安全体系

#### 关联引用
- Vol.3 Agent 编排平面
- Vol.5 数据与模型安全域

### ADR-008 记忆安全管控机制
**状态**：生效中

#### 背景
Agent 持久化记忆是新型攻击面，攻击者可通过投毒篡改记忆内容，影响 Agent 后续决策；也可能通过越权读取记忆获取敏感信息。传统安全体系对记忆层无专项防护，存在明显盲区。

#### 决策
建立**写入校验 + 读取鉴权 + 定期巡检**的全生命周期记忆安全管控：
1. **写入前校验**：所有写入长期记忆的内容，必须经过内容安全、投毒风险、合规性三重校验，高风险内容禁止写入
2. **读取时鉴权**：记忆读取严格校验 Agent 身份与权限，只能读取授权范围内的记忆，禁止跨权访问
3. **定期巡检**：定期对全量记忆做风险扫描，识别已被投毒的异常记忆，及时清理修复

#### 备选方案
1. **无专项管控**：记忆直接读写，不做安全校验
2. **仅写入校验**：只在写入时做检测，读取无限制
3. **全生命周期管控**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 无专项管控 | 实现简单，无额外开销 | 完全暴露在投毒、越权读取风险中，属于严重安全短板 |
| 仅写入校验 | 覆盖主要投毒风险，实现成本适中 | 无法防范越权读取风险，已写入的投毒内容无法发现 |
| 全生命周期管控 | 覆盖写入、读取、存量全场景，风险防护最完整 | 有一定性能开销，巡检需要额外资源投入 |

#### 影响范围
- 记忆管理模块
- 运行时安全平面记忆安全组件
- 数据安全平面敏感数据管控

### ADR-009 输出安全双机制
**状态**：生效中

#### 背景
Agent 输出存在两类核心风险：一是敏感数据泄露，二是泄露后无法溯源。单一脱敏只能防泄露，无法溯源；单一水印只能溯源，无法阻止泄露，需要双机制配合形成完整闭环。

#### 决策
采用**动态脱敏 + 不可见水印**双机制并行：
1. **动态脱敏**：根据接收者权限等级，对输出内容中的敏感数据做对应粒度的脱敏，从源头降低泄露风险
2. **不可见水印**：对输出内容嵌入身份标识不可见水印，包含租户、用户、Agent、时间等溯源信息，泄露后可定位源头
3. 高敏感场景同时启用两种机制，普通场景可按需分级启用

#### 备选方案
1. **仅动态脱敏**：只做输出脱敏，不加水印
2. **仅水印溯源**：只加水印，不做脱敏
3. **脱敏+水印双机制**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 仅动态脱敏 | 从源头降低泄露风险，实现成本适中 | 无法对已发生的泄露做溯源追责，高权限账号泄露无法防范 |
| 仅水印溯源 | 不影响输出内容体验，泄露后可定位责任 | 无法主动阻止泄露，只能事后追责，属于被动防护 |
| 双机制并行 | 事前防护+事后溯源形成完整闭环，兼顾风险防范与责任追溯 | 实现复杂度略高，水印嵌入有少量性能开销 |

#### 影响范围
- 输出校验引擎
- 数据防泄露体系
- 安全审计与溯源能力

## 4. 工具与数据安全类决策
### ADR-010 工具网关统一管控模式
**状态**：生效中

#### 背景
Agent 可直接调用外部工具与业务系统，是最高风险的攻击面之一。如果 Agent 直接对接各个工具，会出现权限分散、审计缺失、参数不可控、攻击面过大等问题，必须做统一收敛管控。

#### 决策
所有外部工具调用必须经过**统一工具安全网关**，Agent 不直接对接任何外部工具：
1. 网关统一承担身份鉴权、参数白名单校验、请求审计、限流熔断、越权拦截职责
2. 工具接入统一注册、统一授权、统一管控，禁止私自接入未纳管工具
3. 按工具风险等级分级管控，高危工具必须人工二次审批后方可执行

#### 备选方案
1. **Agent 直连工具**：Agent 直接调用各工具接口，权限自行管理
2. **各业务线单独管控**：每个业务线自己管理工具权限
3. **统一工具网关模式**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| Agent 直连工具 | 开发简单，对接灵活 | 权限分散、审计缺失、攻击面大，出现问题无法统一管控，风险极高 |
| 各业务线单独管控 | 业务自主性强，适配灵活 | 标准不统一，重复建设，整体安全水位参差不齐，存在短板 |
| 统一工具网关 | 收口所有工具调用，统一安全管控，审计完整，攻击面大幅收敛 | 初期建设有一定成本，工具接入需要走统一流程 |

#### 影响范围
- 工具安全网关
- 所有外部工具与业务系统对接
- Agent 工具调用权限体系

### ADR-011 MCP 协议标准化适配
**状态**：生效中

#### 背景
Agent 工具对接协议碎片化，各厂商、各框架协议不统一，集成成本高、迁移困难，容易形成厂商锁定。需要选定行业通用的标准协议作为工具接入的统一规范，降低集成与迁移成本。

#### 决策
以 **MCP（Model Context Protocol）作为工具接入的统一标准协议**，所有新接入工具优先遵循 MCP 规范，存量工具逐步适配改造。
- 工具网关原生支持 MCP 协议，提供标准化接入能力
- 保留私有协议适配能力，作为存量系统的过渡方案
- 跨厂商、跨平台工具对接优先采用 MCP 标准，避免厂商锁定

#### 备选方案
1. **自定义私有协议**：自研一套工具对接协议
2. **逐一适配各厂商协议**：兼容所有主流协议，无统一标准
3. **MCP 标准协议统一**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 自定义私有协议 | 完全自主可控，可定制性强 | 生态兼容性差，第三方工具适配成本高，无行业共识 |
| 逐一适配多协议 | 兼容性最好，可接入所有工具 | 维护成本极高，协议碎片化，管理复杂度随工具数量线性增长 |
| MCP 标准协议 | 行业共识度高，生态发展快，厂商中立，避免锁定，迁移成本低 | 协议仍在快速迭代，需要持续跟进版本演进 |

#### 影响范围
- 工具网关协议适配
- 插件管理中心
- 第三方工具生态对接

### ADR-012 密钥代理（Secret Broker）机制
**状态**：生效中

#### 背景
Agent 调用工具与服务需要访问密钥、凭证等敏感信息，如果将密钥直接配置在 Agent 运行环境中，存在静态密钥泄露、权限过大、无法审计等风险，不符合最小权限与凭证动态化原则。

#### 决策
采用 **Secret Broker（密钥代理）机制**，所有密钥统一托管，Agent 不持有静态密钥：
1. 所有密钥、凭证、Token 统一托管在企业密钥管理系统中，Agent 环境中无任何静态密钥
2. Agent 需要调用工具时，向 Secret Broker 申请临时凭证，Broker 校验身份与权限后，颁发短时有效的临时凭证
3. 临时凭证随任务生命周期自动失效，全程可审计、可追溯

#### 备选方案
1. **静态密钥配置**：密钥直接配置在 Agent 环境变量或配置文件中
2. **统一密钥服务直接调用**：Agent 直接访问密钥服务自行拉取密钥
3. **Secret Broker 代理机制**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 静态密钥配置 | 实现简单，无额外组件 | 泄露风险极高，权限无法细粒度管控，泄露后无法快速撤销，无审计 |
| 直接调用密钥服务 | 无静态密钥，统一托管 | Agent 拥有拉取密钥的全权限，仍存在权限过大问题，无法按任务管控 |
| Secret Broker 机制 | 零静态密钥，按任务临时授权，权限最小化，全程可审计，泄露风险最低 | 架构复杂度略高，需要额外部署 Broker 组件 |

#### 影响范围
- 密钥与凭据管理
- 工具调用鉴权体系
- 基础设施安全平面密钥管理

### ADR-013 模型水印溯源方案
**状态**：生效中

#### 背景
核心商业模型是企业重要资产，存在被窃取、盗用的风险。需要水印技术实现模型盗用后的溯源能力，但不同水印方案的成本、隐蔽性、鲁棒性差异很大，需要分级适配不同场景。

#### 决策
采用**输出触发式水印 + 权重水印**分级方案：
1. **输出触发式水印**：在模型推理输出中嵌入不可见触发水印，成本低、无训练依赖，适用于所有对外服务的模型，可快速验证服务是否使用了己方模型
2. **权重水印**：将水印嵌入模型权重中，鲁棒性强、不易移除，适用于核心高价值模型，需要训练阶段嵌入
3. 普通模型仅用输出水印，核心高价值模型叠加权重水印，分级保护

#### 备选方案
1. **仅输出水印**：只在输出内容加水印，不修改模型
2. **仅权重水印**：只做模型权重水印，保护强度最高
3. **双方案分级适配**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 仅输出水印 | 实现简单，成本低，无训练侵入，适配所有模型 | 鲁棒性一般，可被一定程度移除，只能验证输出，无法证明模型权重盗用 |
| 仅权重水印 | 保护强度最高，嵌入模型内部，不易移除 | 成本高，需要训练阶段嵌入，无法适配第三方商用模型 |
| 双方案分级适配 | 兼顾成本与保护强度，不同价值模型匹配对应方案，性价比最优 | 方案体系复杂，需要针对不同模型选择对应方案 |

#### 影响范围
- 模型资产保护
- 知识产权保护体系
- 模型推理服务

## 5. 架构模式类决策
### ADR-014 Agent Mesh 架构模式
**状态**：生效中

#### 背景
企业内 Agent 数量与业务线持续增长，如果每个 Agent 各自建设安全能力，会出现重复建设、标准不一、策略分散、运营困难等问题；集中式网关模式又存在性能瓶颈、单点故障、侵入业务链路等问题。

#### 决策
采用 **Agent Mesh 架构模式**，将安全能力下沉到网格层：
1. 所有 Agent 实例旁挂统一的 Mesh Sidecar，安全能力由 Sidecar 统一提供，Agent 业务代码无感知
2. 安全策略、规则、配置由控制平面统一分发，所有 Sidecar 执行标准一致
3. Agent 间通信、工具调用、数据访问全部经过 Mesh 层管控，无旁路流量

#### 备选方案
1. **集中式安全网关**：所有流量经过统一网关做安全管控
2. **各 Agent 自建安全**：每个业务线自行实现安全能力
3. **Agent Mesh 分布式架构**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 集中式网关 | 部署简单，统一管理 | 性能瓶颈明显，单点故障影响全量业务，无法管控内部节点间流量 |
| 各 Agent 自建 | 业务灵活性高，适配性强 | 重复建设，标准不统一，安全水位参差不齐，运营成本极高 |
| Agent Mesh | 分布式无瓶颈，业务无侵入，统一策略管控，安全能力复用度最高 | 架构复杂度高，初期建设与运维有一定门槛 |

#### 影响范围
- 整体安全架构模式
- Agent 部署与运行架构
- 安全能力交付与运营模式

### ADR-015 影子模式（Shadow Agent）灰度机制
**状态**：生效中

#### 背景
安全规则与策略更新频繁，如果直接上线拦截，很容易出现误报影响业务；如果全量测试后再上线，又会滞后于攻击迭代速度。需要一套机制平衡规则迭代速度与业务稳定性。

#### 决策
采用 **Shadow Agent（影子模式）** 作为规则灰度验证机制：
1. 所有新安全规则先以影子模式旁路运行，只检测不拦截，全量日志记录检测结果
2. 运行一段时间后，统计误报率、漏报率，验证规则效果与业务影响
3. 验证通过的规则再逐步灰度上线拦截，验证不通过的回退优化
4. 所有规则必须经过影子模式验证，禁止直接全量上线拦截

#### 备选方案
1. **直接灰度上线**：规则编写完成后直接按流量灰度拦截
2. **线下全量测试后上线**：线下测试验证无误后再全量上线
3. **影子模式旁路验证 + 灰度上线**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 直接灰度上线 | 迭代速度快，流程简单 | 误报直接影响真实业务，存在业务故障风险 |
| 线下全量测试 | 不影响线上业务，风险低 | 测试场景与真实场景有差异，上线后仍可能出问题，迭代速度慢 |
| 影子模式验证 | 用真实流量验证规则，不影响业务，验证最准确，兼顾速度与稳定性 | 流程环节多，规则生效周期略长，需要旁路资源投入 |

#### 影响范围
- 安全规则迭代流程
- 运行时安全策略发布
- 安全运营与优化机制

### ADR-016 AI 防火墙前置部署模式
**状态**：生效中

#### 背景
面向公网的 Agent 服务会面临大量扫描、注入、爆破等批量攻击流量，如果全部放到运行时层检测，会占用大量检测资源，抬高成本，也增加后端防护压力。需要在接入层前置一道轻量化防护，清洗掉大部分基础攻击。

#### 决策
采用**前置 AI 防火墙 + 深度运行时检测**的双层防护架构：
1. 接入层部署 AI 防火墙，做轻量化的基础注入检测、爬虫防护、频控限流、黑名单拦截，清洗掉 80% 以上的低价值攻击流量
2. 运行时层做深度语义检测、工具管控、数据安全等精细化防护，处理经过清洗后的有效流量
3. 两层规则联动，防火墙发现的新型攻击特征同步给运行时层升级检测能力

#### 备选方案
1. **仅接入层防护**：所有安全检测都在接入层完成
2. **仅运行时层防护**：所有检测都在运行时完成，接入层只做传统 WAF
3. **双层协同防护架构**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 仅接入层防护 | 架构简单，性能好 | 防护深度不足，复杂攻击无法检测，核心工具调用、记忆等内部节点完全无防护 |
| 仅运行时层防护 | 防护深度足够，精细化程度高 | 大量无效攻击流量占用后端资源，成本高，DDoS 类攻击容易打穿后端 |
| 双层协同防护 | 兼顾性能成本与防护深度，前置清洗降本，后端深度防护保安全，协同联动效果最优 | 两套规则体系需要联动维护，架构复杂度略高 |

#### 影响范围
- 接入层安全架构

- 威胁检测与规则迭代体系

### ADR-017 策略即代码（Policy as Code）
**状态**：生效中

#### 背景
安全策略如果通过界面配置、人工维护，会存在版本混乱、无法审计、变更不可追溯、无法自动化发布等问题，也难以融入 DevOps 流程，跟不上业务迭代速度。

#### 决策
全面推行 **策略即代码（Policy as Code）** 机制：
1. 所有安全策略、规则、配置全部以代码形式管理，纳入 Git 版本控制系统
2. 策略变更走代码评审流程，经过审批后通过 CI/CD 流水线自动发布
3. 支持灰度发布、一键回滚、变更审计，所有变更可追溯、可验证、可回退

#### 备选方案
1. **可视化界面配置**：通过管理后台界面化配置策略
2. **人工线下变更**：运维人员手动登录服务器修改配置
3. **策略即代码 + 流水线发布**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 界面化配置 | 操作直观，门槛低 | 版本管理困难，变更无审计，无法自动化，容易出现配置漂移 |
| 人工线下变更 | 灵活性最高，无系统依赖 | 风险极高，无审核无审计，容易出现人为失误，完全不可控 |
| 策略即代码 | 版本可控、变更可审、自动化发布、支持灰度回滚，融入 DevOps 流程，符合企业级管控要求 | 有一定学习成本，对团队工程化能力有要求 |

#### 影响范围
- 全量安全策略管理
- 控制平面配置发布
- DevSecOps 流程融合

## 6. 基础设施类决策
### ADR-018 机密计算分级落地方案
**状态**：生效中

#### 背景
核心模型与高敏感数据对安全等级要求极高，明文计算始终存在内存泄露、侧信道攻击的风险。但机密计算目前仍存在性能损耗大、生态不完善、成本高的问题，全量部署性价比极低。

#### 决策
采用**分级落地、场景适配**的机密计算方案：
1. **L1 基础级**：普通场景采用传输加密 + 存储加密，满足基础安全要求
2. **L2 增强级**：核心推理场景采用 CPU TEE 可信执行环境，保护推理过程中的数据与模型安全
3. **L3 旗舰级**：极高价值模型与超敏感数据场景采用 GPU 机密计算，实现全链路密态计算
4. 按业务场景风险等级匹配对应方案，不盲目全量上密态计算

#### 备选方案
1. **全量明文计算**：不使用机密计算，仅靠传统软件安全防护
2. **全量密态计算**：所有场景都部署机密计算环境
3. **分级落地方案**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 全量明文计算 | 成本最低，性能最好，生态最完善 | 安全强度不足，核心资产存在内存泄露、侧信道攻击风险 |
| 全量密态计算 | 安全等级最高，全链路数据可用不可见 | 成本极高，性能损耗大，生态不完善，很多场景无法适配 |
| 分级落地方案 | 安全与成本平衡，不同场景匹配对应强度，整体投入产出比最优 | 架构复杂度高，需要精准的场景分级与适配方案 |

#### 影响范围
- 基础设施安全平面机密计算底座
- 核心模型与高敏数据场景部署
- 整体安全成本规划

### ADR-019 多区域部署架构
**状态**：生效中

#### 背景
全球化业务与合规要求下，AI Agent 服务需要多区域部署，满足数据本地化、低延迟访问、容灾备份等需求。但多区域部署会带来身份同步、策略一致、数据隔离、运维复杂等挑战。

#### 决策
采用**中心管控 + 区域执行**的多区域主从架构：
1. **控制平面中心化**：全局统一的身份、策略、配置、运营中心部署在主区域，向所有区域同步策略与配置
2. **数据平面区域化**：每个区域独立部署业务与安全执行节点，数据本地化存储，满足区域合规要求
3. **容灾多活机制**：核心业务跨区域多活，单区域故障自动切换，保障业务连续性
4. 跨区域访问必须经过身份校验与合规审核，禁止违规跨境数据传输

#### 备选方案
1. **单区域集中部署**：所有服务集中部署在一个区域，全球访问
2. **多区域完全独立**：每个区域独立部署全套体系，互不连通
3. **中心管控 + 区域执行架构**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 单区域集中部署 | 架构简单，运维成本低，数据统一 | 跨区域访问延迟高，无法满足数据本地化合规要求，存在单点故障风险 |
| 多区域完全独立 | 区域隔离性好，合规性强，故障不扩散 | 运维成本翻倍，策略不统一，数据割裂，无法全局运营 |
| 中心管控+区域执行 | 兼顾统一管控与区域合规，策略一致，数据本地化，故障隔离，整体平衡最优 | 架构复杂度高，跨区域同步与一致性保障有技术难度 |

#### 影响范围
- 整体部署架构
- 跨区域合规与数据安全
- 业务高可用与容灾体系

### ADR-020 OpenTelemetry 统一可观测标准
**状态**：生效中

#### 背景
AI Agent 架构涉及组件多、技术栈杂，如果各组件各自实现可观测埋点，会出现数据标准不统一、无法关联、运维成本高、排障困难等问题，需要统一的可观测标准。

#### 决策
全链路统一采用 **OpenTelemetry（OTel）作为唯一可观测标准**：
1. 所有业务、AI、安全、基础设施组件全部基于 OTel SDK 埋点，指标、日志、链路统一规范
2. 全局 Trace ID 贯穿全链路，所有数据可通过 Trace ID 关联
3. 采集层统一使用 OTel Collector 做数据处理与转发，后端存储可灵活替换，避免厂商锁定

#### 备选方案
1. **各组件自研埋点**：每个组件自己实现监控埋点，各自对接监控系统
2. **绑定某厂商可观测方案**：全套使用某云厂商或商业厂商的可观测产品
3. **OpenTelemetry 统一标准**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 各组件自研埋点 | 灵活性高，无额外依赖 | 标准不统一，数据无法关联，运维成本高，重复建设 |
| 绑定厂商方案 | 集成简单，一站式交付 | 厂商锁定严重，迁移成本高，多云/私有化场景无法适配 |
| OTel 统一标准 | 开放标准、厂商中立、生态完善、全链路数据可关联、长期可扩展 | 初期建设有一定集成工作量，需要统一规范约束 |

#### 影响范围
- 全链路可观测体系
- 所有组件埋点规范
- 运维排障与安全运营数据基础

- Vol.3 三大横切能力 · 全链路可观测

### ADR-021 AI 供应链安全管控体系
**状态**：生效中

#### 背景
AI 技术栈依赖大量开源组件、第三方模型、插件、数据集，供应链链路长、组件多、风险隐蔽，传统软件供应链安全体系无法覆盖 AI 专属组件，供应链攻击已成为 AI 安全的核心风险之一。

#### 决策
建立**全链路 AI 供应链安全管控体系**，覆盖 AI 全组件生命周期：
1. **AI-BOM 资产台账**：建立 AI 物料清单，全面梳理所有模型、数据集、框架、插件、依赖组件，形成完整资产台账
2. **准入管控**：所有第三方 AI 组件上线前必须经过安全评审与漏洞扫描，风险超标的禁止接入
3. **持续监测**：持续跟踪全量组件的漏洞、风险、舆情，发现风险及时预警处置
4. **多供应商备选**：核心组件至少保留一个备选供应商，避免单一供应链依赖风险

#### 备选方案
1. **无专项管控**：沿用传统软件供应链安全体系，不做 AI 专项管控
2. **仅漏洞扫描**：对开源组件做基础漏洞扫描，无全链路管控
3. **全链路 AI 供应链管控**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 无专项管控 | 无额外成本，业务不受影响 | AI 专属供应链风险完全暴露，模型投毒、插件后门等风险无法防范 |
| 仅漏洞扫描 | 有基础防护，成本适中 | 覆盖不全，无法应对投毒、后门等 AI 专属供应链风险，属于点状防护 |
| 全链路管控体系 | 覆盖 AI 全组件全生命周期，系统性管控供应链风险，防护最完整 | 建设成本较高，需要配套流程与组织机制，初期工作量大 |

#### 影响范围
- AI 全组件供应链安全
- 第三方组件准入流程
- 基础设施安全平面供应链管控

#### 关联引用
- Vol.7 威胁建模体系 · 供应链攻击类威胁

## 7. 治理与运营类决策
### ADR-022 分级人工审批机制
**状态**：生效中

#### 背景
Agent 执行高危操作需要人工兜底保障安全，但如果所有操作都走人工审批，效率极低，完全丧失 AI 的自动化价值；如果都不审批，又存在严重安全风险。需要在安全与效率之间找到平衡。

#### 决策
采用**按风险等级分级审批**机制：
1. **低风险操作**：自动执行，无需审批，全程审计留痕
2. **中风险操作**：执行后异步通知责任人，异常可回溯撤销
3. **高风险操作**：执行前必须人工审批，多人复核通过后方可执行
4. **极高风险操作**：强制双人审批 + 全程录屏审计
风险等级基于操作类型、影响范围、数据敏感度、身份信任度等维度自动判定。

#### 备选方案
1. **全量人工审批**：所有操作都必须人工审批后执行
2. **全量自动执行**：所有操作都自动执行，仅事后审计
3. **分级审批机制**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 全量人工审批 | 安全等级最高，风险最可控 | 效率极低，完全抵消 AI 自动化价值，业务无法接受 |
| 全量自动执行 | 效率最高，自动化程度最高 | 风险不可控，误操作与恶意操作都会直接造成损失 |
| 分级审批机制 | 兼顾安全与效率，高风险严管控，低风险保效率，整体投入产出比最优 | 风险分级规则设计复杂，需要持续优化调优 |

#### 影响范围
- 高危操作管控流程
- 工具网关执行逻辑
- 安全运营审批体系

#### 关联引用
- Vol.3 运行时安全平面
- Vol.10 运营与治理体系

### ADR-023 决策可解释性框架
**状态**：生效中

#### 背景
AI 决策黑盒特性导致合规审计、问题排查、责任认定都非常困难，监管对 AI 可解释性的要求也日益严格。需要构建体系化的可解释能力，满足合规、审计、运维的多重需求。

#### 决策
构建**全链路决策可解释性框架**，覆盖 Agent 决策全流程：
1. **思考链留存**：完整保存 Agent 的推理过程、思考步骤、决策依据，所有决策可追溯推导逻辑
2. **决策要素结构化**：将影响决策的关键因素、权限校验结果、风险评估结果结构化记录
3. **结果可解释输出**：重要决策自动生成自然语言解释，说明决策原因与依据
4. 所有解释信息与操作日志绑定，支持审计查询与合规导出

#### 备选方案
1. **无专项可解释性**：仅保留输入输出，不保存中间决策过程
2. **仅留存思考链**：保存原始思考链，不做结构化处理
3. **全链路可解释性框架**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 无专项可解释性 | 实现简单，存储成本低 | 完全黑盒，无法审计、无法排障、无法满足合规要求 |
| 仅留存思考链 | 有基本追溯能力，实现成本适中 | 非结构化，检索分析困难，无法满足自动化审计与合规要求 |
| 全链路可解释框架 | 满足合规、审计、排障、问责多维度需求，体系化解决黑盒问题 | 存储成本较高，框架建设有一定复杂度 |

#### 影响范围
- 算法合规治理
- 安全审计与追溯
- 故障排查与问题定位

### ADR-024 统一安全治理中心架构
**状态**：生效中

#### 背景
AI 安全能力分散在身份、运行时、数据、基建等多个模块，如果各自独立运营，会出现告警分散、数据不通、运营效率低、无法全局研判等问题，也难以融入企业现有安全运营体系。

#### 决策
构建**统一 AI 安全治理中心**，作为所有 AI 安全能力的运营中枢：
1. **统一接入**：所有安全组件的告警、日志、事件统一接入治理中心，集中呈现
2. **统一运营**：威胁检测、事件响应、合规审计、风险度量全部在中心完成，一体化运营
3. **联动处置**：发现风险后可联动各安全组件执行处置，形成检测-响应闭环
4. **对接现有 SOC**：治理中心与企业现有 SOC 打通，AI 安全事件纳入企业整体安全运营体系

#### 备选方案
1. **各组件独立运营**：每个安全组件自己的控制台分别运营
2. **完全复用现有 SOC**：所有数据直接灌进传统 SOC，不建专项治理中心
3. **统一治理中心 + SOC 对接**：即最终选定方案

#### 利弊分析
| 方案 | 优势 | 劣势 |
|------|------|------|
| 各组件独立运营 | 无额外建设成本，随用随建 | 数据分散，运营效率极低，无法全局研判，形成安全孤岛 |
| 完全复用现有 SOC | 复用现有运营体系，人员习惯不变 | 传统 SOC 无法适配 AI 原生威胁的检测与运营逻辑，效果差 |
| 统一治理中心+SOC对接 | 兼顾 AI 专项运营能力与企业整体安全体系的打通，运营效率最高，体系最完整 | 需要专项建设治理中心，有一定的建设与对接成本 |

#### 影响范围
- 安全运营体系
- 全量安全数据汇聚与分析
- 事件响应与处置闭环
