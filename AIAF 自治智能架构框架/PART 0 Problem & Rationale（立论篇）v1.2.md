# PART 0 Problem & Rationale（立论篇）
## Autonomous Intelligence Foundations (AIF)
> 本篇为 AIAF 自治智能架构框架的**规范性基础**，统一定义框架的目的、范围、核心概念、元模型、分类体系、架构原则与一致性要求，适用于框架所有其他组成部分。

本篇回答四个根本性问题：
- AIAF 为什么存在？
- AIAF 解决哪些核心问题？
- AIAF 由哪些部分组成？
- AIAF 遵循哪些顶层设计准则？

本篇所有内容均为规范性条款，是所有 AIAF 兼容架构实现的统一基准。

## 第1章 引言

### 1.1 目的
AIAF（自治智能架构框架）是一套厂商中立、行业通用的架构标准体系，用于指导自治智能系统的设计、治理、运营与持续演进。

框架提供标准化的术语体系、结构化的开发方法、分层解耦的参考架构与量化可落地的评估准则，帮助企业在可控、安全、可信、可持续演进的前提下，规模化建设企业级自治智能系统。框架不绑定任何特定模型、技术栈与厂商产品。

### 1.2 目标
AIAF 旨在达成以下核心目标：
1. 建立自治智能系统统一的**架构语言**
2. 定义覆盖全生命周期的标准化**架构开发方法**
3. 提供分层组件化、接口标准化的完整**参考架构**
4. 构建内嵌式、全链路的**治理与安全体系**
5. 输出量化的**评估体系**与成熟度模型
6. 维护可复用的**参考模式库**与场景化落地蓝图
7. 制定正式的**一致性等级**与认证标准
8. 支撑跨组织协作与行业标准对齐

### 1.3 适用范围
AIAF 适用于所有具备自治属性的智能系统的全生命周期建设，典型场景包括：
- ✅ 多智能体平台与智能体运行时基础设施
- 自治 AI 应用与数字劳动力体系
- AI 原生应用与 AI 原生云平台
- 自治机器人集群与工业自治控制系统
- 自治安全运营中心（SOC）与智能运维（AIOps）体系
- 企业级自治能力体系与自治企业演进规划

### 1.4 目标受众
本框架主要面向以下角色与组织：
- 企业架构师与首席架构师
- AI 架构师与系统架构师
- 安全架构师与治理架构师
- 平台架构师与基础设施架构师
- 技术负责人与工程管理团队
- 标准化组织与行业联盟
- 研究机构与学术社区
- 咨询服务机构与评估认证方

### 1.5 非适用范围
以下领域明确不在 AIAF 的覆盖范围内：
- ❌ 模型训练算法与大模型微调方法论
- ❌ 提示工程与单模型调优实现细节
- ❌ GPU 调度与底层硬件加速优化
- ❌ 编程 SDK 与智能体开发框架
- ❌ 算法精度基准与模型效果评测
- ❌ 不具备自主决策能力的传统 MIS、ERP、CRM 与静态应用

### 1.6 一致性说明
AIAF 定义四级一致性等级，任何声明符合 AIAF 标准的实现，必须满足对应等级的全部强制要求。
- **基础级（Core）**：覆盖核心架构域与强制治理安全管控的基线标准
- **进阶级（Advanced）**：完整覆盖全部架构域，具备完整运行、治理与学习能力
- **企业级（Enterprise）**：支持企业级多租户、跨域协同与集中化治理
- **参考级（Reference）**：完全对齐标准参考架构，可用于官方认证的基准实现

详细一致性标准见第8章。

### 1.7 与现有标准的关系
AIAF 并非替代现有的企业架构、治理与安全标准，而是针对自治智能领域的专项深化与工程化落地，与主流框架保持兼容互补。

| 标准/框架 | 领域 | 与 AIAF 的关系 |
|-----------|------|----------------|
| TOGAF® | 通用企业架构 | AIAF 继承企业架构方法论，扩展自治智能专属架构域 |
| SABSA® | 业务驱动安全架构 | AIAF 对齐风险驱动的安全设计思想，扩展至 AI 原生威胁场景 |
| COBIT® | IT 治理与管控 | AIAF 对齐 IT 治理原则，扩展至自治系统治理体系 |
| ITIL® | IT 服务管理 | AIAF 对齐运营最佳实践，延伸至智能体运营（AgentOps）场景 |
| ISO/IEC 42001 | AI 管理体系 | AIAF 为管理体系标准提供架构落地层面的技术支撑 |
| NIST AI RMF | AI 风险管理 | AIAF 将风险管理要求转化为可落地的架构管控措施 |
| **AIAF** | **自治智能架构** | **面向自治系统的专项架构框架** |

| 层级 | 对应部分 | 核心内容 |

## 第2章 概念基础

### 2.1 范式演进
软件系统的发展经历了多轮范式跃迁，每一次跃迁都由系统核心属性的变化驱动，每一代系统形态都对应着一代架构方法论。

```
程序化自动化
    │
    ▼
规则化应用
    │
    ▼
分布式系统
    │
    ▼
云原生系统
    │
    ▼
智能辅助系统
    │
    ▼
智能体系统
    │
    ▼
自治系统
    │
    ▼
群体自治系统
```

- **程序化与规则化系统**：逻辑完全由人类预设，行为确定可预测
- **分布式与云原生系统**：节点动态伸缩、服务松耦合，核心是服务治理与资源编排
- **智能辅助系统**：具备感知识别能力，输出决策建议，最终执行由人类完成
- **智能体系统**：具备单任务端到端执行能力，可在预设规则下完成简单闭环
- **自治系统**：目标驱动、动态规划、环境自适应、持续学习，可在边界内应对未知场景
- **群体自治系统**：多自治体协同形成群体智能，具备涌现性、自组织特征，可完成复杂系统性任务

当前产业正处于从「智能辅助系统」向「自治系统」跃迁的关键节点。系统核心属性从「确定性」转向「自主性」，这一底层变化动摇了传统架构方法论的基础假设，催生了对全新架构框架的需求。

### 2.2 自治系统的核心特征
AIAF 定义自治系统的五大本质特征，框架内所有架构设计均围绕这五大属性展开。

| 特征 | 定义 |
|------|------|
| **目标导向** | 系统行为由使命与目标驱动，而非预设固定流程；系统在约束边界内自主选择路径达成目标 |
| **环境自适应** | 动态感知环境变化，自主调整执行策略与规划路径，无需人工重新配置 |
| **持续学习** | 运行过程中持续积累经验，优化知识、策略与能力，表现随时间持续提升 |
| **自我约束** | 在内置的政策、安全、伦理边界内运行，具备内置合规校验能力，无需外部实时人工监督 |
| **持续演进** | 生命周期内能力、架构、机制持续进化，运行后的系统与上线时不再完全等同 |

### 2.3 架构挑战
传统架构方法论面向确定性系统设计。对于具备上述五大特征的自治系统，存在九大核心架构挑战，无法通过简单扩展现有框架解决。

#### AC-01 架构对象挑战
传统企业架构以应用、数据、技术等静态组件为核心，而自治系统最核心的使命、目标、能力、世界模型、智能体、演进等要素，在传统体系中没有对应定义与设计方法。

#### AC-02 生命周期挑战
传统软件遵循线性交付生命周期，而自治系统遵循「运行-反思-学习-演进」的闭环生命周期，上线只是能力演进的起点。传统项目管理与变更管控体系无法适配。

#### AC-03 治理体系挑战
传统 IT 治理以「事前审批、事后审计」为核心模式，自治系统高频自主决策与人工审批流程之间存在速度与颗粒度的错位，容易陷入「管死就失去自治价值，放开就出现风险失控」的两难。

#### AC-04 运行时架构挑战
传统运行时聚焦请求调度与资源管理，而自治系统需要目标管理、动态规划、独立安全控制器、反思引擎等专属运行时组件，传统运行时架构完全缺失这些核心能力。

#### AC-05 安全范式挑战
传统安全以「边界防护、访问控制」为核心，而自治系统的风险大量是内生的——提示注入、记忆污染、工具滥用、行为漂移、群体合谋等，无法仅靠边界防御解决。

#### AC-06 可观测性挑战
传统可观测性回答「系统是否正常运行」，而自治系统需要观测决策质量、目标对齐度、能力退化、行为合规性，这些维度在传统监控体系中完全缺失。

#### AC-07 信任体系挑战
信任常被视为安全的子集，但实际上信任是独立的一级对象，涉及可解释性、可问责性、可预测性、价值对齐等多重维度。缺少体系化的信任构建机制，是自治系统进入核心业务的最大非技术瓶颈。

#### AC-08 经济价值挑战
行业缺少标准化的成本-收益-风险权衡方法，企业难以判断：什么时候值得做自治？什么时候必须人工？什么时候采用人机混合模式？容易陷入「为技术而技术」的盲目投入。

#### AC-09 系统演进挑战
传统语境中的「学习」仅限于模型与数据优化，而完整的系统演进涵盖知识、能力、策略、流程、架构、组织、治理等全维度。现有体系缺少完整的演进管控方法论。

### 2.4 架构需求
为应对上述挑战，AIAF 定义以下强制性架构需求，所有参考架构与实现均必须满足。

| 编号 | 需求名称 | 需求说明 |
|------|----------|----------|
| AR-01 | 目标驱动架构 | 架构必须围绕层级化目标体系构建，支持从使命到执行的全链路追溯 |
| AR-02 | 运行时原生控制 | 架构必须包含独立于业务逻辑的运行时控制平面 |
| AR-03 | 持续学习闭环 | 架构必须原生支持「执行-反思-学习-发布」的完整闭环 |
| AR-04 | 治理内嵌 | 治理管控必须内置于执行全链路，而非作为外部层叠加 |
| AR-05 | 原生信任机制 | 架构必须原生支持可追溯、可问责、可解释、可预测的信任能力 |
| AR-06 | 全栈可观测 | 可观测性必须覆盖决策、执行、学习全链路，而非仅基础设施 |
| AR-07 | 独立安全护栏 | 必须设置独立的安全控制器，具备最高干预优先级 |
| AR-08 | 分级人机协同 | 架构必须支持分级人工介入，具备清晰的人机权责边界 |
| AR-09 | 可控式演进 | 所有学习与演进活动必须可验证、可灰度、可回滚 |

## 第3章 框架总览

### 3.1 框架组成
AIAF 是由九大核心模块构成的一体化架构框架体系。

```
                        AIAF 框架
                           │
    ┌──────────┬───────────┼───────────┬──────────┐
    │          │           │           │          │
架构语言    元模型     架构域      架构视图    开发方法
    │          │           │           │          │
    └──────────┴───────────┼───────────┴──────────┘
                           │
              ┌────────────┴────────────┐
              │                         │
          治理体系                  评估体系
              │                         │
              └────────────┬────────────┘
                           │
                      参考架构
                           │
                      参考实现
```

| 模块名称 | 模块说明 |
|----------|----------|
| **架构语言** | 整个框架统一的术语、定义与语义体系 |
| **架构元模型** | 核心实体、属性与关系，构成框架的语义基础 |
| **架构域** | 横向划分的九大架构域，覆盖完整能力栈 |
| **架构视图** | 面向不同利益相关者的角色化架构呈现 |
| **架构开发方法（AIAM）** | 十阶段全生命周期架构开发方法论 |
| **治理框架** | 覆盖政策、合规、风险、伦理的全链路治理体系 |
| **安全框架** | 面向 AI 原生威胁的纵深防御安全体系 |
| **评估体系（AIAA）** | 多维度评估方法与一致性认证标准 |
| **参考架构（AIRA）** | 标准化分层参考架构与组件规范 |
| **参考实现（AIRI）** | 典型行业与场景的落地化架构蓝图 |

### 3.2 生命周期对齐
AIAF 各模块对应自治系统建设的全生命周期：
1. **规划阶段**：运用架构视图、元模型与分类体系完成顶层设计
2. **建设阶段**：遵循 AIAM 开发方法与参考架构推进落地
3. **运行阶段**：应用治理、安全与可观测能力保障日常运营
4. **演进阶段**：依托学习框架与成熟度模型实现持续升级
5. **评估阶段**：通过评估体系开展周期评估与一致性认证

### 3.3 组件间关系
- **元模型**是所有组件共享的语义基础
- **架构原则**是所有组件遵循的顶层准则
- **开发方法**贯穿所有架构域的建设过程
- **治理与安全**是嵌入所有层级的横切能力
- **评估体系**为其他所有组件提供验证反馈
- **参考实现**是参考架构的具体场景化实例

## 第4章 架构元模型

AIAF 元模型定义自治智能架构的核心实体、属性与关系，是整个框架的语义基础，保障所有架构域、方法与视图的一致性。

### 4.1 核心实体

| 实体名称 | 定义 |
|----------|------|
| **使命（Mission）** | 系统的顶层定位与价值主张，具备长期稳定性 |
| **目标（Goal）** | 由使命拆解的层级化、可度量目标，包含成功指标与约束条件 |
| **能力（Capability）** | 支撑目标达成的功能能力，具备明确的成熟度等级 |
| **知识（Knowledge）** | 领域本体、世界模型、记忆、经验等结构化信息 |
| **智能体（Agent）** | 承载能力、执行任务、达成目标的自治执行实体 |
| **运行时（Runtime）** | 承载、调度、管控智能体运行的执行环境 |
| **动作（Action）** | 智能体执行的具体操作步骤，包括工具调用与外部交互 |
| **结果（Outcome）** | 动作执行的产出，反馈至系统用于效果评估 |
| **政策（Policy）** | 约束系统行为的正式规则，涵盖合规、安全、伦理 |
| **风险（Risk）** | 潜在负面事件，具备发生概率与影响程度两个维度 |
| **管控（Control）** | 为落实政策、缓释风险而实施的 mitigation 措施 |
| **信任（Trust）** | 由可解释、可问责、可预测、价值对齐共同构成的横切属性 |
| **学习（Learning）** | 基于结果更新知识、能力与策略的过程 |
| **演进（Evolution）** | 系统整体能力、架构与运营模式的长期提升 |

### 4.2 核心实体关系
核心实体之间遵循以下规范性关系：
1. 一个**使命**拆解为一个或多个**目标**
2. 一个**目标**由一项或多项**能力**支撑
3. 一个**智能体**承载一项或多项**能力**
4. **知识**为智能体的推理与决策提供支撑
5. **运行时**编排智能体执行并管控动作
6. **动作**产生**结果**，结果反向用于目标达成度评估
7. **政策**定义对目标、智能体、动作的约束边界
8. **管控**落地政策要求并缓释风险
9. **学习**处理结果数据，反向更新知识、能力与政策
10. **演进**推动整体架构与能力体系的长期变革
11. **信任**是治理、安全、可观测、问责机制共同作用的涌现属性

所有声明符合 AIAF 标准的实现，其核心对象与关系必须能够映射至本元模型定义。

## 第5章 架构分类体系

AIAF 建立覆盖各核心领域的统一分类标准，保障框架内所有模块的分类口径一致。

### 5.1 架构域分类
九大横向架构域构成 AIAF 的核心结构：
1. 业务架构
2. 目标架构
3. 知识架构
4. 智能架构
5. 运行时架构
6. 治理架构
7. 安全架构
8. 学习架构
9. 运营架构

### 5.2 能力分类
自治能力自下而上分为三级：
- **基础层**：感知理解、知识检索、工具调用、基础执行
- **核心层**：推理决策、任务规划、异常处置、协同协作
- **高阶层**：自主学习、能力演进、群体智能、环境自适应

### 5.3 治理域分类
七大治理域构成完整治理体系：
1. 政策治理
2. 合规治理
3. 风险管理
4. 伦理治理

## 第6章 架构原则

架构原则是贯穿 AIAF 整个框架的顶层规范性准则，所有架构设计、方法与实现均必须对齐。

每条原则采用统一结构描述：核心意图、设计依据、规范性要求、落地启示。

---

### AP-01 使命优先
**核心意图**：所有架构决策最终均可追溯至业务使命与价值。

**设计依据**：自治系统天然具备复杂度，若不以使命为最终锚点，容易陷入技术自嗨与价值偏离。

**规范性要求**：
- 所有能力与组件必须具备可追溯的业务使命与目标映射
- 架构权衡必须优先保障使命价值，而非技术先进性

**落地启示**：
- 架构优劣以使命达成度为首要评判标准
- 对使命价值无贡献的能力应予以裁剪

---

### AP-02 目标驱动
**核心意图**：系统运行以目标体系为核心牵引，而非固定流程。

**设计依据**：自治系统与传统系统最本质的区别，就是目标驱动的运行模式，目标是所有决策与执行的源头。

**规范性要求**：
- 架构必须具备完整的层级化目标体系
- 所有执行动作必须可追溯至对应目标
- 目标约束具备最高执行优先级

**落地启示**：
- 规划与执行围绕目标达成动态调整
- 突破目标边界的行为即时触发干预

---

### AP-03 运行时原生
**核心意图**：运行时是自治系统运行的核心载体，所有能力围绕运行时层构建。

**设计依据**：与传统应用逻辑在设计时固化不同，自治系统的能力在运行时真正落地，运行时架构质量直接决定系统可控性。

**规范性要求**：
- 运行时控制器必须独立部署，具备高可用保障
- 治理、安全、可观测管控必须原生嵌入运行时
- 运行时组件必须支持配置热更新

**落地启示**：
- 运行时是所有一致性等级的必备核心组件
- 业务逻辑不得绕过运行时管控机制

---

### AP-04 人类治理
**核心意图**：人类始终保留最终决策权、监督权与紧急接管权。

**设计依据**：自治等级提升不等于去掉人类，而是将人类从操作层提升到治理层，人类始终承担最终责任。

**规范性要求**：
- 架构必须支持分级人工介入机制
- 高风险决策必须保留人类最终审批权
- 紧急停止与人工接管能力必须始终可用

**落地启示**：
- 自治程度受治理要求约束，存在上限
- 人机权责边界必须清晰划分

---

### AP-05 设计原生信任
**核心意图**：信任是一级架构属性，由设计原生构建，而非事后补充。

**设计依据**：信任是自治系统进入核心业务的核心瓶颈，仅靠安全无法构建信任，必须同时具备可解释、可问责、可预测与价值对齐。

**规范性要求**：
- 核心决策必须可追溯、可解释
- 所有动作必须具备清晰的责任归属
- 系统行为在边界内必须具备可预测性

**落地启示**：
- 信任机制贯穿所有架构层级
- 核心业务场景不接受黑箱式决策

---

### AP-06 设计原生治理
**核心意图**：治理能力由设计内嵌，而非事后叠加。

**设计依据**：事后叠加的治理无法匹配自治决策的速度与颗粒度，只有内嵌式治理才能兼顾管控与效率。

**规范性要求**：
- 治理检查点必须嵌入执行链路的所有关键节点
- 治理规则必须由系统自动化强制执行
- 治理必须与架构设计同步，而非上线后补充

**落地启示**：
- 治理不是独立模块，而是横切能力
- 治理规则与能力升级同步更新

---

### AP-07 设计原生安全
**核心意图**：安全是架构内生属性，具备独立护栏机制。

**设计依据**：自治系统的内生风险无法靠边界防御解决，独立的、最高优先级的安全控制器是防止失控的终极保障。

**规范性要求**：
- 必须部署独立的运行时安全控制器
- 安全控制器具备最高干预优先级
- 必须具备分级熔断与降级机制

**落地启示**：
- 安全逻辑与业务逻辑解耦
- 业务逻辑无法关闭或绕过安全规则

---

### AP-08 学习能力原生
**核心意图**：学习能力是自治系统的原生属性，而非可选功能。

**设计依据**：在运行中成长，是自治系统区别于传统系统的本质特征。

**规范性要求**：
- 架构必须内置闭环学习机制
- 所有学习更新必须经过验证与灰度发布
- 所有学习更新必须具备回滚能力

**落地启示**：
- 学习过程受治理管控、风险可控
- 高风险场景不允许无监督全自动学习

---

### AP-09 设计原生可观测
**核心意图**：可观测性覆盖决策-执行-学习全链路，而非仅基础设施层面。

**设计依据**：没有全链路可观测，自治系统就会变成黑箱，治理、安全、信任都无从谈起。

**规范性要求**：
- 决策、执行、学习过程必须全部可观测
- 核心决策必须支持端到端全链路追溯
- 关键状态变更必须可审计、防篡改

**落地启示**：
- 可观测性从基础设施向上延伸至业务决策层
- 审计数据留存必须满足合规要求

---

### AP-10 演进优先
**核心意图**：架构设计以支持长期持续演进为核心目标，而非仅满足当前需求。

**设计依据**：自治系统在全生命周期内持续进化，不能演进的架构会快速过时。

**规范性要求**：
- 架构必须支持分层独立升级
- 必须系统化识别与管理架构债务
- 必须定义阶梯式的成熟度升级路径

**落地启示**：
- 架构稳定性与演进能力同等重要
- 短期收益与长期演进能力相权衡

## 第7章 架构视图

架构视图面向不同角色提供针对性的系统视角，回应不同利益相关者的关注点。每个视图聚焦特定架构域，屏蔽无关细节。

| 视图名称 | 主要受众 | 核心内容 | 覆盖架构域 |
|----------|----------|----------|------------|
| **使命视图** | 高管、业务负责人 | 使命、价值、目标、成功指标、风险偏好 | 业务、目标 |
| **能力视图** | 产品负责人、能力架构师 | 能力地图、差距分析、演进路线 | 智能、学习 |
| **运行时视图** | 系统架构师、研发团队 | 运行时组件、控制流、状态机、异常处理 | 运行时、运营 |
| **知识视图** | 知识工程师、领域专家 | 本体、世界模型、记忆体系、知识生命周期 | 知识 |
| **治理视图** | 合规官、风险经理 | 治理规则、控制点、权责矩阵、审计机制 | 治理 |
| **安全视图** | 安全架构师、安全运营团队 | 威胁模型、防护层级、身份信任、事件响应 | 安全 |
| **信任视图** | 决策者、审计方 | 可解释性、可问责性、可追溯性、价值对齐 | 治理、安全 |
| **学习视图** | AI 工程师、优化团队 | 学习闭环、验证机制、灰度发布、回滚 | 学习 |
| **演进视图** | 架构负责人、技术高管 | 成熟度路线图、架构债务、升级路径、组织演进 | 全架构域 |

所有声明符合 AIAF 标准的实现，应当至少提供使命视图、运行时视图、治理视图与安全视图。

## 第8章 一致性规范

本章定义 AIAF 的规范性用语、一致性等级与评估标准，任何声明符合 AIAF 的实现均必须满足所声明等级的全部强制要求。

### 8.1 规范性用语定义
AIAF 采用 RFC 2119 标准用语定义要求等级：

| 用语 | 含义 |
|------|------|
| **必须（MUST）** | 强制性要求，是达成一致性的必要条件 |
| **严禁（MUST NOT）** | 明确禁止的行为，违反即丧失一致性 |
| **应当（SHOULD）** | 推荐实践，强烈建议执行，若非充分理由不应偏离 |
| **不推荐（SHOULD NOT）** | 不建议采用的做法，除非有充分合理性论证 |
| **可以（MAY）** | 可选能力，允许但不强制要求 |

### 8.2 一致性等级
AIAF 定义四级递进的一致性等级，高等级包含低等级的全部要求。

#### 基础级（Core Conformance）
**适用场景**：单场景试点系统、部门级应用

**强制要求**：
- 必须覆盖业务、目标、运行时、治理、安全、运营六大核心架构域
- 必须满足核心域所有「必须」级要求
- 必须落实独立安全控制器与核心治理检查点
- 必须具备基础可观测与审计能力
- 必须定义清晰的人机权责边界

#### 进阶级（Advanced Conformance）
**适用场景**：多场景整合系统、企业级平台

**强制要求**：
- 必须完整覆盖全部九大架构域
- 必须满足全框架所有「必须」级要求
- 必须实现完整的闭环学习机制，配套验证与灰度发布
- 必须具备全链路可观测与可追溯能力
- 必须具备标准化的架构开发与治理流程

#### 企业级（Enterprise Conformance）
**适用场景**：企业级统一平台、多租户系统、跨域协同体系

**强制要求**：
- 必须支持多租户隔离与统一治理控制平面
- 必须实现企业级知识共享与能力复用机制
- 必须具备集中化的身份、安全与治理体系
- 必须支持多智能体群体协作与群体行为管控
- 必须具备成熟的企业级运营与持续演进机制

#### 参考级（Reference Conformance）
**适用场景**：官方认证参考实现、行业标杆方案

**强制要求**：
- 必须完整满足企业级一致性的全部要求
- 必须完全对齐 AIAF 标准参考架构
- 必须通过官方第三方评估与认证
- 必须具备可公开验证的落地案例与效果数据
- 必须向社区回馈最佳实践

### 8.3 一致性评估
- **内部自评**：企业可对照标准开展内部自评估
- **第三方认证**：正式 AIAF 认证需由授权认证机构开展评估
- **有效期**：认证有效期为 12 个月，需每年复评
- **降级机制**：无法持续维持一致性要求时，将予以等级调整或撤销认证

详细评估方法见第 IX 部分《评估体系（AIAA）》。
