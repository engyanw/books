## 1. 目标和范围 

本文的读者对象是云架构师、系统工程师和安全研究员。

**机密Token** (Confidential Token, CT) 是在经过*远程证明*的机密计算环境中生成的模型输入/输出token；其信任模型是：**云服务商和模型服务商都不能读取用户数据**。本文说明如何构建并验证这样的环境。

本文力求自包含：从未部署过 AMD SEV、Intel TDX 或 Arm CCA 的读者，应当能够从头到尾读懂；已经有相关经验的读者，也应当能看到足够精确的 CT 特定设计决策，并据此提出反驳。

本文的核心主张，是对通常云信任叙事的两步强化：

- **机密计算** (Confidential Computing, CC) 把*云服务商*移出信任边界。它允许*模型服务商*在别人的硬件上运行自己的模型和推理栈，而该硬件的所有者无法读取或篡改工作负载。

- **机密Token** 再进一步，在*用户数据*层面把*模型服务商*也移出信任边界。单靠 CC 做不到这一点，因为 CC 只能证明*哪一份*软件启动了，却不约束*那份软件如何处理*它所处理的数据。CT 补上这些约束：受限操作系统、开源且可复现构建的推理栈，以及把已证明的度量值关联回可审计源码的公开只追加账本。

读者应在全文中始终记住这一区分：**CC 保护模型服务商不被云服务商攻击；CT 进一步保护用户不被模型服务商攻击。**

全文提到的机密计算技术，在 CPU 侧包括 AMD SEV-SNP、Intel TDX 和 Arm CCA，在加速器侧包括机密 GPU/NPU。机密虚拟机（Confidential VM, CVM）是全文的保护单元。

为具体说明信任边界，本文首先介绍一种简化的单节点 CT 部署，并称之为**基础设计**。在该设计中，一台受限 CVM 包含完整的推理路径。用户拥有的 AI agent 在发送机密数据之前，会对照公开透明账本验证 RA-TLS 证明证据。下图给出系统的整体概览；后续各节将说明每个组件和信任边界成立的依据。

## 2. 三种角色 

一次机密推理部署涉及三种逻辑角色。它们拥有不同资产、不同权限，并且关键的是，有不同的作恶动机。

### 2.1 用户 

用户提供提示词并消费模型输出。提示词是敏感资产：其中可能包含源代码、客户记录、合同、医疗数据或商业秘密。

在现代使用方式中，用户很少手动调用 LLM API。一个 **AI agent**（例如 coding agent）或其他 AI 客户端位于人和 API 服务端之间，并由用户拥有。在 B2B 场景下，“用户”可以是一家软件公司，其开发者使用 coding agent 调用模型服务商的 API URL；此时提示词可能包含整个代码仓库、内部 schema、嵌在代码里的凭据等公司的核心资产。

用户拥有：提示词、预期输出、客户端/coding agent，以及（如 [§6](#6-%E8%AF%81%E6%98%8E%E5%92%8C%E5%AF%86%E9%92%A5%E9%87%8A%E6%94%BE%E5%AE%A2%E6%88%B7%E7%AB%AF%E4%BE%A7%E6%B5%81%E7%A8%8B) 所述）可选的小型**本地API代理**。

### 2.2 模型服务商 

模型服务商在由云服务商角色控制的基础设施上部署模型和**推理框架**。本文中，*推理框架*是一个宽泛概念，指**所有负责提供推理服务的软件**，而不只是模型执行引擎。它包括：

- 暴露 LLM API URL 的 **Web服务器**（OpenAI兼容的API服务、流式传输层、请求路由）；

- **推理引擎**（例如 vLLM、SGLang、TensorRT-LLM）及其依赖（PyTorch、CUDA运行时、NCCL、GPU/NPU驱动用户态运行时）；

- **分词器**、提示词预处理和响应后处理；

- **KV-cache** 管理，以及任何 KV-cache 卸载数据库；

- **用户凭据/API密钥数据库**和认证层；

- 日志、监控指标，以及用于运维服务的**管理接口**。

模型服务商也拥有 CVM 的 **guest OS**，即在机密虚拟机内部启动的 OS镜像。但在 CT 相关意义上，它并不“拥有模型”：模型权重是服务商的专有资产，并且有意*保持闭源*（见[§7](#7-%E6%A8%A1%E5%9E%8B%E6%9C%89%E6%84%8F%E6%94%BE%E5%9C%A8%E8%A2%AB%E5%BA%A6%E9%87%8F%E9%95%9C%E5%83%8F%E4%B9%8B%E5%A4%96)）。

模型服务商拥有：模型权重和超参数、推理框架、guest OS镜像。

### 2.3 云服务商 

云服务商拥有并运营物理基础设施：hypervisor、host OS、云管平台 (Cloud Management Platform, CMP)、基板管理控制器（Baseboard Management Controller, BMC）、物理服务器、网络结构（network fabric）和数据中心设施。

云服务商拥有：hypervisor、host OS、CMP、部分未被纳入 TCB 的固件，以及全部物理硬件。某些固件（例如 EL3 可信固件）属于 TCB，会被度量或以其他方式纳入证明策略。

### 2.5 角色不必属于不同组织 

上述三个参与者是安全**角色**，并不要求由三个彼此独立的商业或法律实体承担。一个垂直整合的服务商可以同时承担模型服务商和云服务商角色。CT 按两个角色能力的并集分析这种部署：**O1** 继续保护用户明文不被这个合并实体读取；而模型所有者与基础设施所有者是同一实体时，**O2** 不适用。本文其余部分仍把两个角色分开描述，以明确各自的资产、权限和对应防御。该情况在 [§9.4](#94-%E5%90%88%E8%B0%8B%E6%95%8C%E6%89%8B) 中以 **AX1** 分析。

## 3. 敌手模型和安全目标 

### 3.1 云服务商敌手 

云服务商完全控制 CPU/加速器安全边界之外的一切。具体而言，它可以：

- 在 **host OS 上拥有 root 权限**，并完全管理 hypervisor 和 CMP；

- 部署**带后门的 hypervisor**、BMC 固件或宿主机内核，也就是云服务商自己编写或可任意修改的软件；

- 发起**物理攻击**：用 interposer 窃听内存总线或 DIMM interface，窃听 PCIe / NVLink / NIC，嗅探或修改网络流量，并在断电重启后对 DRAM 发起**冷启动攻击**；

- 选择或替换启动介质，挂载恶意 PCIe 设备，并重置、迁移或释放机器。

这是经典的机密计算敌手：一个具备特权、物理在场的基础设施所有者。

### 3.2 模型服务商敌手 

这是普通机密计算**没有**解决的敌手。模型服务商编写的，正是处理用户提示词的软件；它可能尝试**在推理框架中植入后门以外泄用户数据**。例如：

- 将提示词（或可恢复提示词的哈希/embedding）写入**资源利用率日志**、监控指标服务端或 crash dump，供服务商之后通过管理接口读取；

- 把某个用户的提示词或 KV-cache 复制到另一个会话的上下文中（跨用户泄漏）；

- 在 guest 镜像中携带 **SSH服务器**、调试 shell 或远程运维后门，让管理员可以登录并读取实时内存或磁盘；

- 将可执行代码藏入**模型文件**（例如恶意自定义 CUDA kernel），在推理路径中复制明文数据，见 [§7](#7-%E6%A8%A1%E5%9E%8B%E6%9C%89%E6%84%8F%E6%94%BE%E5%9C%A8%E8%A2%AB%E5%BA%A6%E9%87%8F%E9%95%9C%E5%83%8F%E4%B9%8B%E5%A4%96)。

本文假设模型服务商是*经济理性且重视声誉*的，而不是自毁式的：如果存在隐蔽且可否认的 covert channel，它会利用；但如果某种机制会让后门*公开可发现且不可抵赖地归因*，它就会受到威慑。正是这一假设，让开源加账本的方法（[§5](#5-%E4%BF%9D%E6%8A%A4%E7%94%A8%E6%88%B7%E4%B8%8D%E8%A2%AB%E6%A8%A1%E5%9E%8B%E6%9C%8D%E5%8A%A1%E5%95%86%E6%94%BB%E5%87%BB)）成为真实防御，而不只是口号。

### 3.3 安全目标 

**O1 – 用户数据对两个服务商均保密。** 无论各自行动、彼此合谋，还是与另一用户合谋，云服务商和模型服务商都不能读取用户提示词、模型输出，或任何**可从中恢复用户数据的中间数据**，包括 embeddings、logits、attention/KV-cache、卸载的 KV-cache、交换页和日志。

**O2 – 模型对云服务商保密。** 云服务商不能读取模型权重。

**O3 – 模型绑定（可选）。** 在需要防止模型替换的场景中，用户应能验证本次推理使用的模型身份或权重哈希。该绑定可以通过证明证据建立，也可以通过已证明推理框架产生的 API metadata 建立。O3 是可选目标，因为机密Token的主要职责是用户数据机密性；模型绑定机制见 [§7.6](#76-%E6%A8%A1%E5%9E%8B%E7%BB%91%E5%AE%9A%E8%AF%81%E6%98%8E%E6%89%BF%E8%AF%BA%E6%88%96-api-metadata)。

### 3.4 非目标 

下列事项明确不在范围内，这与一般机密计算相同：

- **可用性。** 云服务商总是可以拒绝服务；CT 保护机密性和完整性，不保护运行时长。

- **微架构和物理侧信道**（时序、功耗、电磁、资源争用）。这些风险真实存在，也是活跃研究方向，但不是 CT 声称要*解决*的问题。

- **模型行为安全。** CT 不阻止幻觉、提示词注入、越狱、训练数据投毒或权重中的行为后门。这些需要模型评测和输出安全机制，与 CT 正交（见 [§7.5](#75-%E6%9C%AC%E6%96%87%E4%B8%8D%E8%A6%86%E7%9B%96%E4%BB%80%E4%B9%88)）。

- **客户端侧入侵。** 如果用户自己的机器、coding agent 或本地API代理被攻破，CT 无能为力。

- **硬件厂商。** CPU/GPU/NPU 厂商及其证明 PKI 是可信基的一部分。

## 4. 机密计算：保护模型服务商不被云服务商攻击 

本节从零构建 CT 所依赖的 CC 机制。熟悉 SEV-SNP/TDX/CCA 和机密 GPU 的读者可以跳到 [§4.7](#47-%E6%9C%BA%E5%AF%86%E8%AE%A1%E7%AE%97%E4%B8%8D%E5%BC%BA%E5%88%B6%E4%BF%9D%E8%AF%81%E4%BB%80%E4%B9%88)，那里说明了CT在CC之上新增的机制。

### 4.1 问题：使用中的数据 

数据有三种状态，以及三类经典防御：

- **存储中** (at rest) – 加密磁盘。

- **传输中** (in transit) – 用 TLS 包裹连接。

- **使用中** (in use) – 数据在 RAM 和寄存器中被解密，以便CPU/加速器计算。这就是缺口。在推理过程中，提示词、激活值和输出都会在某处内存中以明文存在。磁盘和传输加密对此无能为力。

**可信执行环境** (Trusted Execution Environment, TEE) 关闭了使用中数据的缺口：它是一个硬件隔离的上下文，其中的代码和数据受到保护，不受上下文外所有软件影响，包括特权软件（hypervisor、host OS），也不受对内存的物理访问影响。

### 4.2 硬件信任根 

信任必须终止于某个物理实体。在 CC 中，它终止于 **CPU封装**（对加速器而言，则终止于 GPU/NPU 封装）。芯片厂商在制造阶段为每颗芯片写入一个唯一秘密密钥，并配置以厂商 CA 为根的证书链。这个设备密钥最终用于*签署证明证据*，因此验证方才能区分“真正的 TDX/SEV/CCA 芯片”和“伪装成芯片的软件模拟”。厂商根 CA 和芯片密钥配置流程被公理性地信任。

### 4.3 内存加密和隔离 

CT 平台必须为机密内存提供硬件**内存加密**。加密密钥由可信平台硬件管理，hypervisor 和 host 无法获得；其粒度和管理方式取决于具体体系结构。明文只存在于可信硬件边界内部，写入 DRAM 的机密内容均为密文。

这正是用来抵御 [§3.1](#31-%E4%BA%91%E6%9C%8D%E5%8A%A1%E5%95%86%E6%95%8C%E6%89%8B) 中云服务商*物理*攻击的机制：

- **总线/DIMM interposer** 只能看到密文；

- **冷启动攻击** 从冷却后的 DRAM 中只能恢复密文；

- 完整性保护（SEV-SNP 的反向映射表、TDX 的物理地址元数据）阻止 hypervisor **重映射、重放或别名化** CVM 的页面。

此外，由具体体系结构定义的硬件隔离机制会阻止云服务商拥有的同机共驻 VM 读取 CVM 内存。

### 4.4 度量 

**度量值**是由可信硬件/固件对*被加载进机密虚拟机的内容*累积得到的密码学哈希。它是远程方判断*正在运行哪份软件*的锚点。

系统有一个 **launch measurement**，在 VM 创建时对初始内存镜像和初始 vCPU 状态执行一次；在某些技术中，还有随启动链推进而扩展的**运行时度量寄存器**，类似 TPM PCR。

- **AMD SEV-SNP：** AMD Secure Processor 对初始 guest内存页和 vCPU 状态计算 **launch digest**。期望值可以和 *guest 策略* 一起固定在 *ID block* 中；如果测得摘要或策略不匹配，Secure Processor 会中止启动。([AMD SEV-SNP](https://www.amd.com/content/dam/amd/en/documents/epyc-business-docs/white-papers/SEV-SNP-strengthening-vm-isolation-with-integrity-protection-and-more.pdf))

- **Intel TDX：** TDX module 将初始固件/configuration 记录到 **MRTD** (Measurement of the Trust Domain)，并将后续启动链（内核、initrd、内核命令行、ACPI 表）记录到四个 **RTMR** 运行时度量寄存器。([Intel TDX](https://docs.kernel.org/arch/x86/tdx.html))

- **Arm CCA：** **Realm Management Monitor (RMM)** 是运行在 Realm Management Extension (RME) 引入的全新 *Realm world* 中的固件；它度量每个 Realm 的初始内容，以及 Realm 扩展的任何动态度量，并作为顶层*证明环境*。([Arm CCA](https://docs.kernel.org/arch/arm64/arm-cca.html))

统一思想是：当 CVM 运行起来时，硬件持有一个哈希，该哈希唯一标识已加载的 OS镜像和启动配置。guest 镜像改变一个字节，度量值就会改变。

### 4.5 远程证明 

**远程证明** (Remote Attestation, RA) 是一种协议，使 CVM 能够通过不可信网络向远程验证方证明：它是真正的 TEE，并且正在运行某个具体的被度量镜像。

核心对象是 **quote** (也被称为证明报告、TD quote 或 CCA 远程证明 token)：一种包含度量值、平台/固件安全版本号、验证方提供的 **nonce** (用于新鲜性/防重放)，以及工作负载可填入应用数据的 **report-data** 字段的结构。最重要的应用数据，是工作负载刚生成的临时公钥的哈希。quote 由**硬件信任根签名**：

- **SEV-SNP：** 证明报告由链到 AMD 根证书的 VCEK/VLEK 密钥签名。([AMD SEV-SNP](https://www.amd.com/content/dam/amd/en/documents/epyc-business-docs/white-papers/SEV-SNP-strengthening-vm-isolation-with-integrity-protection-and-more.pdf))

- **TDX：** TD 向 TDX module 请求 TDREPORT（受 HMAC 保护、本地），再由 **Quoting Enclave** 转换为 quote，并由Intel认证的远程证明密钥 (DCAP) 签名。([Intel TDX](https://docs.kernel.org/arch/x86/tdx.html))

- **CCA：** Realm 向 RMM 请求 *Realm token*，由 Realm Attestation Key 签名；平台再加入 *platform token*；二者共同组成 **CCA 远程证明 token**。([Arm CCA](https://docs.kernel.org/arch/arm64/arm-cca.html))

验证方（用户，或用户信任的服务）随后：

- 检查**签名链**直到厂商根证书，证明是真实硬件；

- 检查 **nonce** 是否匹配刚发出的 nonce，证明新鲜性，而不是重放旧 quote；

- 检查**度量值**是否等于预期值/已知可信值；

- 根据最低策略检查**固件/TCB 安全版本号**，拒绝已知存在脆弱微码/固件的部件。

**report-data 到临时公钥的绑定** 是把远程证明变成*安全通道*的关键：一旦验证方信任 quote，就会信任 quote 所背书的公钥，并可使用该密钥建立一个终止于 *TEE 内部*的加密会话。这是 RA-TLS（[§6](#6-%E8%AF%81%E6%98%8E%E5%92%8C%E5%AF%86%E9%92%A5%E9%87%8A%E6%94%BE%E5%AE%A2%E6%88%B7%E7%AB%AF%E4%BE%A7%E6%B5%81%E7%A8%8B)）的基础。

### 4.6 机密 GPU / NPU 

对于 LLM 推理，CPU 多数时候只是协调者；提示词、KV-cache 和激活值大部分生命周期都在加速器内存里度过。只保护 CPU、却让 GPU 暴露在外的 TEE，保护不了真正重要的东西。因此，机密 AI 也要求加速器位于信任边界内。

以 NVIDIA Hopper（H100）作为工作示例，这一模型可推广到后续芯片和其他 NPU：

- **每设备身份和证明。** 每个 H100 在制造时熔入唯一 ECC 密钥对和证书。在机密计算（CC）模式下，GPU会对其固件和配置信息度量值生成签名的证明报告。验证可通过 NVIDIA 的 **Remote Attestation Service (NRAS)**，也可在物理隔离环境离线完成，并通过 OCSP 检查吊销状态。([NVIDIA HCC](https://images.nvidia.com/aem-dam/en-zz/Solutions/data-center/HCC-Whitepaper-v1.0.pdf))

- **通过 SPDM 建立安全会话。** 运行在 *CVM 内部*的 GPU驱动与 GPU 执行 **SPDM**（Security Protocol and Data Model）握手，以认证 GPU、取得度量值并建立会话密钥。([NVIDIA HCC](https://images.nvidia.com/aem-dam/en-zz/Solutions/data-center/HCC-Whitepaper-v1.0.pdf))

- **通过 bounce buffers 加密 CPU↔GPU 传输。** 在 CC 模式下，显存被隔离，PCIe 路径被视为不安全。CPU 加密内存和显存之间传输的所有数据都经过 **bounce buffers**，并用会话密钥下的 **AES-GCM** 加密和完整性保护。云服务商窃听 PCIe 只能看到密文。([NVIDIA HCC](https://images.nvidia.com/aem-dam/en-zz/Solutions/data-center/HCC-Whitepaper-v1.0.pdf))

- **隔离的设备内存。** 在 CC 模式下，保存模型权重、KV-cache 和激活值的显存受到保护，无法被宿主机访问。

因此，信任链有两个根：CPU 厂商根和 GPU/NPU 厂商根。用户必须同时验证可接受的 CPU quote 和可接受的 GPU quote，*并且*验证它们描述同一个推理节点（绑定问题见 [§6.3](#63-%E8%AF%81%E6%98%8E%E6%8A%A5%E5%91%8A%E5%BF%85%E9%A1%BB%E5%8C%85%E5%90%AB%E4%BB%80%E4%B9%88) 和 [§8](#8-%E5%90%88%E5%9C%A8%E4%B8%80%E8%B5%B7)）。

#### 4.6.1 正在形成的标准：TEE-I/O（TDISP / TSM） 

bounce-buffer 方法有效，但会通过 CPU 加密内存复制数据。行业方向是 **TEE-I/O**，围绕 PCIe **TDISP** (TEE Device Interface Security Protocol) 章节标准化。两个逻辑实体协同工作：宿主机侧的 **TSM** (TEE Security Manager) 和设备内部的 **DSM** (Device Security Manager)。它们通过 PCIe DOE mailbox 运行安全 SPDM 会话，证明设备，配置 **IDE** (Integrity and Data Encryption) 链路加密密钥，并让设备能够直接 DMA 到 CVM 的机密内存。只有 root port 和设备持有 IDE 流密钥，因此网络结构中的 PCIe 交换机和恶意设备只能看到密文，无法进行中间人攻击。AMD 的 **SEV-TIO**、Intel 的 **TDX Connect** 和 Arm 的 CCA 设备直通工作都是厂商实现。([PCI/TSM](https://lwn.net/Articles/1043262/)) CT 部署会在 TEE-I/O 成熟并可用时采用；用户侧的证明义务保持不变。

### 4.7 机密计算不强制保证什么 

到 [§4.5](#45-%E8%BF%9C%E7%A8%8B%E8%AF%81%E6%98%8E)-4.6 结束时，机密计算能给用户一个可验证答案：*“这是真正的 TEE 硬件吗？它运行的镜像度量值是否等于 X？”*

但它不能回答：*“镜像 X 对我的数据来说真的可信么？”*

度量值只是一串哈希。只要实际启动的是某个 guest 镜像，CC 就会忠实地证明它，即使该镜像包含 SSH 后门、把提示词写入服务商可读的日志路径，或者偷偷把每个请求镜像到第二个服务端的推理引擎。**CC 强制保证*哪份*代码运行；它完全不说明*那份代码做什么*。**这正是*模型服务商*（[§3.2](#32-%E6%A8%A1%E5%9E%8B%E6%9C%8D%E5%8A%A1%E5%95%86%E6%95%8C%E6%89%8B)）可利用的缺口，因为模型服务商就是镜像 X 的作者。

关闭这个缺口是机密Token的任务，也是 [§5](#5-%E4%BF%9D%E6%8A%A4%E7%94%A8%E6%88%B7%E4%B8%8D%E8%A2%AB%E6%A8%A1%E5%9E%8B%E6%9C%8D%E5%8A%A1%E5%95%86%E6%94%BB%E5%87%BB)-[§7](#7-%E6%A8%A1%E5%9E%8B%E6%9C%89%E6%84%8F%E6%94%BE%E5%9C%A8%E8%A2%AB%E5%BA%A6%E9%87%8F%E9%95%9C%E5%83%8F%E4%B9%8B%E5%A4%96) 的主题。策略可以用一句话概括：让镜像 X **开源、可复现构建、受限，并登记在公开只追加账本中**，使硬件证明的度量值能够被任何人在事后不可抵赖地关联回人类可审计的源码。

## 5. 保护用户不被模型服务商攻击 

CC 已经将云服务商从用户数据机密性的图景中移除（内存被加密，总线是密文），也从完整性的图景中移除（云服务商无法在不改变度量值的情况下修改被度量镜像，而用户会拒绝改变后的度量值）。剩下的是模型服务商，它*合法地编写被证明镜像*。CT 从五个互相强化的维度约束该镜像。

### 5.1 受限操作系统 

CVM 内部的 guest OS 是一个**受限操作系统**：一个最小化、不可变、单用途的专用系统镜像，而不是一个管理员可以登录的一般 Linux。它具有以下属性：

基础设计把完整的被度量 guest 软件栈交给模型服务商；[§10.2](#102-%E5%88%86%E7%A6%BB%E8%A2%AB%E5%BA%A6%E9%87%8F%E8%BD%AF%E4%BB%B6%E6%A0%88%E4%B8%80%E7%A7%8D%E6%9C%BA%E5%AF%86%E6%B4%81%E5%87%80%E5%AE%A4%E9%85%8D%E7%BD%AE) 描述了一种可选配置，由 **CT软件栈发布者**为一个或多个独立模型服务商提供该软件栈。

- **无交互式访问。** 没有管理员 shell，没有 `getty`/控制台登录，没有 SSH服务器，没有调试代理，没有远程运维入口。任何人，无论是服务商管理员还是云管理员，都没有办法在 CVM 中获得 shell。

- **一个暴露的数据平面接口。** 唯一外部可达服务是 **LLM API服务端**（服务模型 API URL 的 Web服务器），用于服务来自 [§6](#6-%E8%AF%81%E6%98%8E%E5%92%8C%E5%AF%86%E9%92%A5%E9%87%8A%E6%94%BE%E5%AE%A2%E6%88%B7%E7%AB%AF%E4%BE%A7%E6%B5%81%E7%A8%8B) 的已证明安全通道。

- **受约束的管理接口。** 服务商确实需要运维服务：上传/替换模型、启动/停止推理、读取粗粒度资源利用率监控指标。框架版本发布必须通过新的只读系统镜像和新的账本记录完成，而不是通过运行时管理接口完成。CT 允许一个**管理接口**专门做这些事，但其设计必须保证*不能携带用户数据外流*：

只接受固定且经过审计的操作集合（模型上传、生命周期管理、健康状态/利用率读数），没有任意命令执行、没有临时数据盘文件读取、没有内存检查；

- 利用率监控指标是**聚合且有界的**（GPU %、tokens/sec、队列深度），关于为什么连日志都是被监看的表面，见 [§5.6](#56-%E9%80%8F%E6%98%8E%E8%B4%A6%E6%9C%AC) 的威慑讨论；

- 模型上传路径落到加密临时数据盘，并遵守 [§7](#7-%E6%A8%A1%E5%9E%8B%E6%9C%89%E6%84%8F%E6%94%BE%E5%9C%A8%E8%A2%AB%E5%BA%A6%E9%87%8F%E9%95%9C%E5%83%8F%E4%B9%8B%E5%A4%96) 中“模型即数据”规则。

- **运行时不能安装软件。** 镜像是不可更改的（下一小节）。OS 不能 `apt install`，不能获取并运行二进制文件，也不能加载 out-of-tree内核模块。被度量镜像中不存在的东西，运行时不能出现。这使度量值*随时间保持有意义*：已经证明为可信的镜像，不能在启动后变成别的东西。

- **最小攻击面。** 没有包管理器、没有编译器、没有框架所需之外的脚本解释器。对数据离开 CVM 的控制不是网络目的地允许列表，而是一条**信息流规则**（[§5.4](#54-%E5%BC%80%E6%BA%90)）：数据离开 CVM 的每一条路径，包括日志、监控指标、管理接口、API 响应，都是开源且可审计的，因此审查者可以确认没有用户数据被发出。

仅审计推理引擎还不够。如果 guest OS 允许管理员登录、调试或读取进程内存，运维人员就可以绕过推理引擎，直接访问用户数据。受限操作系统的作用是关闭这些替代访问路径。

### 5.2 只读系统镜像 + dm-verity 

OS 和整个推理框架作为**只读系统镜像**发布。为了在保持启动快速的同时让硬件度量值覆盖*整个*镜像，CT 使用 **dm-verity**：

- 镜像的根文件系统被 **dm-verity** 保护：它是一个由 SHA-256 哈希构成的 Merkle 树，覆盖每个块，并在顶层有一个**根哈希**。读取任何块时都会即时根据该树验证；被修改的块会验证失败并报错，而不是返回被篡改数据。

- 只需要把**根哈希**度量进 launch measurement / RTMR。由于根哈希链式证明了每个块，证明这个很小的根哈希就等价于证明整个（可能多 GB 的）镜像，而不需要在启动时计算整个镜像的哈希。([dm-verity](https://docs.kernel.org/admin-guide/device-mapper/verity.html))

- 文件系统在结构上就是**只读的**，这使 [§5.1](#51-%E5%8F%97%E9%99%90%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F) 中“运行时不能安装软件”在块设备层得到实施：没有地方可以把新的二进制文件写进系统镜像，任何重写块的尝试都会破坏 verity 哈希。

这兼具两方面优点：完整镜像完整性覆盖，以及与根哈希而非镜像大小成比例的启动/度量时间。

### 5.3 加密、临时数据盘 

只读系统镜像无法保存推理合法需要写入的内容：大型模型权重、卸载的 KV-cache、page-swap、系统日志，以及任何敏感工作数据。CT 通过单独的**临时数据盘**提供这些能力，并要求它具备三个属性：

- **启动时为空。** 每次 CVM 启动时临时数据盘都是空白的。它*不是*被度量镜像的一部分（其内容是运行时数据，不是代码），因此不影响远程证明。

- **用云服务商永远看不到的密钥加密**，例如使用 **dm-crypt**，密钥由 CVM 内部基于 TEE 内熵源生成，绝不以明文导出。因此云服务商交给 CVM 的后端存储只包含密文，把目标 **O1** 扩展到任何溢写到磁盘的内容：卸载的 KV-cache、交换页和日志都和加密 RAM 一样，对云服务商不可读。([dm-crypt](https://docs.kernel.org/admin-guide/device-mapper/verity.html))

- **重启后不持久。** 磁盘是*临时的（ephemeral）*：其加密密钥绑定到 CVM生命周期，并在关机或重启时丢弃。因此下一次启动无法恢复上一次启动的数据，云服务商也无法从底层介质中抢救出来。这类似机密容器中把只读且已验证的根文件系统与一次性加密临时空间叠加的模式。

临时数据盘的用途：

用途 | 
为什么必须在加密临时磁盘上 | 
|

模型权重 | 
对只读镜像来说太大；运行时上传；必须对云服务商隐藏（O2） | 
|

卸载的 KV-cache | 
包含用户上下文；必须对两个服务商隐藏（O1） | 
|

页面交换 | 
可能包含任何从 RAM 换出的明文（O1） | 
|

系统 / 框架日志 | 
可能包含敏感片段；不能留存在服务商可读介质上（O1） | 
|

敏感用户工作数据 | 
同上（O1） | 
|

注意分工：**dm-verity** 保护只读*代码*的*完整性*（并被度量）；**dm-crypt** 保护读写*数据*的*机密性*（并且有意*不被度量*，因为其内容是 runtime-variable）。混淆二者是常见设计错误。

### 5.4 开源 

被度量镜像中的一切，即 [§2.2](#22-%E6%A8%A1%E5%9E%8B%E6%9C%8D%E5%8A%A1%E5%95%86) 定义的 guest OS 和整个推理框架，都是**开源**的。具体而言，Web/API服务器、推理引擎、分词器、请求解密模块、证明 agent、密钥协商代码、KV-cache 和输出缓冲区管理、返回结果后处理、日志/监控指标代码、管理接口处理器、启动脚本、安全策略配置，以及**数据离开 CVM 的每一个边界处的代码**都公开可读。

关于这对网络意味着什么，需要说明一点。CT 对数据离开 CVM 的保护**不是**基于 IP 或端口的目的地允许列表。云服务商拥有网络，因此过滤目的地不带来任何机密性；而且在多节点部署（[§10.1](#101-%E5%88%86%E5%B8%83%E5%BC%8F%E9%83%A8%E7%BD%B2%E4%B8%8E-tee-%E8%BE%B9%E7%95%8C)）中，CVM 之间必须能够自由通信。这里的控制是一条**信息流**规则：在开源代码中数据离开 CVM 的每一处，无论是一行日志、一个监控指标、一次管理接口应答、API响应，还是一次对对等服务的调用，审查者都确立**绝不会有机密用户数据被放入任何离开 TEE 的内容中。** 跨越边界的通道都经过加密并终止于 TEE 内部（[§10.1.4](#1014-%E9%9B%86%E7%BE%A4%E8%AF%81%E6%98%8E)）；其中承载的内容由代码审查约束，而不是由防火墙规则约束。

边界由能力划定，而不是由情绪划定：*任何能影响控制流、接触明文、写文件、打开网络连接或发出日志的代码都必须开源*。唯一允许保持闭源的是模型权重和超参数（[§7](#7-%E6%A8%A1%E5%9E%8B%E6%9C%89%E6%84%8F%E6%94%BE%E5%9C%A8%E8%A2%AB%E5%BA%A6%E9%87%8F%E9%95%9C%E5%83%8F%E4%B9%8B%E5%A4%96)），正是因为纯权重*不能*做上述任何事情。后文有两个扩展放宽了这一基线：[§10.3](#103-%E7%94%B1%E5%8F%AF%E4%BF%A1%E6%9D%83%E5%A8%81%E6%9C%BA%E6%9E%84%E5%AE%A1%E6%9F%A5) 用可信权威机构的审查替代公开审查，[§10.4](#104-%E5%9C%A8%E6%B2%99%E7%AE%B1%E4%B8%AD%E8%BF%90%E8%A1%8C%E9%97%AD%E6%BA%90%E4%BB%A3%E7%A0%81) 则允许闭源代码在沙箱限制下进入推理路径，而不要求开源透明。

开源是必要但不充分的。它回答的是“这份代码按写法是否可信？”，但没有回答“实际运行的*是不是这份代码*？”。接下来的两个小节补上缺失的链路。

### 5.5 可复现构建 

远程证明度量的是一个镜像的哈希；人类审计的是*源码*。连接二者的桥梁是**可复现构建** (reproducible build)：一个把给定源码每次都映射为逐比特一致镜像的构建流程，不取决于谁构建、何时构建或在哪台机器上构建。

有了公开可用的可复现构建工具链：

- 模型服务商发布源码 `C`，以及度量值为 `M` 的镜像。

- **任何人**都可以查看 `C`，运行公开工具链，获得镜像，计算其 dm-verity 根哈希 / launch measurement，并确认它等于 `M`。

- 因此，“硬件证明度量值 `M`”就等价于“硬件正在运行源码 `C` 对应的精确代码，而我（或我信任的安全研究员）已经读过它”。

没有可复现构建时，远程证明最多只能告诉用户“某个哈希为 `M` 的二进制文件正在运行”，却无法把 `M` 连接到可审计源码，无法知道构建环境是否干净，也无法发现构建脚本悄悄拉入了额外文件。可复现构建把不透明的哈希变成关于*已审查源码*的声明。构建配方、依赖清单（固定版本、带哈希）、基础镜像摘要和构建者身份会一起发布，因此构建本身也可审计，而不只是源码可审计。

### 5.6 透明账本 

开源加可复现构建仍然留下一个攻击：**“给审计员看代码 A，却向用户证明度量值 B。”** 服务商可以发布一个干净 repo，但实际部署另一份带后门的镜像；或者短暂发布带后门镜像、提供服务，然后在被发现前删除它。

防御方式是一个**公开、只追加、不可抵赖账本**。guest OS 和推理框架的每个版本，即源码仓库和提交、构建配方、依赖清单、构建者身份，以及最终**镜像度量值**，都在被提供服务前记录到账本中。设计直接借鉴 **Certificate Transparency**：一个防篡改、只追加的日志（基于 Merkle 树，如 CT 日志或 Sigstore/Rekor 风格透明日志），其只追加属性本身可用密码学验证。

两个属性至关重要：

- **只追加 / 不可抵赖。** 服务商不能加入恶意镜像、提供服务，然后静默删除记录。正如被错误签发的 TLS 证书一旦记录到 CT 就成为针对签发 CA 的*永久公开证据*，带后门的 CT 镜像一旦记录到账本，也会成为针对模型服务商的永久公开证据。服务商不能追溯改写历史。

- **绑定到远程证明。** 用户不是孤立检查 quote；用户会检查 *quote 中的度量值是否出现在账本中*（[§6.4](#64-%E9%AA%8C%E8%AF%81%E6%B8%85%E5%8D%95)）。“展示 A、证明 B”会失败，因为 B 必须在公开账本中才会被接受，而与已发布源码 A 矛盾的 B 对所有监看日志的研究员都是公开可见的。

账本记录了镜像生命周期。发现软件漏洞后，镜像发布者通常先发布并登记修复后的镜像，完成部署，然后针对旧度量值追加一份已签名的**撤销声明**。严重漏洞可能需要在替代镜像可用之前就撤销旧镜像；与其向已知存在漏洞的代码释放新提示词，宁可暂时中断服务。由于账本只追加，撤销不会修改或删除原始镜像记录，而是加入一份可归因的新声明，标明受影响的度量值、撤销生效时间，以及可用时的替代镜像和相关安全公告。在基础设计中，模型服务商是镜像发布者；在 [§10.2](#102-%E5%88%86%E7%A6%BB%E8%A2%AB%E5%BA%A6%E9%87%8F%E8%BD%AF%E4%BB%B6%E6%A0%88%E4%B8%80%E7%A7%8D%E6%9C%BA%E5%AF%86%E6%B4%81%E5%87%80%E5%AE%A4%E9%85%8D%E7%BD%AE) 中，这一责任由CT软件栈发布者承担。

登记和撤销只是证据，并不是账本强加给所有人的单一全局判断。登记证明镜像及其构建历史已经发布，本身并不意味着镜像可信。除发布者的撤销声明外，账本还可以收录独立研究人员或审计方签名并标明受影响度量值的安全公告。公告不会替所有用户撤销镜像；每个用户的验证策略自行选择信任哪些公告发布者，以及何种证据足以拒绝镜像。用户始终可以在本地拒绝某个度量值。反过来，发布者撤销旧镜像也不会自动批准声明中指定的替代镜像；新镜像仍须独立满足用户策略。

客户端还必须抵御撤销发生前的陈旧账本视图。因此，它会依据足够新的已签名账本检查点判断镜像状态，并验证该视图相对于自己以前接受的检查点仍保持只追加。如果无法获得新鲜且一致的视图，客户端就不会释放下一条提示词；攻击者可以造成拒绝服务，却不能通过重放旧账本状态让已撤销镜像继续被接受。更严格的策略还可以要求一个或多个独立审计方提供当前有效且有时限的背书。这样，即使疏忽的服务商始终不撤销镜像，背书到期而未续期也会使该镜像不再可接受，代价是把这些审计方加入用户的信任策略。这些新鲜度和防回滚机制沿用了透明日志与安全软件更新中的成熟模式（[Certificate Transparency](https://www.rfc-editor.org/rfc/rfc9162.html)、[The Update Framework](https://theupdateframework.github.io/specification/latest/)）。

账本把模型服务商威胁从“相信我们”转换成一个**通过可检测性实现威慑** (deterrence-by-detectability) 的制度，[§5.7](#57-%E6%89%80%E6%9C%89%E4%BA%BA%E9%83%BD%E8%83%BD%E7%9C%8B%E5%88%B0%E7%9A%84%E5%90%8E%E9%97%A8) 会明确说明这一点。

账本至少应记录：源码仓库 + 提交、构建配方、依赖清单、构建者身份、OS/镜像度量值（dm-verity 根哈希和 launch measurement）、允许的固件/TCB 最低版本、受限操作系统策略版本，以及证明策略版本。账本还永久保存撤销声明和它所收录的安全公告。可选地，它还携带第三方审计方对特定提交的签名。

### 5.7 所有人都能看到的后门 

CT 不声称让后门*不可能*被写出来；模型服务商就是代码作者。CT 让后门**不可能隐藏**。因为源码长期公开、可复现构建，且服务中的度量值被固定在只追加账本里：

- 如果服务商发布带有 **SSH服务器**、调试 shell 或**把用户数据复制进日志或外发消息的代码**的镜像，任何阅读公开源码，或对比两个账本条目的研究员都能发现。通过可复现构建，部署的镜像*就是*公开源码；不存在“真正运行的不是这个”的逃路。

- 如果服务商试图**通过资源利用率日志外泄提示词**，输出日志的代码是公开的，数据离开 CVM 的每一条其他路径也都是公开的。编码了提示词内容的日志行，或偷运提示词字节的对等服务调用，都能在审查中看见。

- 以这种方式发现的后门不只是 bug，而是一次故意窃取客户数据尝试的**不可抵赖、带时间戳、公开证据**，并且通过账本归因到服务商。对重视声誉和合同的商业主体来说，这是严重威慑。

这与 Certificate Transparency 对 CA 有效的逻辑相同：重点不是技术上阻止作恶，而是确保作恶*必然被发现并被永久归因*。机密Token把这一逻辑引入 AI 推理。

## 6. 证明和密钥释放：客户端侧流程 

现在我们已经有了一个*值得*信任的环境。本节说明用户如何在交出提示词前*验证*它。支配原则是：**先证明，再提供秘密**。服务商产生证据，用户检查证据，只有在此之后，用户客户端才释放（加密的）提示词。

### 6.1 RA-TLS：把证明融合进通道 

最干净的实现，是把远程证明绑定到 TLS握手，也就是 **RA-TLS**。其思想（源自 SGX，并推广到 CVM）是：

- 在 CVM 内部，推理服务端生成一个**临时 TLS 密钥对**。

- 它取得一个新的远程证明 quote，其 **report-data** 包含该**临时公钥的哈希**。

- 它把 quote（以及硬件证书链）作为自定义扩展嵌入一个**自签名 X.509 证书**，使用 TCG DICE “tagged evidence” OID，并在TLS握手中展示该证书。([RA-TLS](https://gramine.readthedocs.io/en/stable/attestation.html))

- 客户端不通过普通 CA 验证证书，而是**验证嵌入的 quote**：到硬件厂商根证书的签名链、新鲜的 nonce、度量值，以及关键绑定，即证书中 TLS 公钥的哈希等于 quote 的 report-data。

因为终止 TLS 会话的密钥，正是*硬件背书过*的密钥，加密通道就被证明终止于 **TEE 内部**。云服务商或模型服务商外层基础设施都没有机会持有明文：中间人没有私钥，中继攻击也会因report-data 绑定失败。RA-TLS 不需要修改 TLS 库，证据通过证书携带即可。([RA-TLS](https://gramine.readthedocs.io/en/stable/attestation.html))

### 6.2 实用部署：本地API代理 

RA-TLS 是正确终态，但尚未广泛部署；coding agent 也只会对 OpenAI-style URL 说普通 HTTPS，并不知道如何验证 quote。要求每个 agent都具备远程证明的能力并不现实。

务实答案是用户本地运行一个小型**本地API代理**：

```
  coding agent  ──HTTP──▶  本地API代理  ══已证明安全通道══▶  CT LLM API URL
   (无需修改)              (localhost, 用户拥有)   (RA-TLS 或其他)     (CVM 内部)

```

- Coding agent 配置为访问 `[http://localhost:](http://localhost:)<port>`，也就是一行 base-URL 变更，不需要修改代码。

- **本地API代理**与 CT API服务端执行远程证明握手，并建立到 TEE 的安全通道。RA-TLS 是实现该通道的一种方式；代理也可以使用其他远程证明机制（单独的远程证明验证步骤后接密钥协商握手、验证方服务、厂商远程证明 SDK）。这恰好有用，因为 RA-TLS 尚未无处不在。

- 代理执行用户的**验证策略**（[§6.4](#64-%E9%AA%8C%E8%AF%81%E6%B8%85%E5%8D%95)）：如果远程证明失败，它拒绝转发请求，提示词永远不离开用户机器。

这把“让 agent 能工作”和“验证环境”解耦。用户侧信任边界是代理（由用户拥有，也可开源并审计），agent 免费继承机密性。代理也是固定允许的度量值、应用本地拒绝列表和可信公告策略、缓存新鲜账本检查点，以及向用户展示验证状态的自然位置，相当于浏览器小锁。

### 6.3 证明报告必须包含什么 

为了让用户（或代理）做出决策，CT API服务端返回的证据必须携带以下内容，并且全部绑定到同一个新鲜的 nonce：

- **可信硬件报告**，由相应厂商根证书签名：

**CPU** TEE quote（SEV-SNP report / TDX quote / CCA token）；

- 推理路径上每个加速器的 **GPU/NPU** 证明报告。

- **可信固件度量值 / TCB 版本：** 平台安全版本号和固件度量值（例如 TDX module / Quoting Enclave TCB、CCA 中的 platform token、GPU 固件版本，以及使用 TEE-I/O 时的 TSM/device-security state）。

- **CVM 镜像度量值：** 标识精确 guest OS + 推理框架的 launch measurement 和 dm-verity 根哈希。

- **report-data 绑定：** 终止安全通道的临时公钥的哈希（[§6.1](#61-ra-tls%E6%8A%8A%E8%AF%81%E6%98%8E%E8%9E%8D%E5%90%88%E8%BF%9B%E9%80%9A%E9%81%93)），把上述全部绑定到*这个*会话。

CT 基础方案**不要求**证明报告包含**模型身份**。模型权重可以保持闭源并位于被度量镜像之外（[§7.1](#71-%E4%B8%BA%E4%BB%80%E4%B9%88%E6%8E%92%E9%99%A4%E6%A8%A1%E5%9E%8B)）。但如果部署采用可选目标**O3**，则可以把模型标识符、权重摘要或其他模型承诺绑定到新鲜的证明证据中，也可以通过已证明框架产生的 metadata提供模型身份（[§7.6](#76-%E6%A8%A1%E5%9E%8B%E7%BB%91%E5%AE%9A%E8%AF%81%E6%98%8E%E6%89%BF%E8%AF%BA%E6%88%96-api-metadata)）。这两种方式都不要求公开模型权重。

### 6.4 验证清单 

只有在**全部**下列条件成立时，客户端/代理才接受通道：

- **硬件真实：** 每个 quote 的签名都链到正确厂商根证书，并且 CPU 和 GPU/NPU quotes 绑定到**同一个推理节点/会话**，而不是从两台不同机器拼接而来。

- **新鲜：** nonce 匹配刚发出的 nonce（没有重放旧 quote）。

- **TCB 可接受：** 固件/微码安全版本号满足最低策略；被撤销部件（GPU 使用 OCSP）被拒绝。

- **度量值当前可接受：** CVM 镜像度量值及其公开源码和可复现构建记录**出现在公开账本中**（[§5.6](#56-%E9%80%8F%E6%98%8E%E8%B4%A6%E6%9C%AC)），并且符合用户的验证策略。仅有登记并不充分：策略会拒绝被发布者撤销和被用户本地拒绝的度量值，也可以根据用户信任的公告发布者所提供的公告采取行动，或要求审计方提供当前有效的背书。客户端依据足够新的账本检查点做出决定，并验证该检查点与以前接受的检查点一致。

- **密钥绑定到 TEE：** 安全通道的公钥的哈希等于 quote 的 report-data。

（如果采用可选目标 **O3**，客户端还要验证证明证据或已证明框架 metadata 中携带的模型绑定，详见[§7.6](#76-%E6%A8%A1%E5%9E%8B%E7%BB%91%E5%AE%9A%E8%AF%81%E6%98%8E%E6%89%BF%E8%AF%BA%E6%88%96-api-metadata)。）只有在所有必需检查通过之后，客户端才建立加密会话并发送（加密的）提示词；TEE 在内部解密，使用机密 GPU/NPU运行推理，并返回响应，理想情况下由同一个已证明会话签名或绑定到该会话。任何检查失败时，代理拒绝，提示词留在本地。对长连接的接受是有时限的：一旦账本视图超过用户策略规定的新鲜度上限，代理就会先刷新并重新评估镜像，然后才释放下一条提示词。

## 7. 模型：有意放在被度量镜像之外 

### 7.1 为什么排除模型 

模型权重是模型服务商的**核心数字资产**，往往来自巨额训练投入。CT **不**要求它们开源，权重也**不是**被度量 CVM 镜像的一部分。因此，CT基础方案证明的是*框架*，而不要求把权重本身纳入启动度量。采用可选目标 **O3**的部署仍然可以在模型加载后，把模型标识符或摘要绑定到新鲜的证明证据中（[§7.6](#76-%E6%A8%A1%E5%9E%8B%E7%BB%91%E5%AE%9A%E8%AF%81%E6%98%8E%E6%89%BF%E8%AF%BA%E6%88%96-api-metadata)）。这一过程不会泄露模型权重。

在操作上，模型会在启动*之后*通过管理接口上传（[§5.1](#51-%E5%8F%97%E9%99%90%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F)），落在加密临时数据盘上（[§5.3](#53-%E5%8A%A0%E5%AF%86%E4%B8%B4%E6%97%B6%E6%95%B0%E6%8D%AE%E7%9B%98)）。因为权重很大，并且独立于代码变化，将其烘焙进被度量只读镜像既不现实（multi-gigabyte度量值，每次模型更新都要重新度量），也没有必要。

但只有在模型文件真正是纯数据时，把模型排除在度量之外才安全。这个条件不是自动成立的，[§7.3](#73-model-as-code%E5%81%87%E8%AE%BE%E5%9C%A8%E5%93%AA%E9%87%8C%E5%A4%B1%E6%95%88)-7.4 说明如何强制它成立。

### 7.2 Model-as-data：为什么纯权重不能泄漏 

安全形式的模型**只有权重和超参数**：数字张量加标量配置（层数、维度等）。这样的制品是**纯数据**。它由（开源、被证明的）推理框架消费，而推理框架决定全部控制流。纯权重：

不能打开网络连接、写文件或发出日志；

- 不能 fork process 或调用 cloud API；

- 不能改变框架的控制流。

不同权重会产生不同*数值*（不同答案），但不能让*系统*做任何被证明框架本来不会做的事。因此，闭源且未被证明的权重文件不违反**O1**：纯数据没有机制外泄提示词。这就是将权重排除在基于远程证明的信任范围之外的精确理由。

### 7.3 Model-as-code：假设在哪里失效 

一旦模型 artifact 可以携带**可执行代码**，“纯数据”假设就失效了。两个具体向量：

- **不安全序列化格式。** 事实上的 PyTorch 格式（`.bin`/`.pth`）是 Python **pickle**，它在反序列化时*按设计*执行任意代码。加载恶意检查点可以运行攻击者代码，用于外泄数据或安装后门。这是有充分文档记录的供应链漏洞类别。([safetensors](https://huggingface.co/docs/hub/en/security-pickle))

- **模型携带自定义 GPU kernel。** 模型可能合理地携带**自定义 CUDA kernel**（fused ops、novel attention、exotic quantization）。*恶意*自定义 GPU kernel 是运行在 GPU 上、位于 TEE 内部、并可访问保存用户数据张量的代码，包括KV-cache、激活值、提示词embedding。这样的 GPU kernel 可以**把某个用户的提示词复制到另一个用户的上下文中**，把明文写到未加密区域，或通过侧路径偷运数据。这正是[§3.2](#32-%E6%A8%A1%E5%9E%8B%E6%9C%8D%E5%8A%A1%E5%95%86%E6%95%8C%E6%89%8B) 中模型服务商外泄威胁，通过 CT 唯一没有被证明的 artifact 重新进入。

如果可执行代码能搭载在模型文件中，那么“模型闭源且未被证明”就会悄悄重新打开 [§5](#5-%E4%BF%9D%E6%8A%A4%E7%94%A8%E6%88%B7%E4%B8%8D%E8%A2%AB%E6%A8%A1%E5%9E%8B%E6%9C%8D%E5%8A%A1%E5%95%86%E6%94%BB%E5%87%BB) 已经努力关闭的洞：服务商可以把后门放进 *kernel* 而不是*框架*，框架开源也证明不了什么。

### 7.4 CT 规则及其执行方式 

**规则：** *只有模型权重和超参数可以闭源。任何能影响控制流或接触明文的代码，包括自定义 GPU kernel，都必须开源、可复现构建，并作为推理框架镜像的一部分被证明。* CT**不**允许闭源可执行代码通过模型文件进入推理路径。（服务商有意在*框架内部*运行的闭源代码，与通过模型文件偷运代码是不同的情况，只在 [§10.4](#104-%E5%9C%A8%E6%B2%99%E7%AE%B1%E4%B8%AD%E8%BF%90%E8%A1%8C%E9%97%AD%E6%BA%90%E4%BB%A3%E7%A0%81)的沙箱限制扩展下被允许。）

执行方式从最强到最宽松：

- **仅数据序列化。** 要求模型从**不执行代码**的格式加载，**safetensors** 是典型选择：一个扁平张量 blob 加上由 names/shapes/dtypes 构成的 JSON header，反序列化期间没有代码路径。([safetensors](https://huggingface.co/docs/hub/en/security-pickle)) 模型加载器（开源、被证明）拒绝 pickle/`.bin`，并拒绝任何不是纯张量 + 声明的超参数的artifact。这让 “model-as-data” 成为机械强制属性，而不是希望。

- **运行时不允许自定义 GPU kernel。** 受限操作系统（[§5.1](#51-%E5%8F%97%E9%99%90%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F)）和只读镜像（[§5.2](#52-%E5%8F%AA%E8%AF%BB%E7%B3%BB%E7%BB%9F%E9%95%9C%E5%83%8F--dm-verity)）已经禁止运行时代码加载；推理框架进一步拒绝 JIT 编译或`dlopen` 模型 artifact 提供的 GPU kernel。模型只能在已存在于*被证明镜像*中的 GPU kernel 之间选择，不能自带。

- **已证明 GPU kernel 允许列表。** 如果某个模型确实需要自定义 GPU kernel，这些 GPU kernel 必须**上游合入开源框架**，可复现构建，并合入被度量镜像。此时它们像其他框架代码一样被证明，并登记到账本中。不在被证明镜像中的 GPU kernel 不能运行。随后模型文件按 *身份标识*引用 GPU kernel，加载器将这些身份标识绑定到已度量集合。

- **沙箱作为纵深防御。** 即使已被证明的 GPU kernel 也可以被约束：限制为只能访问其声明的输入/输出张量，禁止访问其他会话的内存区域，禁止宿主机 I/O。这样bug（不只是恶意）也不会变成跨用户泄漏。这是对远程证明的补充，而不是替代。

净效果是：服务商唯一保密的是一团数字和少量标量。所有能*作用于*用户数据的东西，包括加载器、GPU kernel、调度器、内存管理、日志，以及每一条把数据发出 TEE的路径，都是开源、可复现构建、被证明，并登记到账本中的。

### 7.5 本文不覆盖什么 

让模型保持“纯数据”可以阻止模型文件*外泄*提示词。但它不处理模型的*行为*：权重文件仍可编码行为后门、触发短语、投毒关联或不安全输出。这些风险真实存在，但它们与机密性正交，属于模型评测、红队测试和输出安全机制，而不是 CT “服务商不能读取你的提示词” 保证的一部分。CT 对自己承诺的内容保持精确；[§11](#11-%E9%99%90%E5%88%B6%E5%92%8C%E5%BC%80%E6%94%BE%E9%97%AE%E9%A2%98) 会重申边界。

### 7.6 模型绑定：证明承诺或 API metadata 

由于模型在启动后加载，并且不属于被度量镜像，CT 基础方案不要求硬件 quote 绑定模型。采用可选目标 **O3** 的部署可以在不公开权重的前提下增加模型绑定。已证明框架可以在加载纯数据模型后计算其哈希，并把模型标识符、权重摘要或其他稳定承诺绑定到与会话密钥关联的新鲜证明证据中。验证者由此可以确认该会话使用了相应承诺所代表的模型。对于闭源权重，预期承诺可以发布到透明账本中，也可以由服务商或审计机构签名；承诺能够标识模型，但不会公开模型内容。

模型绑定也可以通过**已证明推理框架产生的 API metadata**建立。该机制建立在一个已经确立的事实之上：框架是开源、已审查、可复现构建且被证明的（[§5](#5-%E4%BF%9D%E6%8A%A4%E7%94%A8%E6%88%B7%E4%B8%8D%E8%A2%AB%E6%A8%A1%E5%9E%8B%E6%9C%8D%E5%8A%A1%E5%95%86%E6%94%BB%E5%87%BB)）。我们不只依赖服务商关于实际运行模型的承诺，而是验证负责处理模型身份的公开已审查框架，其方向可以是一种或两种：

- **尊重请求中的模型 ID。** 推理 API 输入携带模型标识符。已证明框架经过审查，以确认它确实路由到并运行绑定到该标识符的权重；它不能悄悄把 `strong-model-v2` 映射到更小模型，因为路由代码是公开的，且通过可复现构建，部署代码*就是*公开代码。

- **在响应中盖上模型身份。** 框架在推理输出的元数据中附加**模型身份和/或权重哈希**。因为计算并发出该元数据的代码被证明，一个声称来自 `strong-model-v2` 的响应要么确实来自它，要么框架必须包含可审查的撒谎代码；而这样的代码会在公开源码中可见，并在账本中记录到服务商名下（[§5.7](#57-%E6%89%80%E6%9C%89%E4%BA%BA%E9%83%BD%E8%83%BD%E7%9C%8B%E5%88%B0%E7%9A%84%E5%90%8E%E9%97%A8)）。

两种机制可以结合使用：远程证明把模型承诺绑定到会话，API metadata则记录每次请求由哪个模型提供服务。二者绑定的都是权重的*身份/哈希*，而不是权重的*质量或行为*。它们可以检测静默模型替换，但不能证明所命名的模型本身是好的（那是[§7.5](#75-%E6%9C%AC%E6%96%87%E4%B8%8D%E8%A6%86%E7%9B%96%E4%BB%80%E4%B9%88) 的范围）。

## 8. 合在一起 

### 8.1 端到端信任链 

```
硬件信任根（CPU + GPU/NPU 厂商密钥）
   └─ 度量 → CVM 启动 + dm-verity 根哈希（受限操作系统 + 开源框架）
        └─ 源码 ← 可复现构建 ← 公开源码提交
             └─ 记录到 → 公开只追加账本（CT 风格透明性）
                  └─ 由用户的本地API代理验证 → 远程证明 + 账本检查
                       └─ 释放 → 加密提示词进入 TEE
                            └─ 处理方 → 已证明框架 + 纯数据模型，在机密 GPU/NPU 上
                                 └─ RAM 全部加密，溢写全部进入临时 dm-crypt 磁盘，PCIe 全程密文

```

每个箭头都是*证明*，不是*承诺*。云服务商通过内存加密 + 度量被排除；模型服务商通过受限操作系统 + 开源 + 可复现构建 + 账本 + 纯数据模型被排除在用户数据之外。

### 8.3 剩余可信基 

CT 缩小了必须信任的东西，但没有消除它们：

- **CPU 和 GPU/NPU 芯片**以及厂商远程证明 PKI（信任根）；

- **已批准固件/TCB** 版本（由策略固定，在远程证明时检查）；

- OS 与推理框架的**已发布源码**，以及**可复现构建工具链**；

- **账本**的只追加完整性，以及监看它的研究员的尽责程度；

- **用户自己的客户端和本地API代理**。

与现状相比，也就是相信整个服务商、整个云、每个管理员、每条日志的去向和未来每一次条款变更，这是一组小得多，并且关键是*可验证*的信任对象。

## 9. 基础设计的安全分析 

本节分析针对**基础设计**的具体攻击：单个 CVM 包含完整的明文推理路径；模型服务商同时提供被度量的 guest 镜像和纯数据模型；TEE 之外没有任何服务处理用户数据。本节不分析 [§10](#10-%E5%AF%B9%E5%9F%BA%E7%A1%80%E8%AE%BE%E8%AE%A1%E7%9A%84%E6%89%A9%E5%B1%95) 中的扩展。

分析假设用户客户端和本地API代理可信；CPU 与加速器硬件、固件信任根和证明 PKI 可靠；标准密码算法被正确实现；用户接受的源码已经过专业审计。这些假设定义了两种不同的防御。CC 机制直接阻止云服务商读取受保护内存。CT 对软件作者的防御则带有条件：审查确认被接受的源码不含内容外泄路径，可复现构建与证明确认运行的是对应镜像。证明所证明的是软件身份，并不证明软件行为必然良善。审查中遗漏的恶意路径仍然是残余风险，受 [§3.2](#32-%E6%A8%A1%E5%9E%8B%E6%9C%8D%E5%8A%A1%E5%95%86%E6%95%8C%E6%89%8B) 的可检测性与威慑假设约束。

目标 **O1** 保护明文内容，不隐藏请求或响应长度、时序、资源使用情况或其他侧信道观察。可用性同样不在保证之内。为便于引用，每种攻击都有稳定标识符：**AC** 表示云服务商发起的攻击，**AM** 表示模型服务商发起的攻击，**AU** 表示用户发起的攻击，**AX** 表示涉及合谋的跨角色攻击。

### 9.1 恶意云服务商 

云服务商控制 host OS、hypervisor、虚拟设备、存储和网络后端、机器管理系统及物理基础设施，也可以替换硬件安全边界之外的任何软件。

**AC1 — Host OS 读取 CVM 的 CPU 内存。** SEV-SNP、TDX 或 CCA 使用 host 无法获得的密钥加密 CVM 内存。Host 可以映射或复制后端页面，但得到的是密文，而不是提示词、输出、中间状态或模型权重。

**AC2 — Host OS 修改、重映射、别名映射或重放 CVM 内存页。** 机密计算平台的内存所有权和完整性机制把受保护页面绑定到 CVM 及其预期地址。Host 替换或破坏受保护页面，不能让 CVM 接受攻击者选择的明文，至多让虚拟机 fault。不提供所需完整性保护的平台不符合 CT 要求。

**AC3 — Host OS 读取或写入系统 virtio 磁盘。** 读取系统分区不是机密性攻击：其中只有公开的 guest OS 和推理框架，不包含用户数据或模型权重。Host 修改单个块时，`dm-verity` 会在读取时检测到不匹配；替换整个镜像或根哈希时，被证明的度量值会改变，用户会拒绝。磁盘破坏仍可阻止 CVM 启动或运行，但这属于拒绝服务。

**AC4 — Host OS 读取或破坏数据 virtio 磁盘。** Host 只能看到由 CVM 内部生成并保留的临时密钥加密的 `dm-crypt` 密文，其中包括模型权重、swap、日志和卸载的 KV-cache。基础设计不要求该磁盘具有认证完整性：恶意修改或重放块被视为数据破坏，因此属于范围外的拒绝服务，而不是机密性破坏。

**AC5 — Host OS 读取加速器内存或替换成非机密加速器。** 合规部署让加速器运行在机密计算模式，使设备内存与 host 驱动和管理接口隔离。用户验证加速器签名报告、固件和安全状态，以及它与推理节点的绑定。来自另一设备或非机密设备的证据会被拒绝。

**AC6 — 云服务商恶意管理员窃听物理内存或 CPU–加速器互连。** DRAM 总线窃听或冷启动攻击只能得到 CPU 内存密文。PCIe 或 NVLink 窃听看到的是受 CPU–加速器认证会话保护的密文，无论该会话使用加密 bounce buffer 还是 TEE-I/O/IDE。直接读取 CPU 或加速器封装内部的明文属于对可信硬件本身的攻击，不在威胁模型内。

**AC7 — Host OS 挂载恶意 DMA 设备或控制虚拟设备。** 机密设备分配、IOMMU 隔离，以及适用时的 TEE-I/O，会阻止未授权设备 DMA 访问受保护内存。但 host 可以通过被允许的 virtio 设备返回恶意输入。利用 guest 内核或驱动漏洞的畸形响应属于可信计算基的残余风险：CC 不会让被证明的 guest 驱动免疫 Iago 型攻击。

**AC8 — Host OS 读取、修改或重定向网络流量。** RA-TLS 提供内容机密性和完整性，并把终结通道的密钥绑定到被证明 CVM。把客户端重定向到伪造服务端没有帮助：该服务端无法为自己的通道密钥产生可接受证据，本地API代理不会释放提示词。

**AC9 — 云服务商篡改推理框架，并为被批准镜像伪造证明证据。** 实际 launch 和 runtime 度量值由硬件信任根签名。云服务商若不能伪造该签名，就不能让修改后的代码冒充被批准的度量值。硬件厂商或其证明 PKI 被攻破不在 CT 威胁模型内。

**AC10 — 云服务商篡改框架，但重放或拼接真实证明证据。** 重放来自未篡改 CVM 的报告会在新鲜 nonce 检查，以及 report-data 与当前通道密钥的绑定检查中失败。把一台机器的 CPU 报告与另一台机器的 GPU/NPU 报告拼接，也不满足所有证据必须描述同一推理节点和会话的要求。

**AC11 — 云服务商启动已经登记但已被撤销的镜像。** 登记会作为永久历史证据保留，但不足以支持当前接受。客户端使用足够新的账本检查点，并验证它与自己已经接受的检查点一致，然后依据用户策略评估度量值。如果镜像已被发布者撤销、被用户在本地拒绝，或收到来自用户策略所信任的公告发布者的安全公告，客户端就会拒绝。云服务商可以通过阻断当前账本视图来拒绝服务，却不能利用陈旧状态让客户端释放新提示词。

**AC12 — 云服务商观察流量形态或执行侧信道。** 数据包大小和时序、CPU 或 GPU 利用率、磁盘活动、中断模式、EPT fault 等二级页表 fault、功耗、电磁辐射和资源争用都不在 **O1** 内。重置、暂停或释放 CVM 也一样：CT 不提供可用性。

### 9.2 恶意模型服务商 

模型服务商编写的软件在 TEE 内部合法地看到明文。因此 CT 不仅要约束运行哪一个二进制文件，还要约束该二进制与服务商或其他用户通信的每一种方式。

**AM1 — 框架把用户数据发送到第二个服务端。** 网络外发代码属于公开且经过审计的镜像。根据 CT 的已审计软件假设，被接受的源码中不存在把提示词、输出、embedding、KV-cache 条目或其他可恢复中间数据放入外发消息的路径。可复现构建和证明阻止服务商静默地用另一份部署二进制替换该源码。

**AM2 — 框架把用户数据编码进日志、监控指标或 crash 输出。** 所有日志和监控指标生成代码同样位于公开镜像内，对外暴露的值必须聚合且有界。直接携带内容的字段可在审查中发现；通过时序或资源调制编码则属于下文单独讨论的侧信道。

**AM3 — 服务商通过管理后门取得实时或已存储数据。** 受限镜像没有 SSH服务器、登录控制台、调试 agent 或 crash dump 获取路径。受约束管理接口不实现任意命令、内存读取或数据盘读取操作。临时加密磁盘也防止运维人员在重启后恢复已存储明文。

**AM4 — 服务商发布干净源码，却部署带后门的二进制文件。** 只有当运行镜像的度量值通过可复现构建与账本中的已发布源码绑定时，验证方才接受它。不能从该源码复现的二进制文件具有不同或无法解释的度量值，会被拒绝。

**AM5 — 服务商在成功证明后修改代码。** 系统镜像是只读的，并受 `dm-verity` 保护；安装软件包、加载任意二进制、加载 out-of-tree 内核模块、JIT 编译模型提供的 kernel 以及等价的运行时修改路径都被禁用。合法软件更新会产生新的镜像和度量值，用户必须重新评估。

**AM6 — 服务商部署针对特定用户或短期存在的恶意镜像，随后删除证据。** 本地API代理只向已登记在只追加账本中的度量值释放提示词。一经记录，恶意发布就会成为永久、可归因到服务商的证据。有意隐藏在已发布源码中的条件后门仍可能逃过不完美审查；CT 对这种残余风险的处理是公开可检测性与威慑，而不是对程序语义的形式化证明。

**AM7 — 服务商通过模型 artifact 提供可执行代码。** 被证明加载器只接受纯数据张量格式，并拒绝 pickle 一类可执行序列化。模型不能提供自定义 GPU kernel、触发运行时 `dlopen`，也不能触发对服务商代码的 JIT 编译；所需 kernel 必须已经存在于被度量镜像中。

**AM8 — 服务商提供畸形的纯数据权重，以利用加载器或 kernel 漏洞。** 不执行代码的表示格式，并不会自动让有漏洞的消费者安全。加载器必须验证张量 offset、shape、dimension、dtype、size 和算术运算，kernel 也必须安全处理所有被接受的值。让恶意数据转化为代码执行的 bug，是已审计可信计算基中的残余漏洞。

**AM9 — 服务商把用户数据编码进响应长度或时序。** 闭源权重或恶意框架逻辑可能调制输出 token 的数量或时序，使服务商或云服务商能从原本加密的流量中观察编码。长度和时序不在基础 **O1** 保证内。消息 padding、固定大小记录、batching 和流量整形可以减弱该通道，但基础设计不要求这些机制。框架中有意实施的调制可能在源码审查中被发现，但 CT 不声称消除所有这类通道。

**AM10 — 服务商静默替换模型或改变模型行为。** 强制性的基础配置不绑定动态加载的权重；只有采用可选目标 **O3** 时，才覆盖静默模型替换。权重中的触发词、行为后门、内容审查规则、幻觉和不安全输出属于模型行为问题，不在 CT 内。

**AM11 — 服务商继续运行已知存在漏洞的镜像，并拒绝撤销。** 服务商不是用户负面安全判断的唯一来源。用户策略可以在本地拒绝该度量值，也可以采纳独立研究人员或审计方签名的安全公告；更严格的策略还可以要求有时限的审计方背书，背书到期而未续期时镜像便不再可接受。账本使这些声明公开且可归因，但账本本身无法判断软件是否存在漏洞。如果客户端没有收到任何来自用户所接受来源的负面信号，利用已审计代码中漏洞的攻击仍属于可信计算基的残余风险。

### 9.3 恶意用户 

恶意用户的大多数攻击都是传统 Model-as-a-Service 攻击，并非机密计算引入。以下五种情况界定了相关边界。

**AU1 — 用户 A 提交畸形请求以利用服务软件栈。** 精心构造的 HTTP、分词器或推理输入可能攻击 parser、内存安全、算术或 GPU-kernel 漏洞。小型公开镜像提高了可审计性并移除了不必要攻击面，但证明不会让被接受代码免于漏洞。这类 bug 是可信计算基的残余风险。

**AU2 — 用户 A 尝试读取用户 B 的会话状态。** 猜测标识符、操纵 batching 或诱导 buffer 复用，都不能暴露 B 的提示词、输出或 KV-cache。被证明的调度器、内存管理器和响应路由器强制执行会话所有权；失败意味着实现 bug 或违反已审计镜像要求。

**AU3 — 用户调用管理接口，或上传代码或替代模型。** 公开推理服务端不暴露管理操作，独立的受约束管理接口会认证模型服务商。正确的认证和接口分离属于已审计可信计算基。

**AU4 — 用户通过合法推理请求攻击模型。** 提示词注入、越狱、训练数据提取、membership inference 和基于查询的模型提取同样适用于普通非机密推理服务。它们涉及模型行为、训练数据隐私或模型知识产权保护，不属于 CT 的运行时机密性保证。

**AU5 — 用户耗尽服务资源。** 超长提示词、过高并发和请求洪泛影响可用性与计费，不影响 CT 的机密性保证，因此不在范围内。

### 9.4 合谋敌手 

当云服务商与模型服务商合谋，或其中任一方与恶意用户合谋时，目标 **O1** 仍然成立。论证的硬件部分和软件部分可以组合：云服务商不能直接读取受保护内存，被接受的软件也不向其作者或其他用户提供携带机密内容的外发路径。

**AX1 — 云服务商和模型服务商是同一实体。** 这是 CT 部署的一种特殊情况，而不是例外。垂直整合的服务商可以同时控制模型、guest 镜像发布、云基础设施和运维人员，但在 CC 与已审计软件假设下，**O1** 仍要求该实体不能取得用户明文。此时 **O2** 不适用：不能保护模型所有者不读取自己的模型。

**AX2 — 云服务商与模型服务商部署修改后的代码，同时展示被批准镜像的证据。** Host 控制权不能让它们伪造硬件签名的度量值、绕过 nonce 新鲜性，或替换为未绑定到报告的通道密钥。如果它们转而发布恶意源码和度量值，其行为就会接受公开审计，并以永久、可归因的方式记录在账本中。

**AX3 — 模型服务商与用户 A 通过 A 的输出外泄用户 B 的内容。** A 的响应是通向 A 的合法明文外发路径，因此响应路由是关键信息流检查点。被审计框架只允许该路径包含由 A 的请求和会话状态派生的数据，不能把 B 的提示词、输出、KV-cache 或中间 buffer 复制进去。即使 A 提供专门设计来触发复制的输入，该保证仍然成立。

**AX4 — 云服务商与模型服务商构造基于资源的隐蔽信道。** 它们可能尝试把用户数据编码进 host 可见的 CPU 利用率、磁盘活动、中断模式或二级页表 fault。源码审查可以发现有意根据秘密数据调制这些资源的代码；一旦部署，账本也会把该代码与服务商绑定。尽管如此，资源和时序侧信道仍在基础 **O1** 保证之外：审计提高了发现有意编程信道的可能性，但不能证明所有隐蔽信道或微架构信道都不存在。

## 10. 对基础设计的扩展 

到目前为止，本文描述的都是**基础设计**：单个 CVM 终结 API 服务端、认证用户、分词、调度一个批次、运行 prefill 和 decode，并对响应做后处理——一台被证明的机器完成全部工作，没有闭源代码，TEE 之外也没有任何服务。这种设置是论证信任的最干净载体，但真实的 LLM 部署在四个独立维度上更复杂。本节添加四个**正交**扩展；一个部署可以采用其中任意子集。每个扩展都保持目标 **O1**（[§3.3](#33-%E5%AE%89%E5%85%A8%E7%9B%AE%E6%A0%87)）——即使合谋，两个服务商也都不能读取用户数据——同时放宽基础设计的某一条简化假设。

第一个扩展分布数据路径；第二个把被度量软件栈的所有权与模型所有权分开。二者都保留 CT 的源码透明要求和 **O1**，单纯改变拓扑或所有权并不会增加安全强度。后两个扩展放宽了 [§5.4](#54-%E5%BC%80%E6%BA%90) “数据路径中的一切都开源”的立场，用 CT 的部分*透明性防御*换取运营现实；第四个扩展放宽得最为激进，最好理解为*限制性防御*（defense-by-confinement）。凡是扩展削弱了某条基础保证之处，都会明确说明。

### 10.1 分布式部署与 TEE 边界 

#### 10.1.1 为什么单个 CVM 不够 

生产级推理服务不是单台机器上的单个进程。它通常涉及：

- 一个或多个**数据库服务器**，保存用户账户、API 密钥、订阅和计费状态；

- 一个专门的**前端 / HTTP** 层，终结客户端连接并按负载均衡策略路由请求；

- 多个 **prefill** 节点和多个 **decode** 节点，每个都带多块 GPU/NPU，通常采用 **prefill/decode 分离**（disaggregation）和共享的 KV-cache 结构。

显而易见的做法——把*每个*节点都放进自己的 CVM——会撞上两堵现实的墙：

- **持久化。** 凭据/计费数据库需要在重启后存活的持久存储。而 CT 数据盘有意是**加密且临时的**（[§5.3](#53-%E5%8A%A0%E5%AF%86%E4%B8%B4%E6%97%B6%E6%95%B0%E6%8D%AE%E7%9B%98)）：其密钥在重启时丢弃，因此什么都不会持久。放在该盘上的数据库会在每次重启时丢失全部状态。

- **可运维性。** 数据库需要日常管理——迁移、备份、索引维护、事故调试。而**受限操作系统**（[§5.1](#51-%E5%8F%97%E9%99%90%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F)）恰恰禁止这类维护所需的交互式 shell 访问。

一旦注意到*数据库并不保存机密用户数据*，这两堵墙就消失了。用户身份、API 密钥和订阅记录是**服务商的**运营数据，不是用户的提示词。它们从来不在 CT 的机密性目标之内。因此数据库可以作为一个普通服务运行在 TEE **之外**，在那里它可以持久化并被正常管理——而只有那些真正接触明文提示词的节点才需要是 CVM。

#### 10.1.2 什么算机密用户数据 

这个扩展迫使 CT 精确陈述基础设计可以含糊带过的边界。**机密用户数据**是 **O1** 所保护的集合：提示词、模型输出，以及任何**可从中恢复二者的中间数据**——embeddings、logits、attention/KV-cache、卸载的KV-cache、交换页，以及任何由它们派生的日志或缓冲区。**处理机密用户数据的代码必须运行在 TEE 内部**——被证明、开源、可复现构建、登记在账本中——与[§5](#5-%E4%BF%9D%E6%8A%A4%E7%94%A8%E6%88%B7%E4%B8%8D%E8%A2%AB%E6%A8%A1%E5%9E%8B%E6%9C%8D%E5%8A%A1%E5%95%86%E6%94%BB%E5%87%BB) 完全一致。

*不是*机密用户数据的数据可以在 TEE 之外处理。API 密钥、账户标识符、订阅档次和计费计数器都是服务商运营数据：知道某个用户的 API 密钥并不会泄露该用户向模型问了什么。在示例拓扑中：

#### 10.1.3 审计流出 TEE 的信息 

CT 不禁止 CVM *与*外部世界*通信*——它约束的是 CVM*能说什么*。这与已经施加在管理接口和日志/监控指标路径上的纪律相同（[§5.1](#51-%E5%8F%97%E9%99%90%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F)、[§5.6](#56-%E9%80%8F%E6%98%8E%E8%B4%A6%E6%9C%AC)）：**任何离开 TEE的信息都跨越一个被监看的表面，且必须在开源代码中可审计。** 服务间调用只是该表面的又一个实例。

激励性的例子是**认证**。前端 CVM 收到一个携带 API token 和提示词的请求。为了对其授权，CVM 必须查询 TEE *之外*的用户数据库。执行这次查询的代码是被证明、开源镜像的一部分，它的编写和审查必须保证**只有 API token 离开 CVM，提示词或任何由其派生的东西绝不离开**。这与[§5.4](#54-%E5%BC%80%E6%BA%90) 的信息流义务相同，现在应用到对等服务而不是日志或 API响应：被审计的问题从来不是字节*可以去哪里*，而是它们*被允许包含什么*。一个悄悄把提示词字节附加到认证请求上的查询函数，会在公开源码中可见，并在账本中记录到服务商名下（[§5.7](#57-%E6%89%80%E6%9C%89%E4%BA%BA%E9%83%BD%E8%83%BD%E7%9C%8B%E5%88%B0%E7%9A%84%E5%90%8E%E9%97%A8)），就像任何其他外泄路径一样。

#### 10.1.4 集群证明 

*确实*处理明文的那些 CVM 组成一个**机密计算集群**，用户必须能够把集群作为整体来证明，而不只是它恰好连接的那一个节点。CT 不强制规定某个具体的集群证明协议——CC集群已有若干现成协议——但它要求任何此类协议满足三个属性：

- **整集群证据。** 交给用户的证明报告包含集群中**每一个**处理其数据的节点的硬件与软件 quote（按 [§6.3](#63-%E8%AF%81%E6%98%8E%E6%8A%A5%E5%91%8A%E5%BF%85%E9%A1%BB%E5%8C%85%E5%90%AB%E4%BB%80%E4%B9%88)），而不是单个代表节点。

- **加密的 CVM 间链路。** 任意两个 CVM 之间的通信都被加密，并终止于各自的 TEE 内部，因此云服务商在内部结构上只看到密文，就像在客户端链路上一样。

- **互相证明门控。** 两个 CVM 只有在**都出现在交给用户的证明报告中**时才能交换用户数据。这是面向用户的关键保证：用户被告知*所有*将看到其数据的节点，任何不在被证明集合中的节点都不能被悄悄插入数据路径。

这扩展了 [§6.4](#64-%E9%AA%8C%E8%AF%81%E6%B8%85%E5%8D%95) 的验证清单：客户端/代理只有在数据路径上每个节点都被证明、当前符合用户的验证策略，且出现在一份绑定到会话 nonce 的连贯报告中时，才接受。

#### 10.1.5 这不保护什么 

把认证移到 TEE 之外是有代价的，需要诚实说明：**请求元数据不再受保护。** 提示词的*内容*仍然机密，但用户 A 在时间 T 发起请求这一*事实*——以及其粗粒度的时间和大小——对 TEE之外的认证和路由层是可见的。CT 保护用户说了什么，而不保护用户说了某些话这一可观察事实。（记录于 [§11](#11-%E9%99%90%E5%88%B6%E5%92%8C%E5%BC%80%E6%94%BE%E9%97%AE%E9%A2%98)。）

### 10.2 分离被度量软件栈：一种机密洁净室配置 

**机密洁净室（confidential clean room, CCR）**是一种受硬件保护的环境：互不信任的参与方只有在验证将约束其输入或计算的代码与策略后，才贡献敏感内容。公开的 CCR 架构已把这种模式用于多方分析、机器学习训练和推理（[DEPA](https://depa.world/training/architecture)；[Azure](https://learn.microsoft.com/en-us/azure/confidential-computing/confidential-clean-rooms)）。本文把 *CCR* 用作厂商中立的架构描述，而不是某个特定产品的名称或一项正式标准。

CT 可以通过拆分基础设计中由同一个模型服务商承担的两个角色，部署为一种专用于 LLM 推理的 CCR。**CT软件栈发布者（CT stack provider）提供完整的被度量 guest 软件镜像，包括受限操作系统、内核、设备驱动、证明组件、推理框架、API 服务端和受约束的管理平面。一个或多个**模型服务商在独立验证部署的证明证据后，提供纯数据模型。用户在释放提示词前验证同一个部署，云服务商则继续提供不可信基础设施。这里定义的是四类*角色*，并非固定四方：一个 CT 软件栈实例可以服务多个用户和来自多个模型服务商的多个模型。

角色分离不是一种新的安全机制；它改变的是所有权和问责关系，而不是 CT 的安全论证。CT软件栈发布者现在编写那些可能错误处理用户数据的代码，因此受到与基础设计中模型服务商相同的受限镜像、开源、可复现构建、证明和透明账本机制约束。模型服务商不再编写或拥有 guest 软件栈，但其权重仍对 CT软件栈发布者和云服务商保密。两个角色都不能交互式访问运行中的 CVM；用户得到的机密性保证仍然是：被证明软件栈不会向 CT软件栈发布者、任何模型服务商或云服务商暴露提示词、输出和中间数据。

被度量软件栈分别暴露面向用户和面向模型服务商的接口。前者承载证明证据和推理请求；后者接收纯数据模型，以及 [§5.1](#51-%E5%8F%97%E9%99%90%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F) 允许的有限生命周期操作。每个模型服务商都在上传模型前独立验证证明证据，不要求另设密钥管理服务。模型服务商的凭据和管理操作受到作用域限制，使每个服务商只能管理自己的模型。

推理请求标明所需模型，并携带对应模型服务商签发的凭据。被证明框架把该标识符解析到该服务商已登记的模型并据此路由请求；响应则按照 [§7.6](#76-%E6%A8%A1%E5%9E%8B%E7%BB%91%E5%AE%9A%E8%AF%81%E6%98%8E%E6%89%BF%E8%AF%BA%E6%88%96-api-metadata) 标明实际使用的模型。CT 不规定模型是同时常驻，还是按需加载和卸载；只要切换模型不会把一个服务商的权重或一个用户的状态暴露给另一方，两种策略及其组合都有效。

软件栈可以选择跨请求保留**按用户隔离的 KV-cache**。模型服务商定义其模型允许的 KV-cache 隔离选项，用户可以从中选择，或采用更严格的策略，包括禁用复用。用户释放提示词前，被证明框架会对选定的隔离域进行认证。KV-cache 条目同时绑定到该隔离域，以及确切的服务商和模型标识。禁止跨用户、跨服务商和跨模型复用 KV-cache；请求批处理本身并不构成 KV-cache 复用。

与只执行一次获批计算、随后销毁的洁净室不同，LLM 服务长期运行，并对反复发起的请求分别计费。因此 CT 允许被证明推理框架调用洁净室之外的服务，但须遵守 [§10.1.3](#1013-%E5%AE%A1%E8%AE%A1%E6%B5%81%E5%87%BA-tee-%E7%9A%84%E4%BF%A1%E6%81%AF) 的外发审计规则。

发送到外部的用量信息标明服务商账户和模型，并包含计费所需的 token 数量。启用 KV-cache 复用时，除了普通输入和输出 token 数量，还包括**缓存输入 token 数量**（cached-input-token count）。其中还可以包含计费所需的其他有界元数据，但绝不能包含提示词、输出、KV-cache 内容或其他由内容派生的数据。这必然会向洁净室之外暴露有限的请求元数据，但不会暴露请求内容。

### 10.3 由可信权威机构审查 

基础设计让推理框架**公开**（[§5.4](#54-%E5%BC%80%E6%BA%90)），使*任何人*都能阅读它，后门*必然可被发现*（[§5.7](#57-%E6%89%80%E6%9C%89%E4%BA%BA%E9%83%BD%E8%83%BD%E7%9C%8B%E5%88%B0%E7%9A%84%E5%90%8E%E9%97%A8)）。完全公开披露是强力威慑，但它要求服务商交出自己在推理栈上投入的工程成果。一个替代方案用审查广度换取代码的保密性：服务商不公开源码，而是在 NDA 下把它披露给**一个或多个可信权威机构**，并以法律条款防止它们窃用专有框架。

保持不变的内容和改变的内容同样重要：

- **可复现构建**（[§5.5](#55-%E5%8F%AF%E5%A4%8D%E7%8E%B0%E6%9E%84%E5%BB%BA)）和**透明账本**（[§5.6](#56-%E9%80%8F%E6%98%8E%E8%B4%A6%E6%9C%AC)）的运作完全照旧。权威机构检出源码提交 `C`，确认它可复现地构建为度量值 `M`，并**把这个绑定签名进账本**。基础设计本来就允许账本携带“第三方审计方对特定提交的签名”（[§5.6](#56-%E9%80%8F%E6%98%8E%E8%B4%A6%E6%9C%AC)）；这个扩展把那个可选签名提升为*主要*证据。

- 用户的流程（[§6](#6-%E8%AF%81%E6%98%8E%E5%92%8C%E5%AF%86%E9%92%A5%E9%87%8A%E6%94%BE%E5%AE%A2%E6%88%B7%E7%AB%AF%E4%BE%A7%E6%B5%81%E7%A8%8B)）保持不变，只是在清单第 4 步*信任什么*有所不同：用户验证度量值 `M` 出现在账本中，并**携带有效的权威机构签名**，而不是自己阅读源码。

信任转移是明确的：制度从“**任何人**都能发现后门”变成“**权威机构**能发现后门，并以签名押上自己的声誉”。这严格来说更弱——它依赖权威机构的能力、独立性，以及不与服务商合谋——但比“相信服务商”强得多。使用**多个独立权威机构**并采用*m-of-n* 签名门限，可以降低单点信任的顾虑，并提高合谋成本。如今的威慑，是权威机构对一份后来被证明含有后门的代码所出具的清白证明上那个永久、可归因的签名。

### 10.4 在沙箱中运行闭源代码 

[§7.4](#74-ct-%E8%A7%84%E5%88%99%E5%8F%8A%E5%85%B6%E6%89%A7%E8%A1%8C%E6%96%B9%E5%BC%8F)划了一条红线：只有权重和超参数可以闭源；**任何能接触明文的代码都必须开源**。然而，服务商在自定义推理框架逻辑上投入巨大，合理地希望把其中一部分作为竞争优势保密。这个扩展允许*有限*数量的闭源、接触明文的代码进入——不是通过信任其内容，而是通过**对它做沙箱隔离，并严格控制进出它的信息**。这是CT 唯一一处*限制性防御*而非*透明性防御*。

**一个具体的例子。服务商想实施**提示词审查：一个预处理步骤检查每条提示词，决定接受还是拒绝。公开代码及其黑名单会适得其反——用户只需换种说法绕过过滤器——因此服务商需要把这段逻辑*闭源*运行，即使它读取明文提示词。

**机制。**

- **沙箱启动器是开源的**，并像框架的其他每一部分一样被度量/证明（[§5.2](#52-%E5%8F%AA%E8%AF%BB%E7%B3%BB%E7%BB%9F%E9%95%9C%E5%83%8F--dm-verity)）。只有*沙箱启动器*——也就是限制闭源代码的那个东西——需要被信任，而它是完全可审计的。

- 沙箱启动器实例化一个 **WebAssembly（wasm）** 沙箱。（wasm 是示例；Native Client 是另一种选择。）专有审查二进制通过管理接口**上传进 CVM**（[§5.1](#51-%E5%8F%97%E9%99%90%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F)）——和模型权重一样，它是启动后送入的数据，绝不是被度量镜像的一部分。

- 沙箱保证 wasm 代码**不能读取或写入沙箱之外的任意内存。** 所有 I/O 都由入口函数原型固定；在本例中，*全部*输出就是**一个比特**——接受或拒绝。闭源代码看到提示词，并能返回那一个比特，除此之外别无其他。

- 一个沙箱实例**只处理一个用户的数据**，由沙箱启动器强制执行，因此闭源代码不能跨用户积累或关联数据（没有跨用户泄漏）。

- 沙箱启动器的设计必须保证沙箱**不能通过隐蔽信道把信息泄漏出 TEE**——一段试图把提示词比特编码进宿主机可见的 CPU 利用率模式、时序或内存占用的恶意 wasm 载荷必须被遏制。

**现有工作。** [Hunt 等人的 *“Ryoan: A Distributed Sandbox for Untrusted Computation on Secret Data”*](https://www.usenix.org/conference/osdi16/technical-sessions/presentation/hunt)（OSDI 2016）在 SGX enclave 上确立了本质上相同的模式——限制不可信代码，使其可以在机密数据上计算而不外泄。CT 把这一思想扩展到基于虚拟机的机密计算。

**直白的表述。** 在其他所有地方，CT 信任的是*开放、已审查的代码会守规矩*；而在这里，它信任的是*开放、已审查的沙箱启动器会限制它看不到的代码*。这个保证的强度只等于沙箱启动器的隔离和侧信道缓解的强度。让这一点可以接受的，是**限制本身是可审计的，即使被限制的代码不可审计**：对闭源代码所能做之事的约束本身是公开、被证明并登记在账本中的。服务商保留了它的秘密逻辑；用户保留了一个可验证的上界——每条提示词一个输出比特、每个实例一个用户——约束那段逻辑所能泄露的一切。

## 11. 限制和开放问题 

CT 是一种边界清晰的机密性与完整性机制，不是万灵药。诚实地说：

- **侧信道。** 时序、功耗、内存访问模式和资源争用可以在不解密内存的情况下泄漏信息。CC 和 CT 不关闭这些问题；它们是活跃研究前沿。

- **模型行为。** CT 不处理幻觉、提示词注入、越狱或权重中的行为后门（[§7.5](#75-%E6%9C%AC%E6%96%87%E4%B8%8D%E8%A6%86%E7%9B%96%E4%BB%80%E4%B9%88)）。纯数据执行规则阻止*文件*泄漏；它不管*数字*会做什么。

- **可用性。** 云服务商可以任意拒绝服务或释放节点；CT 不保护运行时长。

- **硬件厂商信任。** 信任根*就是*信任。如果 CPU/GPU TEE 有缺陷，或厂商远程证明 PKI 被攻破，上层一切都会被削弱。

- **账本治理。** “只追加且公开”是必要条件，但带来真实问题：谁运营日志，如何监控，如何衡量审计方签名的权重，发现后门后多快采取行动。CT 借用了 Certificate Transparency 的机制，也继承了 CT 的治理挑战。

- **证明标准化和拓扑。** 多 GPU、多节点、NVLink/NVSwitch 域和 AI agent 工具链都让“把 CPU 和每个加速器绑定到同一个已验证会话”更复杂。TEE-I/O（[§4.6.1](#461-%E6%AD%A3%E5%9C%A8%E5%BD%A2%E6%88%90%E7%9A%84%E6%A0%87%E5%87%86tee-iotdisp--tsm)）正在成熟，但还未无处不在，跨厂商远程证明格式也仍在稳定。

- **客户端信任。** 被攻破的 coding agent、被攻破的本地API代理，或用户把秘密贴到错误服务端，都会在密码学机制开始前击败 CT。

- **分布式部署中的元数据。** 当用户认证、路由或计费运行在 TEE 之外时（[§10.1](#101-%E5%88%86%E5%B8%83%E5%BC%8F%E9%83%A8%E7%BD%B2%E4%B8%8E-tee-%E8%BE%B9%E7%95%8C)、[§10.2](#102-%E5%88%86%E7%A6%BB%E8%A2%AB%E5%BA%A6%E9%87%8F%E8%BD%AF%E4%BB%B6%E6%A0%88%E4%B8%80%E7%A7%8D%E6%9C%BA%E5%AF%86%E6%B4%81%E5%87%80%E5%AE%A4%E9%85%8D%E7%BD%AE)），提示词*内容*仍受保护，但请求*元数据*不受保护：某个用户在某个时间发起了请求这一事实，以及其粗粒度的时间和大小，在信任边界之外可被观察到。

CT *真正*交付的，是把信任面从“相信两整家公司及其管理员”缩小到“相信一些芯片、一些公开源码、一个可复现构建、一个透明日志和你自己的客户端”。这不是全部，但已经很多。
