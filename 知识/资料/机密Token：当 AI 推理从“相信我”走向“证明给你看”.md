<div><div><style></style><style></style><div class="style_m_contentBox__pcPrz style_m_stylePC__Ta0rc undefined markdown-preview" id="content"><p><strong>我们到底把什么交给了 AI？</strong></p>
<p>你问 AI：“帮我润色一下简历。”它看到了你的工作经历、学校、电话、邮箱和职业焦虑。你问 AI：“帮我看看这个合同有没有坑。”它看到了交易金额、合作方、法律条款和违约责任。你问 AI coding agent：“帮我修一下这个 bug。”它可能看到了你的代码仓库、数据库 schema、内部 API、客户字段、测试日志，以及某个前同事三年前留下的那句注释：“TODO: 临时方案，等融资后重构。”</p>
<p>很多模型提供商会告诉你，“我会尊重你的隐私。”这句话很好。但它和很多 SaaS 登录页上的“企业级安全”一样，有一种熟悉的味道。不是说它一定不可信。而是说，真正敏感的数据面前，我们想要的不只是一句“相信我”，而是“证明给我看，你真的看不到。”</p>
<p><img src="https://2012labs.huawei.com/spark/media/v1/image/preview/f579d7e3-e0bb-4644-972f-813233bfaa86_1448x1086.png" alt="ChatGPT Image May 22, 2026, 03_11_39 PM.png" style="background-color: rgb(255, 255, 255);"></p>
<hr>
<p><strong>今天的 AI 隐私，很多时候还是“承诺型隐私”</strong></p>
<p>现在主流 AI 服务当然不是完全没有隐私保护。很多平台会告诉企业用户：你的数据默认不会用于训练，你的提示词不会被人工查看，你的代码不会被用于改进模型，你的企业数据会被隔离，你也可以关闭某些数据共享开关。这些承诺很重要，但承诺有一个天然问题：它约束的是服务商应该怎么做，而不是服务商能不能做到别的事。</p>
<p>如果规则改变了呢？如果某个产品线默认设置变了呢？如果日志系统多记了一点东西呢？如果某个代理层、监控系统、调试工具、异常采样流程意外记录了敏感内容呢？如果公司今天承诺不训练，明天产品条款调整为“默认用于改进服务，可手动关闭”呢？这不是阴谋论，而是软件服务的日常。</p>
<p>隐私政策、企业合同、合规审计都很重要，但它们本质上还是要求用户相信服务商：相信它的制度，相信它的工程实现，相信它的内部权限，相信它的员工，相信它的未来政策不会改变，也相信它的所有依赖方都不会出错。而 AI 的问题在于，用户给出去的上下文越来越敏感。一旦提示词里放进去的是源代码、客户数据、病历、合同、并购计划，单纯的“我们承诺不会滥用”就会显得不够。</p>
<hr>
<p><strong>代码助手让这个问题变得更尖锐</strong></p>
<p>聊天机器人已经足够敏感，AI coding agent 更刺激。因为它不只是看你粘贴的一小段代码。为了真正帮你干活，它需要上下文。上下文越多，它越聪明；上下文越多，你暴露的资产也越多。</p>
<p>它可能读整个 repo，读 package-lock.json，读 CI/CD 配置，读API key，读错误日志，读数据库迁移文件，读内部接口文档，也可能读到那些“千万别给客户看的临时 hack”。对个人用户来说，提示词可能是隐私；对公司来说，提示词可能就是核心资产。这也是为什么 AI coding agent 会让很多企业又爱又怕：不用，效率落后；用，又担心核心资产被送进别人的模型工厂。</p>
<p>这个矛盾不会因为一句“不用于训练”就消失。AI 越有用，它越需要真实上下文；上下文越真实，它越接近用户最不想泄露的东西。</p>
<p><img src="https://2012labs.huawei.com/spark/media/v1/image/preview/1659a8c4-76d3-4913-88fa-7b23a781976f_1448x1086.png" alt="ChatGPT Image May 22, 2026, 03_12_16 PM.png" style="background-color: rgb(255, 255, 255);"></p>
<hr>
<p><strong>自建模型：最安心，也最像为了吃夜宵自己造厨房</strong></p>
<p>一个直接的解决方案是：别用外部 MaaS，自己部署模型。公司买 GPU，搭推理集群，部署开源模型，把数据留在内网。这当然可以。金融、医疗、芯片、法律、政府等场景里，很多团队已经在这么做。</p>
<p>问题是，这条路很贵，也很累。你需要买 GPU，管驱动，管模型，管推理框架，管弹性，管监控，管升级，管利用率。流量低的时候 GPU 在机房里烤空气；流量高的时候用户会抱怨：“为什么 AI 又排队了？”自建模型像自建发电厂：最安心，最可控，但不是每家公司都应该为了每个插座养一座电厂。</p>
<p><img src="https://2012labs.huawei.com/spark/media/v1/image/preview/e3e32064-b2f3-4b90-8e3f-586c2b6ce5a7_1448x1086.png" alt="ChatGPT Image May 22, 2026, 03_11_59 PM.png" style="background-color: rgb(255, 255, 255);"></p>
<hr>
<p><strong>机密计算：不是让云变可信，而是假设云不完全可信</strong></p>
<p>这里轮到机密计算出场。传统上，我们已经比较会保护两种数据：数据在硬盘上，可以加密；数据在网络里，可以用 TLS。但 AI 推理时，数据必须被计算。提示词要进入内存，中间状态要被处理，response 要被生成，KV cache 或 output tokens 也可能包含大量上下文。这叫使用中的数据。</p>
<p>机密计算要保护的，就是使用中的数据。它的基本思路是：不要求你完全相信云服务商，而是把明文数据放进一个硬件隔离的执行环境里。云管理员、宿主机系统、其他租户，甚至 MaaS 提供方本身，都不应该直接看到里面的明文。</p>
<p>这和传统云安全的思路有点不同。传统云安全常常是在问：这个云厂商可信吗？权限配置对不对？日志有没有脱敏？员工有没有访问控制？机密计算问的是另一个问题：就算这些外部环境不完全可信，数据还能不能安全地被计算？</p>
<p><img src="https://2012labs.huawei.com/spark/media/v1/image/preview/53b9575b-faff-4e41-bcc8-8725aa6c1511_1448x1086.png" alt="ChatGPT Image May 22, 2026, 03_12_26 PM.png" style="background-color: rgb(255, 255, 255);"></p>
<hr>
<p><strong>可是 SGX、SEV、TDX 不是早就有了吗？为什么这次不一样？</strong></p>
<p>这是一个专业读者很可能会问的问题。SGX、SEV、TDX 这些技术确实不是昨天才出现的，CPU 机密计算已经讨论、商用、上云很多年了。但过去很多机密计算应用一直没有大规模爆发，原因并不神秘：很多业务对“使用中的数据保护”的付费意愿不够强，TEE 开发、部署、证明、调试都复杂，性能、生态、工具链、云支持也不统一。很多应用即使没有 TEE，也能靠合规、内网、权限控制勉强过日子。</p>
<p>所以问题是：机密Token会不会也变成另一个“很酷、很安全、但没人真的用”的技术？我认为这次有几个不同点。</p>
<p>第一，AI 把“使用中的数据”变成了核心问题。过去很多云应用处理的是结构化数据，权限边界相对清楚。AI 不一样。AI 的价值来自上下文，而上下文本身就可能是隐私和商业机密。</p>
<p>第二，AI 推理天然适合按次计量。过去你很难把“安全计算”包装成一个用户直接理解的商品，但 token 本来就是 AI 世界的计量单位。把安全属性附加到 token 上，比把 TEE 卖成一套复杂基础设施更自然。</p>
<p>第三，NPU/GPU 机密计算补上了大模型的关键短板。CPU TEE 只能保护 CPU 侧，但大模型推理真正的高强度计算主要发生在 NPU/GPU 上。如果加速器、显存、CPU-NPU 通道不在保护范围里，机密 AI 就不完整。</p>
<p>第四，AI 隐私现在是用户能感知的问题。用户可能不懂 TDX，但用户懂“我不想让我的代码被拿去训练”；用户可能不懂远程证明，但用户懂“你能不能证明你没看到我的提示词”。过去机密计算经常在卖“更安全的基础设施”，而机密Token卖的是一个更直接的东西：这次 AI 推理，你的秘密没有裸奔。</p>
<hr>
<p><strong>AI 的特殊之处：NPU 才是干活的人</strong></p>
<p>对普通应用来说，CPU 机密计算已经很有价值。但对大模型来说，CPU 很多时候只是指挥官，真正搬砖的是 NPU 或 GPU。如果提示词在 CPU 里很安全，但一到 NPU、显存、PCIe/UB、驱动、推理进程就暴露，那端到端的私密推理仍然不完整。</p>
<p>所以机密 AI 需要的不只是 CPU TEE。它还需要 CPU 侧的机密虚拟机，NPU 侧的机密计算模式，CPU 和 NPU 之间的安全通道，NPU 和驱动、固件、推理框架之间的度量和证明，以及多卡或多设备场景下的设备证明。换句话说，CPU 保险柜很重要，但大模型真正算 token 的地方，是 NPU 保险柜。</p>
<p><img src="https://2012labs.huawei.com/spark/media/v1/image/preview/76dc957a-ecc4-40c2-945e-54c347c5739f_1448x1086.png" alt="ChatGPT Image May 22, 2026, 03_12_34 PM.png" style="background-color: rgb(255, 255, 255);"></p>
<hr>
<p><strong>MaaS 机密计算的雏形已经出现</strong></p>
<p>最近已经有一些服务开始尝试把 TEE 和模型服务结合起来。比如 Chutes、Tinfoil、RedPill、Phala 等 MaaS 或 AI 基础设施提供方，都在不同程度上宣传 TEE、Confidential GPU、remote attestation、verifiable private AI 等能力。</p>
<p>这些产品还不是终局。它们的证明流程、开源范围、模型锁定方式、用户体验、性能开销、商业模式，都还有很多地方需要演进。但它们说明了一件事：MaaS 正在从“请相信我的隐私政策”，走向“请验证我的推理环境”。这就是 MaaS 机密计算的雏形。</p>
<hr>
<p><strong>什么是机密Token？</strong></p>
<p>我们可以给它一个简单定义：机密Token，是在经过远程证明的机密计算环境中生成的模型输入/输出 token。它不仅代表一次模型推理的计算结果，也携带关于硬件、软件、模型和数据可见性的安全保证。</p>
<p>普通 token 只告诉你模型输出了什么。机密Token还告诉你：它是在什么环境里输出的，谁能看到输入，谁能看到输出，运行的是不是你指定的推理栈，模型有没有被偷偷替换，这次推理有没有对应的证明。</p>
<p>未来我们买 AI token，可能不只看价格、延迟、吞吐、上下文长度和模型榜单分数，还要看它是否运行在 TEE 中，是否支持远程证明，CPU 和 NPU 是否都在证明范围内，推理框架是否开源，构建是否可复现，证明是否绑定模型，是否有透明日志，以及是否能证明服务商看不到提示词和模型输出。</p>
<p>这有点像 HTTPS 改变了网页。早期你访问网站，浏览器只是把页面显示出来。后来你会看地址栏的小锁。未来你调用模型，也许 SDK 会告诉你：本次推理已验证；硬件是 TDX + Confidential NPU；软件度量匹配公开源码；模型是指定版本，未替换；明文可见方仅限 TEE 内部。</p>
<hr>
<p><strong>机密Token需要证明什么？</strong></p>
<p>一个真正有意义的机密Token，至少需要回答四个问题：设备是不是真的，软件是不是对的，软件有没有被审查，模型有没有被绑定。</p>
<p>设备认证回答的是硬件真实性问题。用户需要确认推理运行在支持机密计算的 CPU 和 NPU 上，而不是普通虚拟机或普通加速卡里。这需要硬件可信根、CPU attestation、NPU attestation、固件版本、启动状态等证明。</p>
<p>软件度量回答的是运行环境完整性问题。即使硬件是真的，如果里面运行的是一个偷偷记录提示词的代理程序，也没用。所以需要证明 OS、推理框架、API gateway、日志组件、模型加载逻辑、密钥管理逻辑等软件都是预期版本。这里的 OS 也不只是“跑了某个镜像”那么简单，还要证明它是一个受限操作系统（Locked-down OS or Hardened OS）：没有普通登录界面，没有 SSH，没有调试 shell 或远程运维入口，只暴露受证明策略约束的 MaaS HTTP 接口。否则，即使推理框架本身干净，管理员也可能通过登录、调试、crash dump 或临时运维接口接触到用户数据。</p>
<p>软件审查回答的是“这份被度量的软件是否值得信任”的问题。远程证明通常证明机器上运行的是某个 hash 的二进制，但人类审查的是源码。要让这两者连起来，就需要开源、可复现构建、公开账本或透明日志，以及安全研究员和权威机构的审查。</p>
<p>模型绑定回答的是模型身份问题。如果用户以为自己调用的是强模型，服务商却偷偷换成便宜模型，这也是一种欺骗。机密Token最好能绑定模型身份，至少证明本次推理加载的是某个指定模型、指定版本、指定权重摘要，或者由某个可验证的模型加载策略保证。</p>

<hr>
<p><strong>怎么实现：从承诺链变成证明链</strong></p>
<p>机密Token的目标不是只在营销页面上写“confidential”，而是把一次模型推理拆成可以验证的技术环节。今天很多 AI 服务的信任链是这样的：用户相信模型商，模型商相信云厂商，云厂商相信管理员，管理员相信配置和流程不会出错。这不是说它一定不安全，但它是一条承诺链。</p>
<p>机密Token想要的是证明链。硬件产生证明，启动链被度量，OS 和推理框架被度量，构建产物可以从源码复现，源码和度量值被登记到透明日志或 ledger，用户或第三方 verifier 检查证明，验证通过后客户端才释放提示词的解密密钥。服务端生成 response 后，response 还可以带签名或证明绑定。这个变化的核心是：MaaS 提供方仍然可以提供算力、模型和服务，但不能在 TEE 外部看到用户明文。</p>
<p><img src="https://2012labs.huawei.com/spark/media/v1/image/preview/88836ceb-77b0-4d56-baab-e5399d75bcfd_1774x887.png" alt="ChatGPT Image May 22, 2026, 03_12_48 PM.png" style="background-color: rgb(255, 255, 255);"></p>
<hr>
<p><strong>开源所有能接触明文的软件</strong></p>
<p>机密Token的关键不是“把一切都开源”。模型权重可以是 MaaS 提供方的核心资产，不一定要开放。但所有能接触用户明文、影响控制流、记录日志、发网络请求的软件，都应该尽可能开源并可审计。</p>
<p>这包括 API gateway 中运行在 TEE 内的部分、attestation agent、密钥协商组件、请求解密组件、提示词预处理、tokenizer、推理服务器、模型加载器、KV cache 或 output buffer 管理逻辑、response postprocessor、日志和 metrics 组件、TEE 内部 OS image、启动脚本、安全策略配置和网络 egress policy。</p>
<p>为什么模型权重可以和这些软件区别对待？因为权重通常不像 OS 或推理框架那样能直接打开 socket、写文件、上传日志、分叉进程或调用云 API。但这不等于“模型权重没有安全问题”。模型仍然可能有行为后门、触发词、投毒、恶意输出模式，或者在特定输入下产生攻击性行为。更准确的边界是：防止提示词被服务商窃取，重点要验证所有能执行控制流的软件；防止模型行为作恶，还需要模型评测、模型锁定和输出安全机制。</p>
<hr>
<p><strong>可复现构建：把源码、镜像和度量值连起来</strong></p>
<p>远程证明通常证明的是机器上运行的二进制、镜像、启动度量，但人类审计的是源码。中间缺一座桥，这座桥就是可复现构建 (reproducible builds)。</p>
<p>没有可复现构建时，用户最多知道服务器跑了某个 hash 的二进制。但这个二进制从哪里来？是不是由公开源码构建？构建环境有没有被污染？编译器、依赖、基础镜像是不是一致？构建脚本有没有临时下载未知文件？这些都不清楚。</p>
<p>有了可复现构建，安全专家可以从公开源码构建出同样的二进制，再和 TEE 证明里的度量值对应起来。于是远程证明不再只是一串 hash，而变成一句更有意义的话：这个 TEE 里运行的，就是大家审计过、可以复现构建的那份代码。</p>
<p><img src="https://2012labs.huawei.com/spark/media/v1/image/preview/1768bacc-4e53-4d66-853c-e5ad3a17d089_1448x1086.png" alt="ChatGPT Image May 22, 2026, 03_12_57 PM.png" style="background-color: rgb(255, 255, 255);"></p>
<hr>
<p><strong>透明日志或 ledger：防止“给专家看 A，给用户跑 B”</strong></p>
<p>只开源还不够。如果服务商给安全专家看的代码是 A，实际给用户远程证明的是 B，那用户仍然被骗了。所以需要一个公开、不可抵赖、可审计的记录系统。它可以是区块链 ledger，也可以是 append-only transparency log，也可以是软件供应链透明日志，还可以是由多个审计方共同维护的公证系统。</p>
<p>关键不是“必须上链”，而是被审计的源码、构建产物、度量值、模型版本、证明策略，需要被放进一个事后难以篡改、事前难以定向欺骗的公开记录里。透明日志中至少应该记录 source repository、source commit、build recipe、builder identity、dependency manifest、container image digest、OS image digest、inference binary hash、TEE measurement、NPU firmware policy、model identifier、model weight digest 或模型承诺值、attestation policy version，以及可选的 auditor signature。</p>
<p>这样，用户拿到 attestation evidence 后，不是孤立地检查一个 quote，而是把 quote 放回公开记录系统里验证。</p>
<hr>
<p><strong>远程证明：用户先验明正身，再交秘密</strong></p>
<p>远程证明是机密Token的核心交互。一个典型流程如下：客户端生成 nonce，然后请求 MaaS endpoint 返回 attestation evidence。TEE 内部的 attestation agent 收集 CPU quote，NPU attestation agent 收集 NPU quote 或 NPU 证明材料，服务端返回软件 measurement、启动状态、固件版本、运行策略和模型标识。客户端或 verifier 检查 quote 的签名链，检查 nonce 防止重放，检查硬件型号和安全能力是否满足策略，检查固件版本是否在允许列表中，检查 TEE measurement 是否存在于透明日志中，检查 OS 配置是否符合受限策略，例如无登录入口、无 SSH、无调试接口、仅暴露 MaaS HTTP 接口，检查模型标识是否匹配用户请求，并检查 CPU TEE 与 NPU TEE 是否绑定到同一推理会话。</p>
<p>验证通过后，客户端与 TEE 建立加密会话并发送加密提示词。TEE 内部解密提示词，NPU 在机密模式下完成推理，response 返回给客户端，并最好附带签名，证明它来自刚才那个已验证环境。这一步的精神很简单：不是用户先交秘密，再祈祷服务商守规矩；而是服务商先出示证明，用户再交秘密。</p>

<p><strong>CPU、NPU 和设备通道要一起进信任边界</strong></p>
<p>机密 AI 比普通机密计算更麻烦，因为它不只是 CPU 里的一个进程。它涉及 CPU TEE、NPU TEE、NPU driver、NPU firmware、显存或片上内存、PCIe/UB 通道、多设备拓扑、多节点拓扑、模型权重加载、KV cache、output tokens 和流式输出。</p>
<p>如果只有 CPU 被证明，NPU 没有被证明，推理路径就有缺口。如果 CPU 和 NPU 都被证明，但两者之间的数据通道没有保护，明文也可能在路上暴露。如果推理框架被证明，但模型加载逻辑没有绑定模型 digest，服务商可能偷换模型。如果 response 没有绑定证明会话，用户可能无法确认输出来自刚才验证过的环境。</p>
<p>因此，机密Token至少需要覆盖这些安全边界：CPU 内存中的提示词明文，CPU 到 NPU 的传输路径，NPU 内存中的 tensor 和中间状态，模型权重加载路径，推理服务进程，response 生成和签名路径，以及日志、metrics、crash dump、debug 接口。普通用户不需要理解每个缩写，他们只需要知道一句话：真正的机密Token，不应该只证明“入口是安全的”，而要证明“token 生成链路是安全的”。</p>
<hr>
<p><strong>模型锁定：防止“你买的是强模型，跑的是便宜模型”</strong></p>
<p>隐私不是机密Token的唯一价值，另一个重要附加保证是模型锁定。MaaS 是一个典型的信息不对称市场。用户请求的是某个强模型，服务商实际运行的是什么，用户不一定知道。在普通 MaaS 中，用户通常只能通过输出质量猜测，但输出质量不是证明。</p>
<p>机密Token可以把模型身份纳入证明链。可选做法包括模型权重大小、模型 manifest、模型加载器 measurement、模型版本、推理服务启动时的模型加载证明，以及 response metadata 中绑定 model id 和 attestation session id。这样可以做到在模型权重不公开的情况下锁定模型metadata。</p>

<p><strong>机密Token会改变 token 经济学</strong></p>
<p>今天我们比较模型服务，常常看这些指标：每百万 token 多少钱，首 token 延迟多少，吞吐多少，上下文多长，模型能力多强，是否支持多模态。但如果提示词里是并购计划、芯片设计、客户病历、源代码、法律意见、交易策略，那还应该多一个维度：这个 token 安全吗？</p>
<p>未来可能会出现不同等级的 token。普通 token 便宜、快，适合公开信息。私有 token 主要依赖服务商承诺不训练、不保留。机密Token提供硬件隔离、远程证明和服务商不可见。审计级机密Token则进一步要求开源软件栈、可复现构建、透明日志、第三方审计和模型锁定。</p>
<p>这会让 token 不再只是算力商品，而变成带安全属性的计算凭证。天气查询可以用最便宜的 token，写周报可以用普通企业 token，但审合同、看病历、读私有代码库，就应该用机密Token。</p>
<hr>
<p><strong>不要神化机密计算</strong></p>
<p>机密Token不是魔法。它不能让模型不幻觉，不能自动阻止提示词注入攻击，不能保证模型没有行为后门，不能消灭侧信道攻击，不能阻止用户自己把秘密贴到错误的网站，不能保证客户端 SDK 没有 bug，不能让硬件厂商从信任边界里完全消失，也不能让复杂系统突然变简单。</p>
<p>它真正做的是缩小信任范围。过去你可能需要相信整个服务商、整个云、整个运维系统、整个日志系统、所有内部权限都不会出问题。机密Token把这个范围缩小为：硬件根、公开代码、可复现构建、透明日志、远程证明和少量必要组件。</p>
<p>这已经是很大的进步。安全从来不是包治百病，而是把必须信任的东西变少，变清楚，变可验证。</p>
<hr>
<p><strong>结语</strong></p>
<p>AI 越强，我们越想给它更多上下文；上下文越多，它越有用，也越危险。这就是 AI 时代的基本矛盾。自建模型可以减少外泄，但成本高、利用率低、模型弱、维护重。传统 MaaS 可以提供强模型、低门槛、弹性和经济性，但要求用户把秘密交给黑盒。</p>
<p>机密Token试图在两者之间开第三条路：使用 MaaS 的模型和算力，保留本地式的隐私边界，不靠承诺，而靠证明；不只买 token，而是买带证明的 token。</p>
<p>今天，机密 AI 还很早期。证明格式还不够统一，用户体验还不够丝滑，多 NPU、多节点、agent 工具链还会让证明更复杂，开源、构建、ledger、attestation、模型锁定之间也需要更好的标准。但方向已经很清楚。下一代 MaaS 不应该只出售更便宜的 token、更快的 token、更聪明的 token，它还应该出售可验证的 token、服务商看不到的 token、能证明自己从哪里来的 token。也就是，机密Token。</p>
