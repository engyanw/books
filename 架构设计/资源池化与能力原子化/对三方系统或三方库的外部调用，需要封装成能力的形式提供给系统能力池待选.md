
# 对三方系统或三方库的外部调用，需要封装成能力的形式提供给系统能力池待选

# 回复


是的，而且我认为这应该上升为 **Capability OS 的一条核心架构原则**：

> **任何三方系统、三方服务、三方 API、SDK、开源库或外部 AI 能力，只要被业务系统调用，都必须先被封装为 Capability，再进入 Capability Pool；Graph/Map 不允许直接依赖三方接口。**

这样才能真正实现前面定义的 **“能力统一抽象、资源统一调度、运行统一治理”**。

---

# 一、把“三方依赖”纳入 Capability 体系

原来的能力来源主要是：

```text
Capability Pool
├── Platform Native Capability
├── Self-developed Capability
└── Code Agent Generated Capability
```

现在应该扩展为：

```text
                    Capability Pool
                         │
        ┌────────────────┼────────────────┐
        │                │                │
        ▼                ▼                ▼
 Native Capability   Generated Capability   External Capability
        │                │                │
   平台原生能力       Code Agent开发      三方系统/三方库
                                         │
                              ┌──────────┼──────────┐
                              ▼          ▼          ▼
                           API/SaaS    SDK/Lib    AI Service
```

因此，Capability 的来源不再重要。

无论来自：

* 自研代码
* Serverless Function
* VM
* Container
* 三方 API
* SaaS
* SDK
* 开源库
* AI Model
* MCP Tool
* 外部 Agent
* 远程服务

最终都必须呈现为统一的：

> **Capability Contract**

---

# 二、为什么不能让 Graph 直接调用三方系统？

例如业务 Graph：

```text
OrderMap
   │
   ├── UserRisk
   ├── DeviceRisk
   └── Payment
```

如果 Payment 直接调用：

```text
Stripe API
```

或者：

```text
某银行支付 API
```

那么 Graph 实际上已经和三方系统耦合。

后果是：

```text
Graph
 ↓
Third-party API
```

三方 API 一旦发生：

* API 版本变化
* 参数变化
* SLA 变化
* 限流
* 价格变化
* 网络故障
* 安全策略变化

就会直接影响 Graph。

因此必须变成：

```text
Graph
 ↓
Payment Capability
 ↓
Third-party Adapter
 ↓
Third-party System
```

Graph 永远只认识：

> **Payment Capability**

而不知道底层到底是：

* Stripe；
* Adyen；
* 银行 API；
* 自研支付系统；
* 另一个 SaaS。

# 三、External Capability 应该是“能力适配器”

建议定义：

# External Capability Adapter

它不是简单的 SDK Wrapper，而是：

> **将外部系统的调用模型转换成 Capability OS 内部统一能力模型的适配层。**

例如：

```text
                    Payment Capability
                           │
                    Capability Contract
                           │
                    External Adapter
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
         Stripe API    Bank API      Payment SaaS
```

这样上层 Capability 不依赖具体供应商。



底层可以是：

```text

```

```text

```

而上层完全不用修改。

# 七、External Capability 的特殊性

但是需要特别强调：

> **外部 Capability 与内部 Capability 在“能力语义”上统一，在“运行属性”上不能假设完全相同。**

因为外部 Capability 的 Runtime 往往不在我们的 Resource Pool 中。

例如：

```text
Internal Capability

Capability
 ↓
Runtime
 ↓
Resource Pool
```

而：

```text
External Capability

Capability
 ↓
Adapter Runtime
 ↓
Internet / Private Network
 ↓
Third-party System
```

因此建议把 Capability 分成：

```text
Capability
│
├── Internal Capability
│
├── External Capability
│
└── Hybrid Capability
```

> **Capability-level Load Balancing**

# 十八、这会进一步强化我们之前的一个核心结论

整个 Capability OS 可以最终抽象成四层：

```text
┌────────────────────────────────────┐
│          Business Intent           │
│       用户真正想解决的问题          │
└─────────────────┬──────────────────┘
                  ↓
┌────────────────────────────────────┐
│             Capability             │
│         “系统能做什么”              │
└─────────────────┬──────────────────┘
                  ↓
┌────────────────────────────────────┐
│            Implementation          │
│       “这个能力由谁实现”             │
│                                    │
│ Native / Self / Generated / Third  │
└─────────────────┬──────────────────┘
                  ↓
┌────────────────────────────────────┐
│              Runtime               │
│        “在哪里、以什么资源运行”      │
└────────────────────────────────────┘
```

这个模型非常关键：

> **Capability 定义“做什么”，Implementation 定义“谁来做”，Runtime 定义“怎么运行”，Resource 定义“用什么生产资料运行”。**

四者不能混为一谈。

---

# 十九、我建议把这一条正式加入白皮书的“核心不变量”

新增：

### I11 — External Dependency Encapsulation

> **任何外部系统、第三方服务、第三方 API、SDK 或第三方库，不得被 Graph/Map 直接依赖；必须通过 Capability Adapter 封装为 Capability 后进入 Capability Ecosystem。**

### I12 — Provider Independence

> **Business Graph 依赖 Capability Contract，而不是依赖具体 Provider。Provider 可以在运行时根据 Capacity、SLA、Cost、Security、DFX 和 Policy 动态选择。**

### I13 — External Capacity Awareness

> **External Capability 必须具备下游 Capacity、Health、Load 和 SLA 感知能力，并支持动态路由、限流、熔断、降级及 Provider 切换。**

这三条加入之后，整个体系就从“能力原子化”进一步走向了：

# **能力生态化（Capability Ecosystem）**

最终真正形成：

> **用户不再选择产品，不再绑定服务，不再绑定技术实现，而是提出业务意图；平台从内部能力、第三方能力和 AI 自动生成能力构成的 Capability Ecosystem 中，选择最合适的能力实现，并通过 Map Runtime 按需实例化、弹性调度和持续优化。**

这实际上是后续 **Business OS / Capability OS 商业化**非常关键的一步：**平台不只拥有自己的能力，还可以把整个互联网、企业内部系统和第三方软件生态“能力化”。**
