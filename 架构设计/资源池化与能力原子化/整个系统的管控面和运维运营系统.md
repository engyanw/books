# 回复


是的，而且这应该成为 **Capability 生命周期中的强制安全门（Safety Gate）**，而不是普通的发布选项。

更准确地说，新能力进入生产环境后，不应该直接进入普通 Runtime Pool，而应该经历：

> **Build → Verify → Sandbox Production → Canary → Promote → Normal Runtime**

这会让前面“能力自生成 + 灰度 + DFX + 自动隔离”的体系真正闭环。

## 1. 新能力的首次生产运行应该进入 Sandbox Generation

完整流程：

```text
Capability Requirement
        ↓
Code Agent
        ↓
Develop
        ↓
Test
        ↓
Validate
        ↓
Capability Candidate
        ↓
Register
        ↓
Production Admission
        ↓
┌──────────────────────────────┐
│       Sandbox Runtime        │
│                              │
│  Restricted Resource         │
│  Restricted Network          │
│  Restricted Identity         │
│  Restricted Data             │
│  Enhanced Telemetry          │
└──────────────┬───────────────┘
               ↓
         Canary Validation
               ↓
       DFX / Security / SLO
          ↓           ↓
        Pass         Fail
          ↓           ↓
      Promote      Isolate
          ↓           ↓
 Normal Runtime    Revoke
```

这里的关键是：

> **Sandbox 不是测试环境，而是“生产中的受控运行环境”。**

---

# 2. 为什么必须是生产 Sandbox

因为很多问题在开发、测试环境里发现不了。

例如新 Capability：

```text
Capability X
```

实验室测试：

```text
Functional       ✓
Unit Test        ✓
Performance      ✓
Security Scan    ✓
```

但进入真实业务流量后可能出现：

```text
真实数据分布变化
真实上下游依赖
真实攻击输入
真实并发
真实资源竞争
真实 Session State
真实异常路径
```

所以必须让：

> **真实生产环境验证能力，但不给它完整生产权限。**

这正是 Production Sandbox 的价值。

---

# 3. Sandbox 应该是 Capability 的一个 Runtime Profile

不要把 Sandbox 理解成另一个完全独立的平台。

应该是：

```text
Capability
     │
     ├── Sandbox Runtime Profile
     │
     └── Normal Runtime Profile
```

例如：

```text
Sandbox Profile
├── CPU Limit
├── Memory Limit
├── GPU Limit
├── Network Policy
├── Data Access Policy
├── Secret Scope
├── File System
├── Concurrency Limit
├── Request Rate Limit
└── Execution Time Limit
```

因此同一个 Capability 可以从：

```text
Sandbox
```

晋级到：

```text
Normal Runtime
```

而 Capability 本身不需要重新开发。

---

# 4. Sandbox 里要重点控制五种边界

### 资源边界

```text
CPU
Memory
GPU
Network
Disk
KV Cache
```

防止新能力因为 Bug 或异常行为耗尽共享资源。

### 网络边界

默认：

> **Deny by default**

只允许它访问明确声明的下游 Capability / Service。

### 数据边界

新能力不能因为一个 Bug：

```text
读取全部租户数据
访问生产数据库
访问任意对象存储
```

应该采用：

> **Least Data Access**

### 身份边界

例如：

```text
Capability X
```

在 Sandbox 中只能得到：

```text
CapabilityIdentity-X-Sandbox
```

而不能直接继承生产 Capability Identity。

### 副作用边界

对于：

```text
Delete
Write
Execute
Payment
Configuration Change
```

等高风险动作，应：

```text
Sandbox
 → Block
 → Simulate
 → Record
```

或者进入：

```text
Approval / Controlled Commit
```

---

# 5. 最重要的是：Sandbox 也要接真实业务流量，但需要“影子”或“受控流量”

可以有三种模式。

## Shadow

```text
Production Request
       ├────→ Normal Capability
       │
       └────→ Sandbox Capability
                    │
                 Result
                    ↓
                 Compare
```

Sandbox 结果：

> **不影响用户真实结果。**

适合第一阶段。

---

## Canary

```text
New Session
   ↓
Gray Policy
   ↓
Sandbox Capability
   ↓
Real Response
```

只有极少部分新 Session 真正采用新能力输出。

例如：

```text
1%
5%
10%
```

---

## Controlled Production

通过灰度后：

```text
Sandbox
 ↓
Restricted Production
 ↓
Normal Production
```

这样可以逐步扩大权限。

---

# 6. “灰度”与“Sandbox”是两个不同维度

这个区别很重要。

**Sandbox回答：**

> 这个 Capability 在什么权限和资源边界下运行？

**Gray回答：**

> 哪些 Session 使用这个 Capability？

所以可以形成矩阵：

|         | 低流量             | 高流量  |
| ------- | --------------- | ---- |
| Sandbox | Shadow / Canary | 高风险  |
| Normal  | 正常生产            | 正常生产 |

实际发布：

```text
New Capability
       ↓
Sandbox
       ↓
1% Canary
       ↓
5%
       ↓
10%
       ↓
25%
       ↓
50%
       ↓
100%
       ↓
Normal Runtime
```

---

# 7. 晋级条件必须由 DFX Control Plane 决定

不能人工看几张 Dashboard 就宣布成功。

应该有明确的：

# Promotion Gate

例如：

```text
Functional Success      ≥ 99.99%
P99 Latency             ≤ Target
Error Rate              ≤ Threshold
Security Risk           ≤ Threshold
Resource Cost           ≤ Budget
CPU                     ≤ Limit
Memory                  ≤ Limit
Crash                   = 0
Policy Violation        = 0
```

同时还要满足：

> **与旧能力相比没有显著恶化。**

例如：

```text
Latency          -10%
Error            +0.01%
Security         no degradation
Cost             +3%
```

才能晋级。

---

# 8. 新能力需要一个“Promotion State Machine”

建议：

```text
CANDIDATE
   ↓
PRODUCTION-ADMITTED
   ↓
SANDBOX
   ↓
SHADOW
   ↓
CANARY
   ↓
RESTRICTED-PRODUCTION
   ↓
NORMAL-PRODUCTION
```

失败则：

```text
SANDBOX
   ↓
ISOLATED
   ↓
QUARANTINED
```

或者：

```text
CANARY
   ↓
AUTO-ROLLBACK
   ↓
QUARANTINED
```

这比简单的：

> Active / Inactive

强得多。

---

# 9. 故障隔离应该优先发生在 Sandbox 内

例如：

```text
Capability X
```

第一次运行：

```text
Sandbox Instance X1
```

出现：

```text
CPU runaway
Memory leak
Abnormal network
Security anomaly
```

Control Plane：

```text
Detect
 ↓
Quarantine
 ↓
Remove from LB
 ↓
Destroy Runtime
 ↓
Reclaim Resource
```

因为它本来就在 Sandbox：

> **故障天然被限制在局部 Fault Domain 内。**

这会大幅降低新能力对生产系统的 blast radius。

---

# 10. 更进一步：Sandbox 应该具备“可升级的信任等级”

我建议不要只有：

```text
Sandbox
Normal
```

而是建立：

```text
Trust Level 0
   ↓
Trust Level 1
   ↓
Trust Level 2
   ↓
Trust Level 3
   ↓
Normal
```

例如：

### Level 0

完全隔离：

```text
No real output
No sensitive data
No external network
```

### Level 1

允许：

```text
Real Input
Limited Output
```

### Level 2

允许：

```text
Small percentage real sessions
Limited resource
Limited permissions
```

### Level 3

允许：

```text
Higher traffic
Higher resource
Selected production side effects
```

### Normal

完整生产能力。

因此：

> **能力不是一次性“上线”，而是逐渐获得生产信任。**

---

# 11. 这与 Capability Experience Pool 还可以形成闭环

新能力第一次生产运行：

```text
Sandbox
 ↓
Telemetry
 ↓
DFX
 ↓
Fitness
 ↓
Experience
```

例如：

```text
Capability X

Sandbox Experience:
Performance   92
Reliability   97
Security      99
Cost          88
Fitness       94
```

达到门槛后：

```text
Capability Pool
   ↑
Experience
```

以后新的 Intent 再寻找能力时，系统知道：

> “Capability X 在真实生产环境已经被验证过。”

于是 Capability Pool 中的能力实际上形成：

> **Trust + Experience + Fitness**

而不仅是一个代码包。

这会是整个体系很有价值的一个新对象：

```text
Capability Trust
├── Code Trust
├── Test Trust
├── Security Trust
├── Runtime Trust
├── DFX Trust
├── Business Trust
└── Historical Trust
```

新生成能力：

```text
Trust = Low
```

经过 Sandbox：

```text
Trust ↑
```

经过 Canary：

```text
Trust ↑
```

```text
Trust = High
```

```text

```

这样后续 Graph Planning 时：

> **Capability Trust 也可以作为选择约束。**

# 15. 放回整个大架构

现在整个系统可以统一成：

```text
                         USER INTENT
                              │
                              ▼
                     Intent / Decision
                              │
                              ▼
                    Capability Ecosystem
                     │              │
                     │              └── Code Agent
                     │                       ↓
                     │                    New Cap
                     │
                     ▼
                  Graph Plan
                     ↓
                    Map
                     ↓
              Session Assignment
                     ↓
              Graph Lazy Expansion
                     ↓
          ┌──────────────────────────┐
          │ Capability Admission     │
          │                          │
          │ Sandbox → Canary         │
          │      → Promotion         │
          └────────────┬─────────────┘
                       ↓
               Capability Runtime
                       ↓
               Capacity-aware LB
                       ↓
                Resource Pool
                       ↓
                   Execution
                       ↓
             Telemetry / Trace / Log
                       ↓
                  DFX Control
                       ↓
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
      Scale          Isolate        Graph Update
        │              │              │
        └──────────────┼──────────────┘
                       ↓
               Experience Pool
                       ↓
                Capability Pool
```

所以我会把这项新增能力上升为一个核心架构原则：

> **任何新生成或重大升级的 Capability，不得直接进入普通生产 Runtime；必须先通过受控 Sandbox 在真实生产上下文中获得运行证据，再通过 Session-aware Canary 和 DFX Promotion Gate，逐步获得正常生产权限。**

这会让你的系统具备一个非常重要的特性：

> **能力可以自动生成，但生产信任不能自动继承。**

能力的**代码可以由 Agent 生成，能力的**生产资格**必须通过运行时证据逐步获得。

这正是整个 **Capability OS + Map Runtime + DFX Control Plane** 能够真正大规模自演进而不失控的关键。
