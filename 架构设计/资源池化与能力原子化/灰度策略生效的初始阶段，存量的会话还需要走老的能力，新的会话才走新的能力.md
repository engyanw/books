
# 灰度策略生效的初始阶段，存量的会话还需要走老的能力，新的会话才走新的能力

# 回复

是的，这个约束应该成为**灰度发布机制的一条基础不变量**。而且它会进一步推动我们把“请求”“会话”“Map Instance”“Graph Generation”四个概念分开。

核心原则可以定义为：

> **灰度切换只影响新会话，不迁移存量会话；存量会话保持原有 Graph / Capability Generation 继续运行，直到会话自然结束或达到强制迁移条件。**

这比简单的“新请求按比例路由”更严谨。

## 1. 灰度单位应该从 Request 升级为 Session

不能简单做：

```text
Request
  ↓
Gray Policy
  ↓
v1 / v2
```

因为同一个会话可能出现：

```text
Session A
  Request 1 → v1
  Request 2 → v2
  Request 3 → v1
```

这会破坏会话状态。

应该是：

```text
Session
   ↓
Session Assignment
   ↓
Graph Generation
   ↓
Capability Version
```

一次会话一旦完成灰度归属：

```text
Session S1 → Graph v1
Session S2 → Graph v2
```

那么整个会话生命周期内默认保持：

```text
S1 → v1 → v1 → v1 → ...
S2 → v2 → v2 → v2 → ...
```

---

## 2. 灰度切换应该存在一个“切换水位线”

例如：

```text
T0：Graph v1 全量
        ↓
T1：发布 Graph v2
        ↓
T2：灰度策略生效
```

从 T2 开始：

```text
新 Session → 按灰度策略 → v2
存量 Session → 继续 → v1
```

因此：

```text
               T2 灰度切换点
                    │
        ────────────┼────────────
                    │
Existing Session    │    New Session
      ↓             │         ↓
   Graph v1         │      Gray Policy
      ↓             │         ↓
继续运行            │      Graph v2
```

这实际上形成了一个非常清晰的：

> **Session-level Cutover Boundary**

---

## 3. Graph Generation 应绑定到 Session

因此前面提出的：

> Map Instance 绑定 Graph Generation

还要进一步细化成：

> **Session Instance 绑定 Graph Generation。**

例如：

```text
Session S100
  ├── Map Instance M100
  ├── Graph Generation G101
  └── Capability Instances
       ├── A-v1
       ├── B-v1
       └── C-v1
```

新会话：

```text
Session S101
  ├── Map Instance M101
  ├── Graph Generation G102
  └── Capability Instances
       ├── A-v1
       ├── B-v2
       └── D-v1
```

这样新旧版本可以自然共存。

---

## 4. Capability Runtime Pool 也必须按 Generation 隔离

例如新旧版本同时存在：

```text
Capability B
├── Generation 101
│   ├── B1
│   └── B2
│
└── Generation 102
    ├── B3
    └── B4
```

LB 不能简单把所有 B 实例混在一起。

应该先经过：

```text
Session
 ↓
Graph Generation
 ↓
Capability Generation
 ↓
Instance Pool
 ↓
LB
```

即：

> **先确定“哪一代能力”，再在该代实例池内做负载均衡。**

否则会发生：

```text
Session → v1
      ↓
LB
      ↓
B-v1 / B-v2
```

这是不可接受的。

---

## 5. 所以 LB 实际上是“Session-aware + Generation-aware”

完整路由应该是：

```text
External Request
       ↓
Session Resolver
       ↓
Session → Generation
       ↓
Capability Resolver
       ↓
Capability Generation
       ↓
Load Balancer
       ↓
Runtime Instances
```

LB 的决策顺序应该是：

1. **会话归属哪一代？**
2. **目标 Capability 是哪一代？**
3. **这一代有哪些健康实例？**
4. **哪个实例 Capacity 最合适？**

而不是直接：

> “谁负载最低就发给谁。”

---

## 6. 这会自然产生“旧版本排空”

当 v2 灰度开始后：

```text
New Session
    → v2

Existing Session
    → v1
```

随着旧会话自然结束：

```text
v1 Sessions
10000
 ↓
8000
 ↓
5000
 ↓
2000
 ↓
500
 ↓
0
```

此时：

```text
v1 Capability Instances
    ↓
Drain
    ↓
Scale In
    ↓
Resource Reclaim
```

于是新版本逐渐接管整个业务。

这其实就是：

> **Session-draining Deployment**

比传统的 Pod rolling update 更接近你这个体系的真实生命周期。

---

## 7. 灰度升级因此应该变成“四阶段”

### Phase 1：Prepare

```text
Graph v2
Capability v2
Runtime v2
```

全部完成：

* 注册
* 校验
* 资源准备
* 健康检查

但：

```text
Traffic = 0
```

---

### Phase 2：Canary

开始灰度：

```text
Existing Session → v1
New Session:
    99% → v1
     1% → v2
```

---

### Phase 3：Progressive Expansion

例如：

```text
1%
 ↓
5%
 ↓
10%
 ↓
25%
 ↓
50%
 ↓
100%
```

每一步：

> **只改变新 Session 的分配比例。**

存量 Session 不重新分配。

---

### Phase 4：Drain

当新 Session：

```text
100% → v2
```

此时：

```text
v1
    ↓
No New Session
    ↓
Drain Existing Session
    ↓
Instance Scale In
    ↓
Resource Reclaim
    ↓
Retire
```

---

## 8. 故障回滚也需要区分“新会话”和“存量会话”

例如 v2 出现严重故障。

通常应该：

```text
New Session
    → immediately stop assigning v2
    → fallback to v1
```

但是：

```text
Existing v2 Session
```

不能简单地强制切回 v1。

应该根据会话状态：

```text
Existing v2 Session
    │
    ├── Safe to continue → continue v2
    │
    ├── Stateless / restartable → migrate
    │
    └── Unsafe / corrupted → terminate + restart on v1
```

也就是说：

> **Rollback 不是简单的 Version Switch，而是 Session-aware Rollback。**

---

## 9. 这里还需要增加一个非常重要的对象：Session Contract

因为“存量会话继续走旧能力”要求系统知道：

> 一个 Session 究竟什么时候开始，什么时候结束？

因此需要定义：

```text
Session Contract
├── Session ID
├── Tenant
├── User
├── Device
├── Start Time
├── Last Activity
├── Timeout
├── Generation
├── Map Instance
├── State Location
└── Migration Policy
```

尤其是：

```text
Generation
```

应该成为 Session 的核心元数据。

---

## 10. 于是灰度策略和 Session Assignment 会形成两个不同层次

### Rollout Policy

决定：

> **新 Session 应该进入哪一个 Generation？**

例如：

```text
country = SG
AND device = mobile
→ Graph v2
```

或者：

```text
hash(session_id) < 5%
→ Graph v2
```

### Session Assignment

一旦确定：

```text
Session S1 → G102
```

这个结果就被持久化。

之后所有请求：

```text
S1 Request 1 → G102
S1 Request 2 → G102
S1 Request 3 → G102
```

不再重新计算灰度。

---

## 11. 这会让整个 Map Runtime 形成一个非常清晰的状态模型

```text
                     MAP RUNTIME
                          │
                          ▼
                   Session Resolver
                          │
             ┌────────────┴────────────┐
             ↓                         ↓
       Existing Session            New Session
             │                         │
             ▼                         ▼
      Keep Assigned Gen          Rollout Policy
             │                         │
             │                  ┌──────┴──────┐
             │                  ↓             ↓
             │                 G1            G2
             │
             └────────────┬───────────────┘
                          ↓
                   Graph Generation
                          ↓
                Graph Lazy Expansion
                          ↓
                 Capability Instance Pool
                          ↓
                 Capacity-aware LB
```

这和你前面定义的“地图徐徐展开”模型完全一致。

---

## 12. 最终可以形成一个非常重要的不变量

我建议把它直接写进架构原则：

> **Session Affinity Invariant**
>
> **一旦 Session 被分配到某一 Map/Graph Generation，该 Session 在正常生命周期内始终保持对该 Generation 的亲和性；新的灰度策略只影响新建立的 Session，不主动迁移存量 Session。**

再加两条：

> **Generation Isolation Invariant：不同 Graph Generation 的 Capability Instance Pool 必须逻辑隔离，LB 不得跨 Generation 分发。**

> **Drain Invariant：旧 Generation 停止接收新 Session 后，只通过存量 Session 自然结束或受控迁移逐步收缩，最终释放其 Capability Instance 与 Resource。**

---

## 13. 这样，整个动态地图模型就真正闭环了

现在完整生命周期可以表达成：

```text
                    Graph Evolution
                          │
                          ▼
                  Publish New Graph
                          │
                          ▼
                    Validate / Canary
                          │
                          ▼
                     Rollout Policy
                          │
               ┌──────────┴──────────┐
               ↓                     ↓
        Existing Session        New Session
               │                     │
         Keep Old Gen          Assign New Gen
               │                     │
               └──────────┬──────────┘
                          ↓
                   Map Instance
                          │
                   Lazy Expansion
                          │
                          ▼
                 Capability Instances
                          │
                   Capacity-aware LB
                          │
                   Elastic Scaling
                          │
                          ▼
                      Execution
                          │
                          ▼
                       Outcome
                          │
                          ↓
              Observe / SLO / Fault
                          │
                 ┌────────┴────────┐
                 ↓                 ↓
              Promote           Isolate
                 │                 │
                 ↓                 ↓
              New Gen          Rollback
                 │
                 ↓
            Old Gen Drain
                 │
                 ↓
          Resource Reclamation
```

因此你现在定义的灰度机制，本质上已经不是传统的“服务灰度”。

它更准确地应该叫：

# **Session-Aware Progressive Capability Delivery**

也就是：

> **以 Session 为灰度粘滞单元，以 Graph Generation 为版本边界，以 Map 为唯一外部入口，以 Capability Instance Pool 为运行载体，通过细粒度 Cohort、Capacity-aware LB、弹性扩缩、故障隔离和旧代 Drain 实现能力的渐进式演进。**

这个机制与前面“**能力静态、地图动态、运行时按需展开**”的模型是完全一致的。
