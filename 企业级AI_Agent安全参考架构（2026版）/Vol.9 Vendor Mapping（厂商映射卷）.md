## 1. 模块定位
厂商映射卷是通用架构向产品级落地的转化指南，承接前8卷的架构设计与技术选型体系，针对全球主流云厂商、大模型厂商与安全厂商，将架构中的9大平面、数十个能力域逐项对应到具体产品与服务，同时标注原生能力覆盖范围、需要补充增强的能力缺口、以及厂商专属的落地最佳实践。

本卷遵循厂商中立原则，客观呈现各厂商的能力优势与短板，不做商业推荐，核心目标是帮助企业基于自身已有的厂商合作体系、技术栈偏好、合规要求，选择最优的产品组合落地路径，避免从零开始全栈自研。

- **架构定位**：通用参考架构到厂商产品级的映射桥梁，输出可直接落地的产品级架构
- **能力定位**：覆盖7家主流厂商的全栈产品映射、能力对比、缺口分析与落地指引
- **落地定位**：企业厂商选型、POC测试、架构落地、供应商评估的直接参考依据

## 2. 设计目标
1. **精准映射**：将总体架构9大平面的所有核心能力，逐项对应到各厂商的具体产品与服务，无核心能力遗漏
2. **客观中立**：基于公开产品能力与行业共识进行评估，明确标注各厂商的能力优势、短板与能力缺口
3. **落地可用**：输出每个厂商的完整参考落地架构、产品组合方案与部署步骤，可直接用于POC与项目实施
4. **差距明确**：清晰说明厂商原生能力无法覆盖的安全场景，给出第三方/开源补全方案建议
5. **横向可比**：统一评估维度，跨厂商横向对比能力差异，支撑企业厂商选型决策
6. **场景适配**：针对不同规模、不同行业、不同合规要求的企业，给出差异化的厂商组合建议

## 3. 设计原则
### 3.1 Capability-based Mapping（按能力映射，而非按产品凑数）
严格以架构能力为基准，匹配厂商对应产品；厂商无对应原生能力的，明确标注为能力缺口，给出补全方案，不强行映射。

### 3.2 Native First, Supplement Second（原生优先，补充为辅）
优先使用厂商原生安全能力，降低集成成本；原生能力不足的，推荐第三方/开源方案补充，平衡落地效率与防护效果。

### 3.3 Vendor Neutrality（厂商中立）
所有评估基于公开产品参数与客观能力，不偏向任何厂商，如实呈现优势与短板，明确标注适用场景。

### 3.4 Production Grade（生产级导向）
优先评估生产级成熟、有SLA保障的商用服务；前沿预览版产品标注试用属性，不推荐核心生产场景使用。

### 3.5 Gap Transparency（缺口透明）
不回避厂商能力短板，明确列出架构要求与厂商原生能力的差距，给出可落地的补全路径。

## 5. AWS 厂商映射
### 5.1 整体定位
AWS是全球能力最完整的全栈云厂商，AI侧以Amazon Bedrock为核心的托管模型服务 + SageMaker自研训练体系为双主线，安全侧拥有从基础设施到安全运营的完整产品矩阵，企业级特性、合规认证、全球部署能力均为行业标杆。

AWS的AI安全体系以「云原生安全底座 + 模型服务基础安全」为核心，Agent层、运行时层的AI原生安全能力相对基础，需要企业基于AWS原生组件结合第三方/开源方案增强。

### 5.2 全架构产品映射表
| 架构平面 | 核心能力 | 对应AWS产品 | 能力等级 |
|----------|----------|-------------|----------|
| **业务平面** | 统一接入门户、业务编排、人工审核 | Amazon API Gateway、AWS AppSync、Amazon Lex、AWS Step Functions | ✅ 原生支持 |
| **AI平面** | 多模型接入、推理服务、RAG、模型管理 | Amazon Bedrock、Amazon SageMaker、Amazon OpenSearch Serverless（向量检索）、Amazon Kendra | ✅ 原生完整支持 |
| **Agent平面** | Agent运行引擎、多Agent编排、插件管理 | Amazon Bedrock Agents、LangChain on EKS、AWS Step Functions | ⚠️ 部分支持，Bedrock Agents能力偏基础，复杂Agent需自建 |
| **运行时平面** | 安全Sidecar、工具网关、沙箱隔离 | AWS App Mesh / Envoy、API Gateway + WAF、AWS Lambda沙箱、AWS Fargate | ⚠️ 基础网关与隔离能力完整，AI原生运行时防护需补充 |
| **数据平面** | 数据分类分级、加密、脱敏、审计 | Amazon S3、AWS KMS、Amazon Macie、AWS Lake Formation、Amazon GuardDuty S3 Protection | ✅ 原生完整支持 |
| **安全平面** | 身份权限、运行时防护、数据安全、威胁检测 | AWS IAM、AWS WAF、AWS Shield、Amazon GuardDuty、AWS Network Firewall | ✅ 传统安全能力完整，AI原生威胁检测需增强 |
| **治理平面** | 合规管理、审计、风险运营、SOC | AWS Security Hub、Amazon Detective、AWS Config、AWS Audit Manager、AWS Trusted Advisor | ✅ 原生完整支持，AI专项合规需补充 |
| **控制平面** | 配置管理、调度、生命周期、弹性伸缩 | AWS Systems Manager、Amazon EKS、AWS Auto Scaling、AWS CloudFormation / CDK | ✅ 原生完整支持 |
| **基础设施平面** | 计算、存储、网络、云原生底座 | EC2、EKS、VPC、S3、Route53、AWS Global Accelerator | ✅ 原生完整支持 |

### 5.3 AWS 企业级AI Agent安全参考落地架构
#### 核心部署架构
1. **入口层**：CloudFront + WAF + API Gateway 作为统一接入，前置DDoS防护与基础Web安全
2. **业务与Agent层**：Agent应用部署在Amazon EKS集群，基于LangChain/LangGraph构建，通过App Mesh实现服务治理与Sidecar注入
3. **AI能力层**：统一通过Amazon Bedrock调用多模型，私有模型部署在SageMaker；向量检索使用OpenSearch Serverless pgvector引擎
4. **安全管控层**：
   - 身份：IAM Identity Center统一身份，IRSA实现工作负载身份，API层面执行mTLS双向认证
   - 运行时：WAF做基础注入防护，第三方AI安全网关部署在EKS中补充提示注入、内容安全检测
   - 数据：S3全量加密，KMS统一密钥管理，Macie做敏感数据识别，Lake Formation做数据权限管控
5. **运营治理层**：Security Hub做统一安全运营中心，GuardDuty做威胁检测，Detective做链路溯源，Config做配置合规，CloudTrail做全操作审计
6. **基础设施层**：全栈部署在私有VPC，多AZ多Region部署，网络ACL + 安全组 + Network Firewall做多层网络隔离

### 5.4 核心安全能力详解
#### 模型安全（Bedrock & SageMaker）
- Bedrock默认数据不用于模型训练，支持VPC私有部署，数据不出企业VPC
- 内置基础内容过滤，支持自定义过滤规则，可对接第三方内容安全增强
- SageMaker支持模型加密存储、私有训练、VPC内推理，支持模型注册表与版本管理
- 支持模型水印、推理限流、API密钥托管，防范模型提取攻击

#### 零信任身份体系
- IAM Identity Center实现员工统一身份，支持SSO与多因素认证
- IAM Roles for Service Accounts (IRSA) 实现K8s工作负载的细粒度权限，无需静态密钥
- AWS Verified Access实现应用层零信任访问，替代传统VPN
- 支持ABAC属性权限控制，基于标签实现动态授权

#### 基础设施安全
- GuardDuty覆盖EC2、EKS、S3、Lambda等全栈威胁检测
- EKS原生支持Pod安全策略、节点安全组、镜像扫描
- KMS全栈密钥管理，支持客户托管密钥、密钥轮换、硬件安全模块
- 全操作通过CloudTrail审计，日志不可篡改归档

### 5.5 能力优势与短板
| 维度 | 优势 | 短板 |
|------|------|------|
| 全栈完整性 | 从基建到AI到安全运营全栈覆盖，产品间打通度高 | AI原生安全深度不足，Agent专属防护能力弱 |
| 合规能力 | 全球合规认证最全，覆盖金融、政务、医疗等各行业 | AI专项合规工具较少，需自行适配AI监管要求 |
| 企业级能力 | 多Region部署、高可用、SLA保障成熟 | 成本较高，大规模部署费用显著 |
| 生态开放性 | 兼容开源生态，支持第三方安全产品集成 | 深度使用后存在一定厂商锁定 |

### 5.6 落地最佳实践
1. 优先使用Bedrock托管模型服务，大幅降低基础设施与模型安全的运维工作量
2. 开启Bedrock VPC端点与数据不用于训练选项，从源头保障数据隐私
3. 复用现有IAM体系，基于IRSA实现Agent工作负载的最小权限，避免静态密钥
4. 基础安全全量使用AWS原生服务，AI运行时安全、工具网关等AI专属能力补充第三方方案
5. 启用Security Hub聚合所有安全告警，统一运营，避免多控制台分散管理

## 6. Microsoft Azure 厂商映射
### 6.1 整体定位
Azure凭借微软全球企业服务体系与OpenAI的深度合作，形成了「Azure OpenAI + AI Studio + Entra ID + Defender + Sentinel」的全栈AI安全体系，最大优势是与微软Office 365、Entra ID身份体系深度打通，企业级零信任能力行业领先，非常适合已深度使用微软生态的企业。

Azure在AI内容安全、身份治理、合规运营方面原生能力突出，Agent开发与运行时防护偏基础，复杂场景需结合开源方案增强。

| 架构平面 | 核心能力 | 对应Azure产品 | 能力等级 |
|----------|----------|---------------|----------|

| **AI平面** | 多模型接入、推理、RAG、模型管理 | Azure OpenAI服务、Azure AI Studio、Azure AI Search（向量检索）、Azure Machine Learning | ✅ 原生完整支持，OpenAI模型原生深度优化 |
| **Agent平面** | Agent运行、多Agent编排、插件管理 | Azure OpenAI Assistants、LangChain on AKS、Azure AI Studio Copilot Studio | ⚠️ 基础Agent能力完整，复杂多Agent需自建 |
| **运行时平面** | 安全Sidecar、工具网关、沙箱隔离 | Azure Application Gateway + WAF、Istio on AKS、Azure Container Apps、Azure Functions | ⚠️ 基础网关与隔离完整，AI原生运行时防护需补充 |
| **数据平面** | 数据加密、脱敏、分类分级、审计 | Azure Blob Storage、Azure Key Vault、Microsoft Purview、Azure SQL 数据脱敏 | ✅ 原生完整支持 |
| **安全平面** | 身份权限、运行时防护、威胁检测 | Microsoft Entra ID、Azure WAF、DDoS Protection、Microsoft Defender for Cloud | ✅ 传统安全能力完整，AI原生检测需增强 |
| **治理平面** | 合规、审计、风险运营、SOC | Microsoft Sentinel、Azure Policy、Azure Compliance Manager、Purview 合规治理 | ✅ 原生完整支持，AI合规工具持续完善 |

### 6.3 Azure 企业级AI Agent安全参考落地架构
#### 核心部署架构
1. **入口层**：Azure Front Door + WAF 做全球接入与DDoS/Web防护，API Management做统一API网关
2. **Agent与业务层**：Agent服务部署在AKS集群，基于LangGraph构建，服务网格实现流量治理与Sidecar注入
3. **AI能力层**：核心推理使用Azure OpenAI服务，私有模型部署在Azure Machine Learning；向量检索使用Azure AI Search
4. **安全管控层**：
   - 身份：Entra ID做统一身份，Conditional Access做条件访问，工作负载身份实现Agent细粒度权限
   - 运行时：Azure Content Safety做内容安全审核，第三方AI安全网关补充提示注入、工具调用管控
   - 数据：Purview做数据分类分级与治理，Key Vault统一密钥管理，存储全量加密
5. **运营治理层**：Microsoft Sentinel作为统一AI SOC，Defender for Cloud做基建威胁检测，Azure Policy做配置合规，Purview做数据合规
6. **基础设施层**：私有VNet内部署，多AZ多Region冗余，网络安全组 + Azure Firewall做多层网络隔离

### 6.4 核心安全能力详解
#### Azure OpenAI 安全体系
- 支持私有网络部署，数据默认不用于OpenAI模型训练，企业数据隔离
- 内置Azure Content Safety内容安全，支持多维度自定义过滤策略
- 集成Entra ID身份认证，支持基于角色的访问控制与审计
- 支持限流、配额管理、调用日志全审计，防范模型滥用与提取攻击

#### Entra ID 零信任体系
- 全球领先的企业级身份体系，支持SSO、多因素认证、条件访问、身份治理
- 工作负载身份支持，无需静态密钥即可访问云服务
- 权限管理、身份保护、访问评审全套身份治理能力
- 深度集成微软生态，Office、Teams、Azure全栈身份打通

#### 安全运营与合规
- Microsoft Sentinel云原生SIEM/SOAR，支持AI安全告警接入与自动化响应
- Defender for Cloud覆盖基建、容器、多类工作负载的威胁检测
- 合规认证全面，内置全球各区域监管合规包，AI合规持续更新
- Purview实现数据全生命周期治理，满足AI数据合规要求

### 6.5 能力优势与短板
| 维度 | 优势 | 短板 |
|------|------|------|
| 身份与零信任 | Entra ID行业领先，零信任能力最成熟 | 多模型支持弱，OpenAI生态绑定强 |
| 微软生态 | 与Office、Teams、Power Platform深度打通 | 厂商锁定程度高，迁移成本高 |
| 内容安全 | Azure Content Safety能力完善，多语言多模态支持 | Agent运行时安全、工具管控能力偏基础 |
| 合规运营 | Sentinel + Defender组合成熟，合规能力强 | 成本较高，企业级服务门槛高 |

### 6.6 落地最佳实践
1. 已使用微软生态的企业优先选择Azure，身份、办公、AI体系天然打通，落地效率最高
2. 开启Azure OpenAI的私有网络访问与内容安全，禁用公网访问
3. 基于Entra ID条件访问实现多维度动态授权，构建Agent场景的零信任体系
4. 用Sentinel统一纳管所有安全日志，补充AI安全检测规则，构建AI原生SOC
5. 利用Purview做AI训练数据与业务数据的统一治理，满足数据合规要求

## 7. Google Cloud Platform 厂商映射

### 7.3 核心安全能力详解

- 工作负载身份原生支持，GKE Workload Identity实现无密钥访问
- 零信任理念贯穿全栈产品设计

#### 数据安全
- Cloud DLP原生敏感数据识别与脱敏，能力行业领先
- Dataplex统一数据治理，支持数据分类分级与血缘追踪
- KMS统一密钥管理，支持客户托管密钥与外部密钥

### 7.4 能力优势与短板
| 维度 | 优势 | 短板 |
|------|------|------|
| 云原生技术 | 技术理念领先，Kubernetes/Istio原生支持最好 | 企业级服务与支持较弱 |
| 零信任理念 | BeyondCorp体系成熟，零信任原生设计 | 落地门槛高，适配成本高 |
| 数据安全 | DLP能力突出，数据治理完善 | AI原生安全运营能力一般 |
| 算力成本 | TPU大规模训练推理有成本优势 | 国内落地支持不足，合规适配弱 |

## 8. 大模型厂商专项映射（OpenAI / Anthropic）
### 8.1 整体定位
OpenAI与Anthropic是纯模型服务商，仅提供模型API服务，不提供完整的Agent运行、工具管控、基础设施安全能力。企业使用这类模型时，所有上层业务、Agent、安全、运营能力均需企业侧自行构建或由第三方提供。

这类厂商的安全能力集中在模型层内置安全与API基础管控，适合作为企业多模型体系中的模型供给方，配合企业自有安全架构使用。

### 8.2 安全能力映射表
| 架构能力域 | OpenAI 对应能力 | Anthropic 对应能力 | 能力等级 |
|----------|-----------------|--------------------|----------|
| 模型内置内容安全 | Moderation API，支持多维度内容检测 | Constitutional AI，宪法原则安全对齐 | ✅ 原生基础支持 |
| 提示注入防护 | 基础内置防护，可被绕过 | 原生对抗鲁棒性较强，仍需外层防护 | ⚠️ 模型层基础防护，不能替代运行时安全 |
| API访问控制 | API密钥、组织级权限、项目级隔离 | API密钥、工作区权限、企业级SSO | ⚠️ 基础管控，细粒度权限不足 |
| 数据隐私保护 | 企业级协议可承诺数据不用于训练 | 默认不保留用户数据，隐私保护更强 | ✅ 企业版可满足数据隐私要求 |
| 调用审计与限流 | 调用日志、用量统计、限流配置 | 调用日志、用量监控、配额管理 | ⚠️ 基础审计，无法满足企业级合规 |
| 模型安全 | 水印、防提取基础能力 | 模型对齐能力强，安全性口碑好 | ⚠️ 基础防护，高级保护需企业侧补充 |

### 8.3 企业侧落地补全方案
使用纯API模型厂商时，企业侧必须补充以下安全能力：
1. **统一模型网关**：部署企业侧模型网关，统一鉴权、限流、审计、日志，统一管控所有模型API调用
2. **运行时安全层**：在模型网关前部署AI运行时安全防护，补充提示注入检测、越狱检测、输出脱敏
3. **工具调用管控**：Agent工具调用全部经过企业侧工具安全网关，不能由模型直接调用外部服务
4. **数据防泄露**：输入输出双向数据防泄露，防止敏感数据通过模型对话泄露
5. **审计与合规**：全量调用日志留存企业侧，满足合规审计要求

### 8.4 优势与短板
| 优势 | 短板 |
|------|------|
| 模型能力行业领先，效果最优 | 企业级安全管控能力弱，无法独立落地企业级场景 |
| 模型迭代快，新能力跟进迅速 | 数据安全依赖企业承诺，合规证明不足 |
| API接入简单，开发成本低 | 厂商锁定风险极高，迁移成本大 |
| 基础安全内置，开箱即用 | 自定义安全能力弱，无法适配企业个性化安全需求 |

### 8.5 落地最佳实践
1. 绝不直接从业务端调用公网模型API，必须经过企业侧统一网关与安全层
2. 签署企业级数据保护协议，明确数据所有权与使用范围
3. 仅将其作为多模型体系中的一个选项，避免单一厂商依赖
4. 敏感数据场景优先使用私有化部署模型，公有API仅用于非敏感场景

## 11. 厂商选型与组合策略
### 11.1 不同场景选型建议
| 企业场景 | 推荐厂商组合 | 核心理由 |
|----------|--------------|----------|
| 跨国企业、全球业务 | AWS 为主 + Azure 补充 + 多模型接入 | 全球部署节点多，合规认证全，企业服务成熟 |
| 深度微软生态企业 | Azure 全栈 + Azure OpenAI | 身份、办公、AI体系打通，落地效率最高 |
| 国内政企、等保密评 | 阿里云 / 华为云 为主 | 国内合规完善，信创适配好，监管对接顺畅 |
| 技术导向、云原生优先 | GCP + 开源安全方案 | 云原生技术领先，开源生态友好，成本有优势 |
| 模型效果优先、多模型混合 | 统一模型网关 + 多家模型API接入 | 避免厂商锁定，按需调用最优模型 |
| 信创国产化要求 | 华为云 + 昇腾算力体系 | 自主可控程度最高，信创适配最完善 |

### 11.2 避免厂商锁定的架构策略
1. **统一抽象层**：在厂商服务之上构建统一抽象层（模型网关、工具网关、策略中台），业务不直接调用厂商原生接口
2. **开放标准优先**：优先选择兼容OpenTelemetry、SPIFFE、OPA等开放标准的产品，保留替换能力
3. **多厂商冗余**：核心能力至少有一个备选厂商，避免单一厂商故障或涨价导致业务停摆
4. **数据所有权可控**：核心数据、模型资产、策略规则全部存储在企业自有侧，不绑定厂商平台

### 11.3 混合云/多云落地原则
- 身份统一：构建全局统一身份体系，跨云身份互通
- 策略统一：安全策略集中管理，跨云统一分发执行
- 日志统一：全栈日志统一汇聚，统一运营分析
- 管控统一：控制平面统一调度，数据平面分布式部署
